# Discovery Report: CLO-318 — Severity ladder for HumanVerifier gates

## Problem framing

Workflow authors and operators using `HumanVerifier` gates are affected: today a human gate can pause a phase, but timeout urgency is only partially represented as static pending metadata. The current hook writes `severity` and a default `timeout_at`, then returns a failing verify result while waiting for a response; it does not apply low/medium/high escalation behavior after the deadline, nor does tracing/status output consistently expose severity. We want a spec-configurable severity ladder where low defaults to auto-approve after 1h, medium defaults to auto-fail after 24h, and high blocks indefinitely, with the runner honoring overrides. This is needed now because CLO-317 landed the scaffold and Phase 11's downstream UI/fallback work depends on traceable, machine-readable HITL urgency.

## Existing code

- `src/strategy/verify/human_verifier.rs` already defines `HumanVerifierConfig`, `HumanSeverity`, `HumanDecision`, `PendingRequest`, and `HumanResponse`. It writes `runs/<id>/pending/<phase>.json`, consumes `responses/<phase>.json`, maps approve/reject/comment-only to `VerifyResult`, and currently derives timeout metadata with `timeout_from(now, severity)` (`low=1h`, `medium=24h`, `high=None`).
- The same module does not yet compare the current time with `timeout_at`, cannot inject a fake clock, and cannot express a configurable timeout action. Missing response always returns `VerifyResult::Fail { waiting for human review... }`, so low auto-approve and medium timeout-specific auto-fail are not implemented.
- `src/phase_runner.rs` has `VerifyHookName::HumanVerifier(HumanVerifierConfig)`, invokes the hook after canonical artefact bytes are selected, emits a generic `verify_result` trace span, and writes normal completed/failed markers through `persist`/`MarkerWriter`. It does not pass severity into the trace span result or failed marker.
- `src/phase_runner/dispatch.rs` resolves `VerifyHookName::HumanVerifier` into `HumanVerifier::new(cfg.clone())`, so the least invasive configuration seam is to extend `HumanVerifierConfig` and the enum payload rather than adding a new dispatcher family.
- `src/trace.rs`, `src/trace/writer.rs`, and `src/trace/memory.rs` define `VerifySpanResult` and sinks. `VerifySpanResult` only carries pass/message/duration today, while the JSON schema already permits forward-compatible `loker.*` fields.
- `src/run_state/markers.rs` defines strict `StartedMarker`, `CompletedMarker`, and `FailedMarker` structs with `serde(deny_unknown_fields)`. Surfacing severity in status markers will require deliberate schema-compatible field additions and matching tests, not ad-hoc extra JSON.
- `docs/schemas/pending.schema.json` already requires `severity` and enforces `high => timeout_at: null`, `low|medium => timeout_at: string`. Existing negative fixtures validate this baseline; implementation changes should preserve the pending schema unless configurable high timeouts are intentionally introduced in a later task.
- `tests/phase_runner_human_verifier.rs` covers block-until-response and response consumption through `PhaseRunner`, while unit tests in `human_verifier.rs` cover pending payloads and response parsing. New timeout matrix tests can be colocated there and should avoid wall-clock sleeps.
- Roadmap Phase 11 describes T-049 as low 1h, medium 24h, high infinite, timeout-as-fail with fake-clock test, and resolution of EscalatingRetry interaction.

## Baseline score

**7/10.** The scaffold already has the right module boundaries, config object, pending schema, and phase-runner dispatch. The missing pieces are behaviorally important but localized: clock injection, timeout policy configuration, trace/status metadata, and documentation/tests. No rewrite is needed, though marker structs and trace interfaces need careful compatibility updates.

## Approaches

### Approach A — Extend HumanVerifierConfig with policy + clock seam

Add timeout/escalation policy fields to `HumanVerifierConfig`, keep the ladder logic inside `human_verifier.rs`, add an injectable clock function for tests, and thread optional severity metadata into trace/status outputs from `PhaseRunner`.

**Pros**

- Minimal churn around the existing T-048 scaffold and dispatch path.
- Keeps timeout behavior next to pending/response state machine logic.
- Easy to test deterministically with a fake clock and temp run directories.

**Cons**

- `HumanVerifierConfig` grows more complex before TOML workflow parsing is fully mature.
- Trace/status additions require small cross-module changes.
- EscalatingRetry semantics must be documented explicitly to avoid surprising retries after medium timeout failures.

**Effort:** M  
**Risk:** low

### Approach B — Introduce a generic HITL policy evaluator layer

Create a new policy module that consumes pending/response records and returns a typed HITL state (`Pending`, `TimedOutApprove`, `TimedOutFail`, `Blocked`, `Resolved`). `HumanVerifier` delegates to it and future UI/fallback routes can share it.

**Pros**

- Strong separation between filesystem IO and timeout policy decisions.
- Reusable for T-051/T-053 UI/fallback work.
- Could centralize custom policy validation.

**Cons**

- More code and API surface before downstream consumers exist.
- Requires a larger design for ownership of pending timestamps and overrides.
- Higher risk of over-abstracting the v0 scaffold.

**Effort:** L  
**Risk:** medium

### Approach C — Encode severity behavior only in workflow parser/runner wiring

Keep `HumanVerifier` simple and make the workflow/spec layer translate severity into precomputed timeout/action config, with `PhaseRunner` applying timeout decisions outside the hook.

**Pros**

- Treats severity as workflow policy rather than hook internals.
- Could align with future per-gate spec validation.
- Avoids adding much logic to `human_verifier.rs`.

**Cons**

- Splits pending/response state across hook and runner, making correctness harder to reason about.
- PhaseRunner becomes aware of a specific hook's timeout semantics.
- More invasive than necessary for current code layout.

**Effort:** M  
**Risk:** medium

## Chosen approach

**Approach A: Extend HumanVerifierConfig with policy + clock seam.** The existing scaffold already localizes HITL behavior in `human_verifier.rs`, so adding explicit default/override policy and fake-clock test seams there is the shortest path to satisfy T-049 without redesigning the runner. PhaseRunner should only receive enough optional metadata to include severity in trace/status outputs and to preserve current retry semantics.

## Discovery debt

None.
