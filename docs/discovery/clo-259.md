# Discovery Report: CLO-259 — Strategy::ParallelFanOut with min_responses floor

## Framing

**WHO** is affected: Workflow authors who need concurrent multi-backend execution with partial-failure tolerance. Today loker has `SingleModel` (one backend) and `EscalatingRetry` (sequential ladder), but no concurrent fan-out primitive. The `role/` module has `RoutingStrategy::Parallel` for backend selection, yet the `Strategy` trait layer—which produces schema-shaped phase results—lacks a parallel variant.

**WHAT** the current behaviour is vs WHAT we want: Currently, phases can only run one backend at a time or walk a sequential ladder. We want to dispatch a single prompt to N backend targets concurrently, collect per-target `Result<Output, BackendError>`, and yield outcomes to an aggregator. The strategy must short-circuit once `min_responses` successful responses arrive, cancelling remaining in-flight requests. If fewer than `min_responses` complete before all targets settle, a structured floor-violation error is surfaced.

**WHY now**: FR-6 in the PRD blocks the `design-doc-tdd` reference workflow (Phase `review` fans out to three families in parallel). CLO-257 (`SingleModel`) and CLO-258 (`EscalatingRetry`) are both complete, so the trait shape is mature and object-safe.

## Existing code

### Strategy trait (`src/strategy/mod.rs`)
- Trait `Strategy: Send + Sync` with `async fn execute(...) -> Result<StrategyOutput, StrategyError>`
- `StrategyKind` enum: `{ Single, Escalating }` — needs `Parallel` variant
- `StrategyOutput` struct with `attempts: Vec<Attempt>` — serializes against `phase_result_single.schema.json` and `phase_result_escalating.schema.json`
- `Attempt` struct captures per-call metadata (backend, model, usage, finish_reasons, verify outcome)
- `StrategyError` carries `Backend`, `NoBackends`, `PromptRender`, `Exhausted` variants

### Implementations
- `SingleModel` (`src/strategy/single_model.rs`): looks up one backend by name, renders template, calls `Backend::query`, returns one attempt.
- `EscalatingRetry` (`src/strategy/escalating_retry.rs`): walks `rungs` sequentially, records every attempt, short-circuits on verify pass. Demonstrates the pattern for multi-attempt output.

### Backend layer (`src/backend/mod.rs`)
- `Backend` trait with `async fn query(...) -> Result<QueryOutput, BackendError>`
- Typed `BackendError` variants (Timeout, RateLimit, Auth, Network, Parse, ExecutionFailed, Unavailable, Config)
- `QueryOutput` carries stdout, model, usage, duration, backend name
- `create_backend` resolves names to `Arc<dyn Backend>` handles

### Consensus / aggregation (`src/consensus.rs`)
- Pure functions: `majority_vote`, `weighted_vote`
- `ConsensusStrategy` enum: `First`, `Synthesis`, `Vote`, `WeightedVote`
- **Not wired into the `Strategy` trait**; operates on collected `BackendResponse` values
- No `Aggregator` trait exists yet at the strategy layer

### Tests & infrastructure
- Test pattern: `MockBackend` with `AtomicUsize` call counter + closure-driven responses, run via `tokio::runtime::Runtime::new().unwrap().block_on`
- Schema validation via `jsonschema` crate against `docs/schemas/*.schema.json`
- `futures = "0.3"` and `tokio` already in `Cargo.toml`

### Schemas
- `phase_result_parallel.schema.json` exists and expects: `branches[]`, `aggregator` (enum), `aggregate_output_path`, `verify` object
- `summary.schema.json` already lists `"parallel"` as a valid strategy kind
- `trace_event.schema.json` already lists `"parallel"` as a valid strategy kind

### Config / workflow layer
- `RoutingStrategy::Parallel` in `src/role/mod.rs` — this is role-level routing, not the strategy primitive we need
- No `TargetSpec` type currently exists; `SingleModel` uses `backend: String`

## Baseline score: 7/10

Strengths:
1. Trait is object-safe and proven by two implementations
2. Backend error types are rich and testable
3. Mock-backend test harness is robust
4. Parallel result schema already designed
5. `futures::stream::FuturesUnordered` + `tokio` available

Gaps:
1. `StrategyOutput` uses `attempts: Vec<Attempt>`; parallel schema expects `branches[]` — requires conditional serialization
2. No `Aggregator` trait or enum at the strategy layer
3. No `TargetSpec` struct (issue description references it)
4. `StrategyKind` missing `Parallel` variant
5. `consensus.rs` is not connected to strategy execution

The score of 7 reflects that the foundation is solid but the output shape and aggregator wiring need adaptation. A full rewrite is unnecessary; an incremental extension of the existing trait and output structs is appropriate.

## Approaches identified

### Approach 1: Minimally-invasive struct expansion (chosen)
- Keep `Strategy` trait signature unchanged
- Add `StrategyKind::Parallel` variant
- Create `ParallelFanOut` struct implementing `Strategy`
- Add `Aggregator` enum (`Concat`, `AnyFail`, `Vote`, `LLMJudge`) as a simple labelled field on `StrategyOutput`
- Implement custom `Serialize` for `StrategyOutput` that emits `attempts` (single/escalating) vs `branches` (parallel) based on `StrategyKind`
- `ParallelFanOut` uses `futures::stream::FuturesUnordered` to dispatch concurrently, tracks successes, short-circuits on `min_responses`, cancels remaining via `drop(futures)`
- Floor violation returns `StrategyError` with new variant or wraps in `Exhausted`-style output
- Pros: minimal breaking changes, leverages existing test patterns, satisfies ACs without scope creep
- Cons: `StrategyOutput` serialization gets more complex; aggregator is a schema label in v0, not active logic
- Effort: S-M
- Risk: low

### Approach 2: Full aggregator trait integration
- Introduce `Aggregator` trait: `fn aggregate(inputs: &[BranchResult]) -> Result<AggregatedOutput, AggregationError>`
- Implement `Concat`, `AnyFail`, `Vote`, `LLMJudge` as concrete aggregators
- Wire `Box<dyn Aggregator>` through `ParallelFanOut` constructor so `execute` returns the aggregated result
- Pros: matches PRD FR-9..12 architecture, future-proof, aggregator logic lives where it belongs
- Cons: adds a new trait family, changes `ParallelFanOut` signature, risks scope creep beyond the ACs (issue says aggregator may land in follow-up)
- Effort: M
- Risk: medium

### Approach 3: Enum-based unified strategy
- Replace the `Strategy` trait with a `Strategy` enum holding all variants' config
- Single dispatch method on the enum
- Pros: easy TOML deserialization, closed set of variants, no trait object overhead
- Cons: massive refactor — `SingleModel` and `EscalatingRetry` already ship as structs implementing the trait; enum switch breaks all call sites, tests, and the compile-time object-safety check in `strategy/mod.rs`
- Effort: L
- Risk: high

## Approach chosen: Approach 1

**Reason**: The issue explicitly says "Aggregator trait stub may land here or in a follow-up; prefer threading `Box<dyn Aggregator>` through the runner now to avoid a second refactor." This signals that the primary deliverable is the `ParallelFanOut` strategy with `min_responses` concurrency semantics, not a full aggregator suite. Approach 1 satisfies all listed acceptance criteria:
- `cargo test strategy::parallel_fanout` covers the four wiremock cases ✓
- No additional public API beyond the new enum variant + existing `Strategy::execute` entrypoint ✓
- `make check` clean ✓

We still introduce an `Aggregator` enum so the parallel schema validates, but actual aggregation logic can be deferred.

## Discovery debt

1. **Aggregator trait design**: The full `Aggregator` trait shape (trait methods, error types, streaming vs batch API) needs a brief design spike before M3. This is captured in the PRD as a follow-up.
2. **`family_of(backend_id)` lookup**: The parallel schema requires `family` per branch. Where does family resolution live? `Backend::family()` method? Config lookup? This is an open question from PRD §8 that affects `ParallelFanOut` output population.
3. **Cancellation semantics**: `FuturesUnordered` drop semantics cancel spawned futures, but our `Backend::query` trait method takes `&self` and has no cancellation handle. In practice the underlying HTTP client (reqwest / genai) may continue the request even after the future is dropped. This is acceptable for v0 but should be documented.
