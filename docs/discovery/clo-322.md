# Discovery Report: CLO-322 — Sessions UI

## Problem

Build three server-rendered HTML views (index, run detail, pending gates)
on top of the T-052 axum daemon. No JS framework, minimal CSS, localhost-only.

## Existing code

### `src/ui/` (T-052 — Daemon)

- **`mod.rs`**: Module structure. Re-exports `discover_runs`, `RunSummary`, `serve`.
- **`discovery.rs`**: `discover_runs(project_root)` scans `runs/` directories,
  reads `manifest.json`, scans `markers/` for phase status. Returns
  `Vec<RunSummary>`. Thoroughly tested (13 tests).
- **`routes.rs`**: Axum `Router` with `GET /` returning JSON runs list.
  `AppState { project_root }`. Clean, test-covered (2 tests).
- **`serve.rs`**: Daemon bootstrap — binds to localhost, runs axum with
  graceful shutdown. Test helper `spawn_test_daemon`.

### `src/hitl_server/` (T-051 — HITL Gates)

- **`routes.rs`**: `render_gate_view(config) -> Html<String>` renders per-gate
  HTML with approve/reject forms. `approve()`/`reject()` handlers write
  response JSON. Uses raw string formatting (not a template engine).
  Uses `PhaseLock` from `run_state`.

### Template engines available

- **`minijinja`** (already in deps): Used in `src/template/` for prompt
  templates. Runtime-compiled, flexible. `Environment` with strict mode.
  Custom filters (`json_encode`, `join`, `first`, `last`).
- **`askama`** (not yet in deps): Compile-time templates, type-safe.
  `askama_axum` provides seamless `IntoResponse`.
- **`maud`** (not yet in deps): Macro-based HTML in Rust.

### Trace subsystem

- **`src/trace.rs`**: `TraceSink` trait, `TraceWriter` (append-only JSONL).
  `InMemorySink` for tests. Spans have `PhaseSpanContext`, `AttemptSpanContext`,
  etc. Trace events are JSONL lines, one per event.

### Run directory layout

```
runs/<workflow>-<timestamp>-<short-uuid>/
  manifest.json
  markers/           # phase.started, phase.completed, phase.failed
  pending/           # <phase>.json (HITL gate context)
  responses/         # <phase>.json (human decision)
  artefacts/         # phase outputs
  trace.jsonl        # OpenTelemetry GenAI spans
```

### Route handlers to extend

Current T-052 router:

```rust
Router::new()
    .route("/", get(runs_list))  // returns JSON today
    .with_state(state)
```

T-051 gate routes are served on a separate one-shot server today (different
port). For the daemon, they need to be mounted at `/pending` or `/gates/:id`.

## Baseline score: 7/10

The T-052 daemon infrastructure is solid and well-tested. No rewrite needed.
Additions are purely additive — new routes, new templates. The only gap is
the missing HTML rendering, which is exactly what T-053 adds.

## Approaches

### Approach 1: Askama (compile-time templates)

**Summary**: Add `askama` + `askama_axum`. Write `.html` template files for
each view. Templates are compiled at build time with type-checked variables.

**Pros**:
- Spec explicitly calls for askama or maud.
- Type-safe — template variable mismatches are compile errors.
- Clean separation of HTML from Rust logic.

**Cons**:
- New dependency (2 crates).
- Template files live outside `.rs` files.

**Effort**: M (3 views, templates + routes + CSS).
**Risk**: Low.

### Approach 2: Maud (macro-based HTML)

**Summary**: Add `maud`. Write HTML inline in Rust using `html! {}` macro.
Everything stays in `.rs` files.

**Pros**:
- Spec explicitly calls for askama or maud.
- Pure Rust — no separate template files.
- Compile-time checked.

**Cons**:
- New dependency.
- HTML mixed with Rust logic, can be harder to read for complex pages.
- Snapshot tests must include the macro output, less clean than template
  file-based snapshots.

**Effort**: M (3 views, inline HTML + routes + CSS).
**Risk**: Low.

### Approach 3: Minijinja (existing dep)

**Summary**: Use the already-present `minijinja` engine to render HTML
templates stored as const strings or loaded from files.

**Pros**:
- Zero new dependencies — minijinja is already in Cargo.toml.
- Familiar API — used for prompt templates.
- Template engine handles iteration, conditionals, filters natively.

**Cons**:
- Not in the spec ("askama or maud"). The Linear task body explicitly
  asks for askama or maud.
- Runtime template errors (not compile-time).
- Adds runtime cost of parsing templates.

**Effort**: M (3 views, templates + routes + CSS).
**Risk**: Low.

## Chosen approach

**Approach 1: Askama**

Reason: The spec explicitly calls for askama or maud. Askama provides the
best separation of concerns — templates are clean HTML files, routes are
Rust. Compile-time safety catches template errors before they reach
production. `askama_axum` integrates directly with the existing axum router.
The two-crate dependency cost is minimal for the safety gained.

## Discovery debt

None. All dependencies (T-052 daemon, T-051 routes) are in place. The path
from template to route to snapshot test is well-understood.
