# Discovery Report: SSE tail-f of trace.jsonl (CLO-323)

## Problem Framing
Users of the Loker daemon UI currently view run trace events statically or via page refresh. During long-running workflows, this creates a "blind spot" where users cannot see real-time progress or failures until the run concludes or they manually reload. We want to provide a live-updating trace timeline using Server-Sent Events (SSE) to stream new events from `trace.jsonl` as they are written.

## Existing Code
- **`src/ui/routes.rs`**: Contains the daemon router. `run_detail` currently reads the last N lines of `trace.jsonl` synchronously using `trace_reader::tail_trace_file`.
- **`src/ui/trace_reader.rs`**: Implements `tail_trace_file` which reads the entire file into memory and takes the last N lines. This is sufficient for initial page load but inefficient for live streaming.
- **`docs/designs/clo-294-run-dir-layout.md`**: Defines `RunDir::trace_path()` which provides the canonical path to `trace.jsonl`.
- **`docs/designs/clo-293-trace-jsonl.md`**: Describes the `TraceWriter` which appends events to the file.

**Baseline Score: 8/10**. The infrastructure for run directory management and trace reading is already in place. The primary additions are the SSE endpoint, the file watcher, and the frontend `EventSource` glue.

## Identified Approaches

### Approach 1: `notify` crate + Asynchronous Streaming (Chosen)
Implement a watcher using the `notify` crate that monitors `trace.jsonl` for write events. When a change is detected, the server reads the newly appended bytes and sends them as SSE events to the client.
- **Pros**:
    - Real-time delivery (sub-second).
    - Efficient resource usage (event-driven, not polling).
    - Decoupled from the writer logic.
- **Cons**:
    - Handling file system event noise (e.g., double events).
    - Complexity in managing the file offset (cursor) across reconnections.
- **Effort**: M
- **Risk**: Medium

### Approach 2: Simple Periodic Polling
The server polls the `trace.jsonl` file size every 500ms. If the size increases, it reads the delta and ships it via SSE.
- **Pros**:
    - Simple implementation.
    - No dependency on `notify`.
- **Cons**:
    - Latency is bound by polling interval.
    - Unnecessary IO overhead.
- **Effort**: S
- **Risk**: Low

### Approach 3: In-Memory Event Bus
Modify `TraceWriter` to send every written event to a `tokio::sync::broadcast` channel. The SSE endpoint subscribes to this channel.
- **Pros**:
    - Lowest possible latency.
    - No file IO for the stream.
- **Cons**:
    - Requires altering core `TraceWriter` and the `PhaseRunner` dependency injection.
    - Server restarts lose the stream state (though file tailing handles this better).
- **Effort**: M
- **Risk**: Medium

## Chosen Approach
**Approach 1 (`notify` crate)**.
Reason: It provides the best balance of performance and architectural cleanliness. It implements a true "tail -f" behavior that remains robust even if the writer is an external process or the server restarts, whereas an in-memory bus is too tightly coupled and polling is too sluggish.
