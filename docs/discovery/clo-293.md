# Discovery Report — CLO-293: Implement trace.jsonl writer with OpenTelemetry GenAI semantic conventions

## Problem framing

Loker's PhaseRunner (CLO-292) can now execute phases end-to-end, but the system is completely opaque to observability tooling. Every backend call, strategy decision, aggregator fold, and verify-hook invocation happens without leaving a durable, structured record. This makes debugging, cost analysis, and compliance impossible. The manifest already defines a `TraceJsonl` artefact kind, and `trace_event.schema.json` exists, but no code path actually writes traces. The desired behaviour is an append-only `trace.jsonl` per run that emits OpenTelemetry GenAI-compatible spans so existing OTel tooling can ingest the file. This is needed now because it is a PRD requirement (FR-20) and downstream run/resume/debug tasks need structured traces.

## Existing code

### What exists

- **`src/phase_runner.rs`** — `PhaseRunner::run(...)` is the key lifecycle hook where all observable events occur: strategy execution, aggregation, verify, manifest append, and marker writes. It already owns the full phase lifecycle.
- **`src/phase_runner/dispatch.rs`** — Resolves strategy, aggregator, and verify-hook implementations by name.
- **`src/phase_runner/persist.rs`** — Helpers for `start_attempt`, `commit_success`, and `record_terminal_failure`.
- **`src/backend/mod.rs`** — `Backend::query()` returns `QueryOutput` carrying `model`, `duration`, `usage` (`TokenUsage` with `prompt_tokens` / `completion_tokens`), and `backend` name. These map directly to OTel GenAI span fields.
- **`src/strategy/mod.rs`** — `StrategyOutput` contains `attempts: Vec<Attempt>` where each `Attempt` has `backend`, `model`, `usage` (`TokenUsageReport` with `input_tokens` / `output_tokens`), `finish_reasons`, `output_path`, and `verify` outcome. `StrategyKind` (Single, Parallel, Escalating) is the strategy discriminator.
- **`src/aggregator/mod.rs`** — `Aggregator` enum with concat, vote, LLM judge, any_fail, all_pass, first. Aggregation produces canonical bytes.
- **`src/strategy/verify/mod.rs`** — `VerifyHook` trait with `name()`, `verify(ctx)` → `VerifyResult`. `VerifyContext` carries `stdout`, `stderr`, `exit_code`, `backend_name`, `model`.
- **`src/manifest.rs`** — Already has `Kind::TraceJsonl`. Contains TODO(T-029) comments: "replace eprintln with injected log sink once trace writer lands".
- **`src/run_state/load.rs`** — Also has TODO(T-029) and TODO comments about replacing eprintln with trace logger. Already references `Kind::TraceJsonl` in orphan sweep.
- **`docs/schemas/trace_event.schema.json`** — Existing schema that uses an event model (`loker.event` enum) with OTel GenAI fields. This is close but the issue specifies a span model with `parent_span_id`.
- **`src/run_state/atomic.rs`** — `atomic_write` is the existing crash-safe write primitive we can reuse for the trace file (or use standard line-buffered append since trace.jsonl is explicitly NOT manifest-registered and mutable).

### Gaps for CLO-293

- No `TraceWriter` or `TraceSink` trait exists. There is no abstraction for emitting trace spans.
- `PhaseRunner::run()` does not capture or emit any trace data.
- No `trace_span.schema.json` exists; `trace_event.schema.json` uses events rather than spans with `parent_span_id`.
- The issue requires `loker.run_id`, `loker.phase`, `loker.attempt`, `loker.strategy`, `loker.aggregator`, `loker.verify_hook`, `loker.outcome` — none of these are collected in a single trace record today.
- Tests have no way to capture in-memory traces; the `TraceSink` trait is needed for testability.
- The TDD test contract (`tests/trace_jsonl.rs`) does not exist yet.

### Baseline score

**7 / 10.** PhaseRunner and all data sources exist and are well-typed. Backend outputs already carry token usage and model metadata. The manifest knows about `TraceJsonl`. The remaining work is a writer module, a sink trait, schema definition, and PhaseRunner instrumentation — additive integration rather than a rewrite.

## Approaches identified

### Approach A — TraceSink trait + TraceWriter, wired into PhaseRunner

- **Summary**: Define a `TraceSink` trait with methods for emitting spans (phase start, backend call, aggregator, verify, outcome). Implement `TraceWriter` with a line-buffered append writer to `run_dir/trace.jsonl`. Add a second `InMemorySink` for tests. Wire calls into `PhaseRunner::run()` at every lifecycle point.
- **Pros**
  - Directly matches the T-029 spec: OTel GenAI spans, `parent_span_id`, `loker.*` namespace.
  - `TraceSink` enables in-memory test capture (TDD contract requires this).
  - Append-only writer is simple, fast, and naturally line-buffered.
  - Reuses existing data types (`QueryOutput`, `Attempt`, `VerifyResult`) without transformation layers.
- **Cons**
  - Requires instrumenting every point in `PhaseRunner::run()` which is the hottest code path.
  - `trace_event.schema.json` would need to be superseded by `trace_span.schema.json` (or we keep both; the issue explicitly asks for spans).
- **Effort**: M
- **Risk**: Low

### Approach B — Extend existing trace_event.schema.json event model

- **Summary**: Reuse `trace_event.schema.json` and emit events rather than spans. Add a writer that appends events to `trace.jsonl`. Wire into PhaseRunner.
- **Pros**
  - Schema already exists; no new schema to write.
  - Event model is simpler — no `parent_span_id`, `span_id`, `trace_id` to manage.
- **Cons**
  - Does NOT match the issue spec, which explicitly requires "OpenTelemetry GenAI span" with `parent_span_id`.
  - Existing OTel tooling expects spans, not custom events.
  - The TDD contract names span concepts ("phase span", "backend span", "parented correctly").
- **Effort**: S
- **Risk**: High (doesn't meet spec)

### Approach C — Integrate an external OTel SDK (opentelemetry-rust)

- **Summary**: Add the official `opentelemetry` crate, configure a `trace.jsonl` exporter, and instrument PhaseRunner/backends with OTel macros or manual span creation.
- **Pros**
  - Native OTel compliance out of the box.
  - Future-proof for live OTLP export (post-v0 non-goal but could be easier).
  - Rich span context propagation, sampling, etc.
- **Cons**
  - Heavy dependency (opentelemetry + opentelemetry_sdk + exporter) for a v0 feature.
  - The spec asks for a simple append-only JSONL file, not a full OTel pipeline.
  - `TraceSink` testability pattern would be harder to layer on top of an external SDK.
  - Overkill for the stated non-goals (no live OTLP, no metrics, no logs).
- **Effort**: L
- **Risk**: Medium-High

## Chosen approach

**Approach A — TraceSink trait + TraceWriter wired into PhaseRunner.**

This is the only approach that satisfies all acceptance criteria:
- OTel GenAI span model with `parent_span_id`.
- `loker.*` namespace for Loker-specific fields.
- Append-only line-buffered writer with configurable fsync gate.
- `TraceSink` trait for test in-memory capture.
- No external OTel SDK dependency (matches non-goals).

## Discovery debt

None. CLO-292 (PhaseRunner) is already merged; all lifecycle hooks needed for trace emission are present. The blocked_by relationship to CLO-292 in Linear is satisfied.
