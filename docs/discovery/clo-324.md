## 1. Problem Framing

**WHO is affected**: loker users who run `loker ui --serve` and review HITL gates in a web browser. Any regression in the UI daemon's security posture exposes these users to cross-origin attacks, path traversal, or stale-lock issues.

**WHAT the current behaviour is**: The UI daemon (`src/ui/routes.rs`) has seven working routes, basic `run_id` string sanitisation, and a non-loopback bind warning in `serve.rs`. However, there are:
- No CSRF / Origin-check defences on POST handlers.
- No artefact route (`GET /runs/<id>/artefact/<path>`).
- No security response headers (CSP, X-Frame-Options, CORP, Referrer-Policy).
- No automated tests for symlink escape, path traversal beyond string-contains, cross-origin SSE, replay/race behaviour, or lock heartbeat expiration.

**WHAT we want**: A dedicated, automated threat-model test suite that exercises every mitigation from the accepted threat model (`docs/security/2026-04-25-ui-threat-model.md`), plus a top-level `docs/threat-model.md` that can be reviewed independently.

**WHY now**: M11 close is gated on this suite (roadmap Phase 12). Without it, security regressions in the UI layer slip into releases undetected.

## 2. Existing Code

| Module | Role | Security posture |
|--------|------|------------------|
| `src/ui/routes.rs` | axum router + handlers | Basic `run_id` sanitisation (`..`, `/`, `\` rejected). POST handlers accept any `Origin`. No artefact route. No lock-timeout tests. |
| `src/ui/serve.rs` | Daemon bootstrap | Emits `WARN` on non-loopback bind. Defaults to `127.0.0.1:8080`. |
| `src/ui/sse.rs` | SSE streaming | No `Access-Control-Allow-Origin` emitted (correct for same-origin defence, but not tested). |
| `src/run_state/phase_lock.rs` | Advisory lock (`<phase>.json.lock`) | `O_CREAT \| O_EXCL` lock with heartbeat. Race-guard on existing `responses/<phase>.json`. No automated heartbeat-expiry test in UI layer. |
| `src/hitl_server/routes.rs` | One-shot fallback server | Reused by daemon. Same POST handlers, no artefact route. |
| `tests/ui_daemon.rs` | Integration smoke tests | Covers index, empty list, corrupt run skip, graceful shutdown. No security assertions. |

**Baseline score: 5/10.**

The UI layer is functional but the security surface is undertested. The existing threat model doc already enumerates the exact tests needed (§5 test list), so the design debt is low.

## 3. Approaches

### A. Add security tests to existing test files

- **Summary**: Extend `tests/ui_daemon.rs` and `src/ui/routes.rs` unit tests with security assertions.
- **Pros**: Minimal file churn; reuses existing `DaemonFixture`.
- **Cons**: Security contract buried among functional tests; harder to use as a readable M11 gate document.
- **Effort**: S
- **Risk**: low

### B. Dedicated threat-model test file + incremental production hardening (chosen)

- **Summary**: Create `tests/ui_threat_model.rs` that follows the exact §5 test list from the threat model doc. Add missing production code (artefact route, Origin validation, security headers) only as needed to make those tests pass.
- **Pros**: Clear M11 gate document; 1:1 mapping with accepted threat model; separates security contract from UI functionality.
- **Cons**: Requires adding a new artefact route and middleware layer for headers.
- **Effort**: M
- **Risk**: low

### C. Refactor into security-first middleware layer

- **Summary**: Extract all security checks (Origin, content-type, CSP, etc.) into axum middleware, then test the middleware in isolation.
- **Pros**: Clean architecture; reusable for any new routes.
- **Cons**: Over-engineering for a v0 surface with only seven routes; touches existing route signatures and unit tests.
- **Effort**: L
- **Risk**: medium

---

## 4. Choice

**Approach B** is chosen. The threat model doc already enumerates 20+ concrete tests. A dedicated `tests/ui_threat_model.rs` file creates a direct, auditable trace from the accepted threat model to the CI gate. Production changes are limited to:

1. Adding `GET /runs/:id/artefact/:path` to the daemon router (with traversal + symlink checks).
2. Adding Origin + content-type validation to POST handlers.
3. Adding security headers (CSP, X-Frame-Options, CORP, Referrer-Policy) to responses.
4. Ensuring the advisory-lock heartbeat expiry is testable.

These are incremental additions, not a refactor, and they align with the TDD flow (failing test first, then implementation) the roadmap prescribes.
