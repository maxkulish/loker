# Discovery Report: CLO-327 — Wire Phase-Based Runner into `loker run`

## Problem Frame

**WHO**: Loker users authoring phase-based workflows (design → review → plan pipelines)
via the `[[phases]]` TOML grammar. The mentis project's `task-kickoff.toml` is the first
real-world workflow.

**WHAT**: Today `loker run` silently produces an empty manifest when given a phase-based
workflow — the step-based runner has no `phases` field so `[[phases]]` blocks are dropped
at deserialisation. The phase-based pieces (grammar parser in `grammar.rs`, executor in
`phase_runner.rs`) both exist with test coverage but are never connected to the `loker run`
dispatch path.

**WHY NOW**: Phase-based workflows are the intended primary workflow format. Without this
wiring, the gramma/phase-runner investment is dead code. The mentis workflow is blocked
on this.

## Existing Code

### CLI dispatch (`src/main.rs:1086`)

`Commands::Run { name, spec, var, ... }` calls `run_workflow(...)` which:

1. Calls `workflow::find_workflow(name)` to locate the `.toml` source
2. Calls `workflow::load_workflow_from_source(source)` which deserialises as step-based
   `workflow::Workflow` via `toml::from_str` — **no `phases` field → silent drop**
3. Creates `WorkflowRunner` and calls `runner.run(&wf)` — iterates `workflow.steps` (empty)
   and exits cleanly

The comment at `src/main.rs:1458` explicitly notes: *"Effective once the phase-based runner is wired."*

### Step-based Workflow (`src/workflow/mod.rs:124`)

```rust
pub struct Workflow {
    pub name: String,
    pub description: Option<String>,
    pub extends: Option<String>,
    pub steps: Vec<Step>,
    // ...
}
```

No `phases` field. Deserialised via `#[derive(Deserialize)]` — unknown keys (like `[[phases]]`)
are silently ignored because of `#[serde(default)]` on steps.

### Phase-based grammar (`src/workflow/grammar.rs:39`)

```rust
pub struct Workflow {                   // grammar::Workflow
    pub name: String,
    pub description: Option<String>,
    pub phases: Vec<Phase>,
    pub defaults: Option<toml::Value>,
}
```

Fully implemented with:
- `FromStr` impl that calls `toml::from_str` then `validate()`
- `validate()` — checks: no empty workflow, no duplicate phases, no forward refs,
  backend scheme validity, strategy constraints
- `lint()` — warns on reserved fields
- Backend resolution: `resolve_backend_scheme()` → `BackendRef` enum
- Input resolution: `parse_input_ref()` → `InputRef` enum (PhaseRef, VarRef, Spec)

**Only consumed by `loker explain`** via `explain_workflow_source()`.

### Phase-based executor (`src/phase_runner.rs:194`)

`PhaseRunner::run(cfg: &PhaseConfig, inputs: PhaseInputs, attempt: u32) -> Result<PhaseOutcome>`

- Accepts pre-built `PhaseConfig` (strategy, aggregator, verify, artefact, prompt template, backends)
- Accepts `PhaseInputs` (resolved `Arc<dyn Backend>` vec, `Prompt`, `PhaseContext`)
- Handles strategy dispatch, aggregation, verify hooks, marker writing, manifest appending
- **Only invoked from `ResumeRunner`** in `src/resume.rs:191`

### Template rendering

Template variables like `{{ spec }}`, `{{ phase.X.output }}` are mentioned in the grammar
but template rendering is not yet implemented — will need a `TemplateEngine` or similar.

### Run directory (`RunDir`)

`RunDir::create(&cwd, name)` creates `runs/<wf>-<ts>-<id>/` with manifest. The step-based
runner writes results as markdown files; the phase runner writes to
`attempts/<phase>/<n>/<output>`.

## Baseline Score: **4/10**

The phase-based infrastructure (parser + executor) is solid with good test coverage, but
the critical glue is completely missing:

- No phase detection in `run_workflow()` (hardcoded to step-based)
- No `grammar::Workflow` → `PhaseConfig` builder
- No template rendering engine for `{{ phase.X.output }}` / `{{ spec }}` / `{{ var.X }}`
- No backend resolution from `BackendRef` to `Arc<dyn Backend>` in the `loker run` path
- `--resume` works only for previously-run phases (via `ResumeRunner`)

Score would be 7+ once the wiring is done.

## Approaches

### Approach A: Detect-and-dispatch inside `run_workflow()` (Recommended)

Modify `run_workflow()` in `src/main.rs` to detect phase vs step grammar and dispatch
to the appropriate runner.

**How it works:**
1. `load_workflow_from_source()` becomes aware of the content (currently it only gets the
   source path, then reads+parses internally). Refactor to return the raw text + source.
2. In `run_workflow()`, try `grammar::Workflow::from_str()` first on the raw text.
3. If it parses as a phase-based workflow, build `Vec<PhaseConfig>` and run phases
   sequentially via `PhaseRunner`, resolving backends via `create_backend()`.
4. If it fails with a grammar error (and has `[[steps]]` or no `[[phases]]`), fall
   through to the step-based path.

**Pros:**
- Minimal structural change — one decision point in the existing dispatch
- Both runner paths remain independent
- Step-based workflows untouched
- Naturally handles `--spec`, `--var`, `--rerun` (already in `run_workflow`)

**Cons:**
- Need a `build_phase_config(&grammar::Phase, inputs, ...)` builder function
- Template rendering is new work
- Need to wire `--resume` for phase-based workflows separately

**Effort:** L (builder + template engine + backend resolution + resume)
**Risk:** Medium (template rendering is non-trivial, `--resume` integration complex)

### Approach B: CLI-level router with separate `run_phase_workflow()`

Detect the grammar type at the `Commands::Run` handler and dispatch to either
`run_workflow()` or a new `run_phase_workflow()`.

**Pros:**
- Cleaner separation — two independent functions
- No shared state between runners

**Cons:**
- Duplicates CLI argument handling (spec/var/rerun parsing)
- More refactoring than Approach A
- Harder to maintain parity between the two paths

**Effort:** L (nearly identical to A but with more refactoring)
**Risk:** Medium

### Approach C: Convert phases to steps (grammar→step bridge)

Make `grammar::Workflow` convertible to step-based `Workflow` by representing each
phase as a step that shells out to `loker run-phase` or embeds phase logic.

**Pros:**
- Reuses all of `WorkflowRunner` — no new executor code
- `--resume` and `--rerun` work automatically

**Cons:**
- Forces phase semantics (strategies, aggregators, verify hooks) into the step model
- Loses the rich phase abstraction
- Would need a `loker run-phase` subcommand or an internal phase-injector
- Leaky abstraction — defeats the purpose of having a phase-based grammar

**Effort:** M (simpler wiring, but wrong abstraction)
**Risk:** Low (engineering risk) / High (design risk — wrong approach)

## Chosen Approach

**Approach A: Detect-and-dispatch inside `run_workflow()`**

Reasoning: It makes the smallest possible change to the existing CLI dispatch while
keeping both runner paths independent. The phase-based infrastructure already exists
with test coverage — we just need the glue. Step-based workflows are completely
unaffected. This is the approach implied by the issue's scope and the existing
comment at `src/main.rs:1458`.
