# CLO-325 Discovery Report: Resume Round-Trip Integration Test

## Problem Framing

**WHO is affected:** Loker users and developers relying on the `loker resume` feature to recover interrupted runs. The original CLO-310 implementation shipped guard clauses and binary-level validation tests but the round-trip integration test was descoped because the integration between `loker run` (step-based runner) and `loker resume` (phase-based runner) was not yet complete.

**WHAT the current behaviour vs what we want:** Currently, `loker resume` has unit tests for the planner, binary-level guard clause tests (`test_resume_run_not_found`, `test_resume_fully_complete_exit_zero`, `test_resume_no_resumable_state`, etc.), and planner logic tests. But there is no end-to-end test that: (1) creates real phase markers via execution, (2) interrupts mid-phase, (3) resumes, and (4) validates sentinel mtime invariance (no duplicate work). Without this, regressions in the pause→resume→continue path can go undetected.

**WHY now:** CLO-301 wired the PhaseRunner into the workflow execution engine, CLO-295 established the phase marker protocol, and CLO-310 established the resume surface. The phase-based workflow path in `run_workflow` (main.rs:1414+) now dispatches to `PhaseRunner` when `[[phases]]` sections are detected, producing proper phase markers. The infrastructure is finally in place for a meaningful round-trip test.

### Baseline score: 8/10

The resume infrastructure is well-designed and tested at the unit and binary-guard levels. The missing piece is the round-trip integration that exercises the full pause→resume→continue→verify path. No rewrite is needed — only an additional integration test.

### Key insight for testability

The `PhaseRunner` with `MockBackend` (from `tests/phase_runner_integration.rs`) already produces real markers and manifest entries. This means a round-trip test can:
1. Run PhaseRunner for phase 1 (completes normally, producing `.completed` marker)
2. Run PhaseRunner for phase 2, abort mid-flight — markers dir will have `phase2.started.0`
3. Use ResumeRunner programmatically to resume from this state
4. Assert phase 1 is skipped (sentinel mtime unchanged) and phase 2 completes

No subprocess management, mock backend server, or real API keys needed. The test runs entirely in-process with tokio.

## Approaches

### Approach A: Pure Rust in-process round-trip test (recommended)

Use the existing `MockBackend` and `PhaseRunner` infrastructure to create real phase markers in a temp directory, then resume via `ResumeRunner`. No subprocesses required.

**One-line summary:** Test the pause→resume cycle entirely in-process using mock backends and the existing planner/runner APIs.

**Pros:**
- No subprocess management, no timing-dependent SIGTERM delivery
- Reuses existing test infrastructure (`MockBackend`, tempdir)
- Fast execution (< 1s per test case)
- Deterministic — no flakiness from OS signal delivery timing

**Cons:**
- Doesn't test the binary CLI entry point (`loker resume`)
- Can't verify the RunLock or heartbeat path end-to-end
- Must simulate mid-phase interruption (not a real SIGTERM)

**Effort:** S (few hundred lines of test code)
**Risk:** Low

### Approach B: Binary-level subprocess round-trip test

Spawn `loker run` as a subprocess with a phase-based workflow, send SIGTERM mid-phase, then spawn `loker resume`.

**One-line summary:** Full end-to-end test using `loker run` and `loker resume` as subprocesses with a mock HTTP backend.

**Pros:**
- Tests the full binary path (CLI args, RunLock, heartbeat, state loading)
- Verifies SIGTERM handling and process-level robustness
- Closest to real-world usage

**Cons:**
- Requires a long-running mock backend server (subprocess or fixture)
- Timing-dependent — SIGTERM must arrive mid-phase
- Slower (subprocess startup + mock backend + sleep/wait)
- Flaky on CI runners with variable scheduling

**Effort:** L (mock backend server + subprocess orchestration + timing logic)
**Risk:** Medium (timing-dependent flakiness)

### Approach C: Hybrid fixture-backed round-trip test

Write a small fixture binary that creates phase markers via the `MarkerWriter` API directly, then use `ResumeRunner` programmatically to resume.

**One-line summary:** Use a fixture binary for marker creation (subprocess level) and programmatic `ResumeRunner` for the resume (Rust level).

**Pros:**
- Verifies that real on-disk markers (created by a subprocess) work with ResumeRunner
- Avoids needing a real backend or mock server
- More realistic marker content (from a real process with real PID/hostname)

**Cons:**
- Still doesn't test the binary `loker resume` path
- Fixture binary needs separate compilation
- Adds a build dependency for test fixtures

**Effort:** M (fixture binary + programmatic ResumeRunner)
**Risk:** Low

## Chosen Approach

### Approach A: Pure Rust in-process round-trip test

**Reason:** The in-process approach uses the same `PhaseRunner` and `ResumeRunner` that production code uses, creates real on-disk markers in a temp directory, and exercises the full marker→load→plan→execute cycle. It avoids subprocess timing flakiness and reuses well-tested mock infrastructure. The existing binary-level tests in `tests/resume.rs` already cover the CLI entry point guard clauses. What's missing is the marker lifecycle round-trip, which this approach nails deterministically.

Two test scenarios:

1. **`resume_roundtrip_kill_phase2`**: Phase 1 completes (`.completed` marker written), phase 2 is interrupted mid-execution (`.started.0` marker written but no `.completed`). ResumeRunner correctly skips phase 1 and resumes phase 2 at attempt 1. Sentinel mtime for phase 1 artefact is unchanged.

2. **`resume_roundtrip_phase2_failed_then_resume`**: Phase 1 completes, phase 2 starts but fails (`.failed` marker). ResumeRunner archives the failed attempt and starts a new one. Sentinel mtime invariant holds.

3. **`resume_roundtrip_all_complete`**: All phases completed. ResumeRunner skips all phases. Sentinel mtime invariant holds.
