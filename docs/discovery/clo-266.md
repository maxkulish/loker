# Discovery Report: CLO-266 — Aggregator::Concat with per-source headings

## Problem framing

Workflow authors running parallel review phases are affected: `ParallelFanOut` can collect multiple backend outputs, but downstream phases still lack a deterministic merged artefact to read. Today the code records branch metadata and an `aggregator: concat` label for schema compliance, while `aggregate_output_path` points at a placeholder and no concat logic exists. We want the simplest production aggregator: concatenate successful outputs under deterministic source headings and preserve failed targets in an errors footer. This is needed now because roadmap T-016 / PRD FR-9 blocks T-028/T-029, where the phase runner will consume aggregator output as the canonical phase artefact.

## PRD

Created task PRD at `docs/prds/clo-266-aggregator-concat.md` because the Linear issue contains Goal/Scope/ACs but no dedicated PRD artefact.

## Existing code

- `src/strategy/mod.rs` currently defines `Aggregator` as a schema-facing enum: `Concat`, `AnyFail`, `Vote`, `LLMJudge`. It has no configuration payload, trait, or `aggregate()` method.
- `StrategyOutput` serializes `Parallel` outputs as `branches`, `aggregator`, `aggregate_output_path`, and `verify`; this already validates against `docs/schemas/phase_result_parallel.schema.json`.
- `src/strategy/parallel_fanout.rs` stores only attempt metadata in `StrategyOutput`. Successful branch text (`QueryOutput.stdout`) and backend errors are not retained in the public output, so concat needs a separate input type or an extension to captured branch results.
- `ParallelFanOut` already records attempts in arrival order by pushing as futures complete. That order is the right source of truth for concat section order.
- `src/family.rs` exists and provides `family_of(&backend_id).to_string()`, yielding schema-compatible family labels such as `anthropic`, `openai`, `local`, and `other`.
- `tests/strategy_parallel_fanout.rs` validates `Aggregator::Concat` as a label through the parallel phase result schema but does not test any aggregation output.
- `Cargo.toml` does not currently include `insta`, so the snapshot acceptance criterion requires adding it as a dev-dependency.

## Baseline score

**7/10** — The schema label, parallel result shape, branch ordering, and family lookup are already in place. The missing pieces are localized: a real aggregator API, concat input/result types that carry stdout/errors, and snapshot tests. No broad rewrite is needed, but the existing `Aggregator` enum cannot simply grow a payload without considering serialization compatibility for `StrategyOutput`.

## Approaches

### Approach A — Add pure aggregator module and keep strategy schema label stable

Add `src/aggregator.rs` with a pure `Aggregator` config enum or `ConcatAggregator` type plus `AggregateInput/BranchOutcome` structs. Keep `strategy::Aggregator` (or a renamed/re-exported label) serializing exactly as today, and have concat return `{ text, metadata }` for the phase runner to write later.

Pros:
- Minimal risk to `ParallelFanOut` and existing schema tests.
- Easy to unit/snapshot test without invoking backends.
- Gives T-028/T-029 a clean seam for phase-runner composition.

Cons:
- Temporarily leaves two concepts named aggregator unless carefully re-exported/documented.
- Requires small adapter code later to feed real `ParallelFanOut` branch outputs into the aggregator.

Effort: M  
Risk: low

### Approach B — Expand `strategy::Aggregator` into `Concat { heading_template }` and aggregate inside `ParallelFanOut`

Change the existing strategy enum to include concat configuration and have `ParallelFanOut::execute` retain successful `QueryOutput.stdout` / errors long enough to produce the aggregate artefact string.

Pros:
- One public enum for label and behavior.
- Closest to the Linear wording: `Aggregator::Concat { heading_template: String }`.
- May reduce adapter work when the phase runner arrives.

Cons:
- Larger churn in strategy serialization because schema expects string labels.
- Mixes strategy execution with aggregation, making later LLMJudge/Vote more awkward.
- Harder to preserve current tests that treat aggregator as a simple copyable label.

Effort: M/L  
Risk: medium

### Approach C — Implement concat as a method on `StrategyOutput`

Add a method that derives a string from `StrategyOutput.attempts`, using attempt metadata only and leaving output content to be loaded from `output_path` by the caller.

Pros:
- Very small API addition.
- Avoids new input/result types.
- Aligns with future manifest-driven artefact loading.

Cons:
- Cannot satisfy snapshot tests without real branch text fixtures or filesystem reads.
- Blurs `StrategyOutput` (metadata) with artefact loading/aggregation behavior.
- Failed error reasons are not currently stored in `Attempt`, only `FinishReason::Error`.

Effort: S/M  
Risk: medium

## Chosen approach

**Approach A — Add pure aggregator module and keep strategy schema label stable.**

This satisfies FR-9 and the snapshot-heavy acceptance criteria with low risk: concat can be specified and tested as a deterministic pure function while leaving the existing D2 `phase_result_parallel` serialization untouched. The phase runner can later wire `ParallelFanOut` branch stdout/errors into this module and write the returned string to `aggregate_output_path`.
