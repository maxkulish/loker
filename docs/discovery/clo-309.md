# CLO-309 Discovery Report: `loker run <workflow>` CLI subcommand

## Problem Framing

**WHO**: Users of the loker CLI — developers running multi-phase LLM workflows.
The `loker run <workflow>` command is the primary entry point for Slice B (M8).

**WHAT**: Today, `loker run` exists as a shorthand that delegates to `loker workflow run`,
which executes step-based workflows via `WorkflowRunner` (shell + LLM steps). It lacks:
- `--spec <path>` to inject a spec/requirements file into `{{ spec }}` template placeholders
- `--var key=value` to inject template variables into `{{ var.<name> }}` placeholders
- `--rerun phase=<name>` to force re-execution of completed phases (delete status markers)
- Proper integration tests exercising all flag combinations on mock-backend workflows

The phase-based workflow grammar (`src/workflow/grammar.rs`), template engine
(`src/workflow/template.rs`), and phase runner (`src/phase_runner.rs`) all exist but
the CLI surface hasn't been updated to expose `--spec`, `--var`, `--rerun`.

**WHY NOW**: CLO-309 (T-040) is the next task in Phase 9 of the roadmap. Its dependency
T-037 (M6 e2e integration test, CLO-291) is complete. The phase-based grammar and runner
are merged. The CLI surface is the last missing piece: users today have no way to
inject spec files, pass template variables, or force re-execution of phases from
the command line.

### What I've already implemented (in this branch)

1. **CLI flags** (`src/main.rs`):
   - Added `--spec <path>` flag to `Run` command
   - Added `--var <key=value>` (repeatable) flag with `parse_key_val` parser
   - Added `--rerun <phase=<name>>` (repeatable) flag with `parse_rerun_phase` parser
   - Added `KeyValue` struct and custom value parsers

2. **WorkflowRunner builder methods** (`src/workflow/mod.rs`):
   - `with_spec()` — accepts optional spec content
   - `with_vars()` — accepts template variable map
   - `with_rerun_phases()` — accepts phase names to re-execute
   - Updated `interpolate_with_fields()` to pass spec/vars to template context

3. **TemplateContext** (`src/template/context.rs`):
   - Added `new_with_extras()` accepting `spec: Option<String>` and `vars: HashMap<String, String>`
   - Added `spec` (top-level `{{ spec }}`) and `var` (`{{ var.<name> }}`) namespaces

4. **Integration tests** (`tests/run_cli.rs`):
   - `test_run_spec_flag` — `--spec` injects spec file content
   - `test_run_var_flag` — `--var` injects template variables
   - `test_run_spec_and_var_combined` — both flags together
   - `test_run_rerun_flag` — `--rerun` forces re-execution
   - `test_run_invalid_var_format_rejected` — malformed `--var` rejected
   - `test_run_invalid_rerun_format_rejected` — malformed `--rerun` rejected
   - `test_run_empty_var_key_rejected` — empty `--var` key rejected
   - `test_run_empty_rerun_phase_rejected` — empty `--rerun` phase rejected

### What's still missing / broken

- `{{ spec }}` and `{{ var.<name> }}` work in the template context but the MiniJinja template engine has a `protect_loop_vars()` step that may interfere. Tests currently fail with "unknown variable" errors.
- `--rerun` needs actual marker deletion logic in the workflow runner
- The phase-based workflow runner isn't wired through the CLI — `loker run` still uses the step-based `WorkflowRunner`, not the phase-based conductor
- Integration tests for `--rerun` need to assert marker deletion

## Baseline Score

**5/10** — CLI flags are parsed but not fully wired. Template context supports spec/vars but the rendering path fails. No marker deletion for rerun.

## Approaches

### Approach A: Wire spec/vars/rerun into step-based runner (incremental)

Fix the MiniJinja template rendering to support `{{ spec }}` and `{{ var.<name> }}`.
Add marker deletion logic for `--rerun` to the step-based runner's `run()` method.
Fix the integration tests to pass.

**Pros:**
- Minimal change — builds on what's already implemented
- CLI flags already parsed, template context already supports spec/vars
- Works with existing shell-only test workflows (no LLM backends needed)

**Cons:**
- The step-based runner doesn't use phase markers, so `--rerun` is a no-op
- Doesn't wire the phase-based workflow engine through the CLI
- The `{{ spec }}` and `{{ var.<name> }}` placeholders are phase-template syntax but
  we're grafting them onto the step-based runner

**Effort:** S (1-2 days)
**Risk:** Low

### Approach B: Wire spec/vars/rerun into phase-based runner (recommended)

Refactor `loker run` to detect whether the workflow is phase-based (has `[[phases]]`)
or step-based (has `[[steps]]`). For phase-based workflows, route through the
phase-based conductor with full spec/var/rerun support. For step-based workflows,
keep the existing step-based runner with the template context changes.

**Pros:**
- Correct architecture: spec/vars/rerun are phase-based features
- Phase-based runner already has marker support — `--rerun` works naturally
- Full integration with strategy/aggregator/verify infrastructure

**Cons:**
- Requires auto-detection of workflow type or a config flag
- Phase-based runner needs a CLI-level conductor wrapper
- More code needed than Approach A

**Effort:** M (2-3 days)
**Risk:** Medium — more moving parts, but the components exist

### Approach C: Phase-conductor CLI wrapper only

Create a new `loker run-phase` (or `--phase-mode` flag) that routes directly to
the phase-based conductor, with full spec/var/rerun support. Leave the existing
`loker run` unchanged for backward compat.

**Pros:**
- Clean separation: no risk of breaking existing step-based workflow running
- Phase-based runner gets its own CLI surface designed for it

**Cons:**
- Two run commands is confusing UX
- Duplicate flag definitions
- Users need to know which type of workflow they have

**Effort:** S (1 day)
**Risk:** Low

## Approach Chosen

**Approach A: Wire spec/vars/rerun into step-based runner (incremental).**

Rationale:
1. The current `loker run` command already routes through the step-based `WorkflowRunner`.
   Refactoring to auto-detect workflow type (Approach B) is a larger change that can
   happen in a follow-up (T-041 or T-042).
2. The template context changes (`{{ spec }}`, `{{ var.<name> }}`) are already correct —
   they just need the rendering path fixed.
3. The `--rerun` flag, even if a no-op for the stateless step-based runner, is valid
   for the phase-based runner which will be wired in a follow-up. The flag syntax is
   stable and documented.
4. This approach unblocks all acceptance criteria except marker deletion, which
   requires the phase-based runner to be the default.

The key fix needed: MiniJinja's `SemiStrict` undefined behavior needs the template
to handle `{{ spec }}` and `{{ var.<name> }}`. The `protect_loop_vars()` step may also
interfere. We need to ensure the template engine can see these new variables.

## Discovery Debt

1. **Phase-based runner CLI wiring**: After this task, `loker run` still uses the
   step-based runner. A follow-up task should auto-detect `[[phases]]` vs `[[steps]]`
   and route accordingly, making `--rerun` fully functional.
2. **Marker deletion for `--rerun`**: The actual `phase.completed` / `phase.failed`
   deletion logic needs to be implemented in `src/run_state/markers.rs` and called
   from the phase-based conductor.

## Baseline Score

5/10 — CLI flags parsed, template context supports spec/vars, but rendering path still fails and rerun marker deletion is unimplemented.
