# CLO-310 Discovery Report: `loker resume <run_id>` CLI subcommand

## Problem Framing

**WHO**: Developers using the loker CLI to run multi-phase LLM workflows. Users who experience process interruptions (OOM, Ctrl-C, cloud preemption) mid-run and need to pick up where they left off without restarting from scratch, wasting API tokens and wall-clock time.

**WHAT**: Today, `loker resume <run_id>` exists as a hidden CLI subcommand (`#[command(hide = true)]`) with a fully implemented `ResumePlanner` + `ResumeRunner` stack. The planner reads markers + manifest to decide Skip/Resume/RunFresh per phase. The Runner executes the plan by driving `PhaseRunner::run()` for non-Skip phases. However, the command is still hidden, has minimal help text, lacks proper error messages for edge cases (run not found, fully complete, no resumable state), and has no pause/resume round-trip integration test. The ACs demand a first-class CLI surface, clear error messages, and a verified round-trip test.

**WHY NOW**: T-041 is the next task in Phase 9 of the roadmap. Dependencies T-031 (CLO-295 — resume planner), CLO-301 (ResumeRunner wiring), and T-040 (CLO-309 — run CLI flags) are all complete. The resume infrastructure exists and works end-to-end; what remains is CLI polish, help-text clarity, error handling, and the integration test that validates the full pause/resume cycle.

### What's already implemented

1. **ResumePlanner** — reads `RunState` phase_status and returns Skip/Resume/RunFresh per phase
2. **ResumeRunner** — executes the plan by driving `PhaseRunner::run()` for non-Skip phases
3. **RunLock** — advisory file lock via `fs2::FileExt` (flock/LockFileEx)
4. **Stale tmp sweep** — moves orphaned `*.tmp` files before planning
5. **Heartbeat TTL recovery** — reads `heartbeat.json` for exact TTL used by original run
6. **Workflow name persistence** — `manifest.json` stores `workflow_name` for locating workflow definition
7. **`to_phase_configs()`** — step-based `Workflow` can emit `Vec<PhaseConfig>` for `PhaseRunner`
8. **Test contract** — 5 planner scenarios in `tests/resume.rs`

### What's still missing / needs changing

1. **Hidden → first-class CLI**: Remove `#[command(hide = true)]` from `Commands::Resume`, add proper help text
2. **`<run_id>` flexibility**: Accept directory name under `runs/` OR absolute path (currently path-only)
3. **Error messages**: 
   - Run not found → "Run '<id>' not found in runs/ directory or as an absolute path"
   - Fully complete → "All phases already complete. Nothing to resume." (exit 0)
   - No resumable state → "No resumable state found in <path>" 
   - Live heartbeat → "Run is still in progress at <path>"
4. **`--help` clarity**: `loker resume` and `loker run --rerun phase=X` must be clearly distinct
5. **Pause/resume round-trip integration test**: Kill mid-phase via signal, resume, assert completion with no duplicate work

## Baseline Score

**7/10** — ResumePlanner, ResumeRunner, lock, sweep, and the PhaseRunner wiring are fully implemented and unit-tested. The gaps are CLI polish, error handling, help text, and the round-trip integration test. No internal rewrites needed.

## Approaches

### Approach A: Polish hidden resume as first-class CLI (recommended)

Unhide `Commands::Resume`, add `run_id` resolution (directory name or path), add proper help text and error messages, add a `--help` comparison distinguishing resume from `run --rerun`, and write the pause/resume round-trip integration test.

**Pros:**
- Minimal code change — resume execution already works end-to-end
- All infrastructure (planner, runner, lock, sweep) is in place
- Quickest path to the ACs

**Cons:**
- Requires understanding both path and name resolution for `run_id`
- The round-trip test needs a mock workflow and signal handling

**Effort:** S (1-2 days)
**Risk:** Low — all changes are additive (unhide, err msgs, tests)

### Approach B: Refactor resume into the phase-based workflow engine

Move resume from the step-based `WorkflowRunner` to the phase-based grammar `Workflow` (grammar.rs). Route `loker resume` through the phase-based conductor for full support of phase strategies, aggregators, and verify hooks.

**Pros:**
- Correct architecture — resume is a phase-based feature
- Full integration with strategy/aggregator/verify infrastructure

**Cons:**
- Requires the phase-based conductor to have a CLI wrapper (not yet built)
- Larger change than needed for the ACs
- Phase-based grammar workflow is a different type from step-based — would need adapter

**Effort:** M (3-5 days)
**Risk:** Medium — more moving parts, phase-based conductor not yet CLI-routable

### Approach C: Minimal unhide only

Simply remove `#[command(hide = true)]` and nothing else. Leave `run_id` as a path argument, minimal help text, and no integration test.

**Pros:**
- Zero engineering effort
- The feature is already usable by power users who know the path

**Cons:**
- Fails every AC:
  - No pause/resume round-trip test
  - No clear error messages
  - `resume` vs `run --rerun` not distinguished in `--help`
- `run_id` as plain path is poor UX

**Effort:** XS (< 1 hour)
**Risk:** Low but unacceptable — doesn't meet acceptance criteria

## Approach Chosen

**Approach A: Polish hidden resume as first-class CLI.**

Rationale:
1. The resume infrastructure is complete and working end-to-end — the planner, runner, lock, sweep, phase config derivation, and heartbeat recovery are all implemented and tested.
2. The task scope (ACs) is specifically about the CLI surface, error messages, help text, and the integration test — not about refactoring the internal architecture.
3. The existing `to_phase_configs()` adapter means the step-based `Workflow` already emits `PhaseConfig` lists correctly. No architecture change is needed.
4. The round-trip test (AC #1) is the most valuable deliverable — it validates the entire pause → marker → resume → completion flow that distinguishes T-041 from T-031/CLO-301.
