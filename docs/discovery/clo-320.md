# Discovery Report: CLO-320 — Per-gate fallback axum server for HITL approval

| Field | Value |
|-------|-------|
| Task | CLO-320 |
| Date | 2026-05-06 |
| Phase | discovery |
| Branch | `feat/clo-320-fallback` |

## Problem Framing

**Who is affected:** Operators using `HumanVerifier` gates in loker workflows. Today, when a gate triggers, the operator must manually create a `responses/<phase>.json` file with the correct schema. There is no interactive path — the workflow simply fails with "waiting for human review" and the operator has to understand the filesystem contract, craft JSON by hand, and place it in the right directory.

**Current behaviour:** `HumanVerifier::verify_with_report` writes `pending/<phase>.json` and returns `VerifyResult::Fail` when no response file exists. The loker process exits. The operator must manually author `responses/<phase>.json` and run `loker resume`.

**Desired behaviour:** When a `HumanVerifier` gate triggers and no response exists, a minimal one-shot axum HTTP server spawns on a free localhost port, prints a clickable URL to stdout, and blocks until the human approves or rejects via the browser. The server writes the response file through the advisory lock (T-050), shuts down, and the blocked `HumanVerifier` returns the appropriate `VerifyResult`, allowing the phase runner to continue. Timeout policies (low=1h auto-approve, medium=24h auto-fail, high=infinite block) still apply.

**Why now:** T-048 (HumanVerifier scaffold) and T-049 (severity ladder) are implemented. T-050 (advisory lock) is complete. The per-gate server is the last M10 dependency before M11 UI daemon work can start. Without it, operators have no usable HITL path short of hand-editing JSON.

## Existing Code

### HumanVerifier scaffold (T-048 / CLO-317)
- `src/strategy/verify/human_verifier.rs`
  - `HumanVerifierConfig` carries `run_dir`, `run_id`, `phase`, `severity`, `timeout_policy`, `decision_options`.
  - `verify_with_report` writes `pending/<phase>.json`, reads `responses/<phase>.json`, and maps decisions to `VerifyResult`.
  - `HumanResponse` schema: `schema_version`, `phase`, `claimed_by`, `decided_at`, `decision`, `global_comment`, `inline_comments_path`.
  - Timeout logic is deterministic: fake-clock tests cover low/medium/high severity paths.
  - On successful parse, the response file is atomically renamed to `responses/<phase>.json.handled.<timestamp>`.

### Severity ladder (T-049 / CLO-318)
- Same file (`human_verifier.rs`) — `HumanTimeoutPolicy` with `rule_for(severity)`.
  - Low: 1h timeout → `AutoApprove`
  - Medium: 24h timeout → `AutoFail`
  - High: no timeout → `Block`
  - `HumanTimeoutOutcome` tracks whether the gate resolved via explicit decision, auto-approve, auto-fail, or is still blocking.

### Advisory lock (T-050 / CLO-319)
- `src/run_state/phase_lock.rs`
  - `PhaseLock::acquire(run_dir, phase, run_id, ttl_seconds)` returns `Result<PhaseLock, PhaseLockError>`.
  - `PhaseLockError::LockInUse` surfaces holder PID, host, and timestamp.
  - `Drop` truncates the lock file to 0 bytes, releasing the OS advisory lock.
  - Used by `ResumeRunner::run_phase` before invoking `PhaseRunner::run`.
  - Unit tests cover concurrent acquire, stale reclaim, PID-liveness check, and inspect-without-holding.

### Phase runner integration
- `src/phase_runner.rs`
  - `run_phase` calls `HumanVerifier::verify_with_report` when `cfg.verify == VerifyHookName::HumanVerifier(...)`.
  - On `VerifyResult::Fail`, it records a terminal failure marker with HITL context (severity, timeout_at, timeout_action, timeout_outcome).
  - On `VerifyResult::Pass`, it records a completed marker with the same HITL context.
  - Trace events include `HitlTraceMetadata` via `hitl_trace_metadata()`.

### Run directory layout
- `runs/<id>/`
  - `pending/<phase>.json` — gate context and artefact preview
  - `responses/<phase>.json` — human decision payload
  - `locks/<phase>.lock` — advisory lock file + JSON body
  - `markers/` — phase status markers

### Dependencies
- `Cargo.toml` already has `tokio`, `serde_json`, `chrono`, `reqwest`.
- **No axum, tower, or hyper** — these must be added for the server.
- `reqwest` (dev-friendly) can be used in integration tests to exercise the one-shot server.

### Baseline score: 8 / 10

The codebase has mature primitives for every sub-problem: the pending/response JSON contract is frozen, the advisory lock is tested and ready, the phase runner already records HITL metadata in traces and markers. The only gap is the HTTP surface itself. No rewrite of run-state layout, marker schema, or verify hook API is needed. The score is 8 (not 10) because integrating an axum server into an async verify hook requires careful tokio task lifecycle management to avoid leaking the server on Ctrl-C or unexpected drop.

## Approaches Identified

### Approach A — In-process blocking server inside HumanVerifier
When `HumanVerifier` detects a missing response, it spawns a one-shot axum server on `127.0.0.1:0` (free port), prints the URL, and blocks on a `tokio::sync::oneshot::channel` (or timeout select). The server handles `GET /`, `POST /approve`, `POST /reject`. On receiving a POST, it acquires `PhaseLock`, atomically writes the response file, sends the decision back through the channel, and shuts down. The blocked `HumanVerifier` reads the response and returns the mapped `VerifyResult`.

- **Pros**
  - Seamless user experience: `loker run` → URL printed → click → run continues.
  - No detached processes or background threads to manage.
  - Natural fit with the existing `VerifyHook` async contract.
  - Timeout policies from T-049 apply automatically via `tokio::time::timeout`.
- **Cons**
  - The `loker` process stays alive during the gate; Ctrl-C loses the server.
  - Requires axum + tower dependencies in the main binary.
  - Server lifecycle must be carefully managed to avoid leaking tasks on drop.
- **Effort:** M
- **Risk:** low

### Approach B — Detached background child process
`HumanVerifier` spawns a new `loker` child process (e.g. `loker gate-serve --run-id X --phase Y`) when the gate triggers. The child runs the server independently. The parent returns `Fail`, the run stops. The child writes the response file when a human hits the endpoint. On the next `loker resume`, the response is found.

- **Pros**
  - Parent process exits immediately; user can resume later.
  - Server survives parent crash (separate OS process).
  - Could be reused for "daemon-lite" mode without full M11.
- **Cons**
  - Requires a new CLI subcommand and extra binary entry point (or hidden flag).
  - Process management complexity: zombie children, signal handling, port discovery.
  - Not a "clickable URL resumes the run" experience — user must still run `loker resume` after clicking.
  - Overkill for a one-shot gate; contradicts the "no daemon" scope.
- **Effort:** M
- **Risk:** medium

### Approach C — Polling loop with external server
`HumanVerifier` returns `Fail` immediately as today, but also spawns a background tokio task with the axum server. The task prints the URL and writes the response file when a POST arrives. The run stops. On `loker resume`, the verifier polls the response file as usual.

- **Pros**
  - Minimal change to `HumanVerifier` blocking semantics.
  - Background task is easy to spawn with `tokio::spawn`.
- **Cons**
  - Tokio tasks are dropped when the runtime shuts down. The server would die with the process, making it useless unless the runtime stays alive.
  - To survive process exit, the task would need a separate thread with its own runtime — which is essentially Approach B without the clean process isolation.
  - User still must `loker resume` after clicking the URL.
- **Effort:** S
- **Risk:** high (task survival is unreliable)

## Approach Chosen

**Approach A** (in-process blocking server inside HumanVerifier).

Reason: The acceptance criteria explicitly state "approving / rejecting it resolves the gate and resumes the run." This implies synchronous resolution within the same process. The operator runs `loker run`, the gate blocks with a printed URL, and the run continues automatically after human interaction. No `loker resume` is needed for the happy path. The timeout policies from T-049 handle the case where the human never interacts. The one-shot server is spawned, serves exactly one decision, and exits — matching the "one-shot, no daemon" requirement from the roadmap.

## Discovery Debt

- [ ] Server shutdown on Ctrl-C: we should ensure the server task is aborted when the parent tokio runtime shuts down (e.g. via `tokio::select!` with a cancellation token). This is a graceful-degradation detail, not a blocker.
- [ ] HTML vs JSON response for `GET /`: the acceptance criteria don't require a styled UI (that's M11). A plain JSON response or minimal HTML form is sufficient for the fallback. We will ship a minimal HTML form with two buttons so the URL is truly "clickable" without requiring curl.
- [ ] Port binding race: binding to `127.0.0.1:0` and reading the actual port is safe, but we must ensure the port is communicated to stdout before the server starts accepting (already guaranteed by `TcpListener::local_addr`).
