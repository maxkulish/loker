# Discovery Report — CLO-316

## Problem framing

**WHO:** Existing `lok` users and maintainers evaluating upgrades to `loker` in M9 are the primary audience; they need a clear, non-code migration path for commands and workflow concepts.
**HOW today:** There is no dedicated migration guide. The project has inherited command compatibility notes and a partially related note in `docs/old-readme.md`, but there is no single authoritative document mapping each legacy knob and command to current loker equivalents.
**WHAT we want:** A concrete, validated migration doc (`docs/migration-from-lok.md`) that translates concepts and commands, calls out breakages and non-porting behavior, and documents deprecation expectations for compatibility paths.
**WHY now:** `CLO-314` (README rewrite) is complete, and this task is the next M9 dependency. Without this guide, users cannot self-serve migration despite the command/API parity work landing in code.

## Existing code

The relevant implementation and docs surface for migration mapping currently exists in:

- `src/main.rs` command definition: current loker CLI includes legacy-facing commands (`ask`, `hunt`, `audit`, `diff`) and expanded modern workflow tooling (`run`, `resume`, `workflow run/list/validate`, `explain`, `trace`, `report`, etc.).
- `README.md` and `docs/old-readme.md` currently document a mix of command surface and historical context, but only partially cover the mapping goal:
  - `README.md` states that the lok surface is preserved, and lists both inherited and new commands.
  - `docs/old-readme.md` retains fork-history details and compatibility notes but is now archival.
- `docs/plans/001-implementation-roadmap.md` and `docs/prd/2026-04-25-loker.md` already define M9 intent, explicitly requiring a lok-to-loker migration guide and deprecation-window language.
- `docs/status/clo-316-workflow.yaml` already indicates no existing PRD for this issue and no design/workflow artifacts yet.

Current baseline is therefore incomplete for task scope because the required migration mapping and verified command examples are not in one canonical place.

## Baseline score

**4/10.** The repo already preserves many legacy behaviors and has the primitives to support migration, but it lacks a dedicated, authoritative, and verified translation artifact that addresses all requested dimensions (concept map, command table, breakage notes, timeline/deprecation expectations).

## Approaches considered

### Approach A — Standalone migration document first, then link from README

- **Summary:** Add `docs/migration-from-lok.md` with complete side-by-side mapping and breaking-change notes.
- **Pros:**
  - Directly satisfies issue scope and acceptance criteria.
  - Isolates migration risk and review to docs changes.
  - Easy to keep in sync as a single source of truth.
- **Cons:**
  - Adds one extra doc touchpoint users must discover.
  - Requires disciplined linking from README.
- **Effort:** S
- **Risk:** low

### Approach B — Expand README with a dedicated "Migrating from lok" section

- **Summary:** Fold all migration content into a long README section.
- **Pros:**
  - No new docs entry to discover.
  - High visibility on the project front page.
- **Cons:**
  - README becomes crowded and hard to keep updated.
  - Command/context tables are hard to maintain in one flat doc.
- **Effort:** M
- **Risk:** medium

### Approach C — Add generated script-based migration aids

- **Summary:** Build validation scripts/command wrappers that output recommendations from `lok` workflows to loker equivalents.
- **Pros:**
  - Potentially best for ongoing migration consistency.
  - Provides automation beyond documentation.
- **Cons:**
  - Scope exceeds current task (would be implementation work).
  - Requires test coverage and behavior guarantees not requested in this phase.
- **Effort:** L
- **Risk:** high

## Approach chosen

**Approach A — Standalone migration document first, then link from README.**

This is the fastest, lowest-risk path to meet the explicit acceptance criteria with minimal code churn, while giving users one canonical migration artifact that can be expanded later if needed.
