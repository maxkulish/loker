# Discovery Report: CLO-267 — Implement Aggregator::AnyFail (first failure wins)

| Field | Value |
|-------|-------|
| Task | CLO-267 |
| Date | 2026-04-28 |
| Phase | discovery |
| Branch | `feat/clo-267-anyfail` |

## Problem Framing

**Who is affected:** Workflow authors using `Strategy::ParallelFanOut` who need pessimistic consensus across multiple backend reviews. Example: a design-doc-tdd workflow where three different-family models review an implementation plan; if *any* reviewer rejects it, the phase must fail and block the pipeline.

**Current behaviour:** `ParallelFanOut` dispatches to N backends and records per-branch `Attempt` records, but performs zero aggregation logic. The `aggregator` field is purely a schema label (`"concat"`, `"any_fail"`, `"vote"`, `"llm_judge"`). Every branch gets `verify: { "status": "skipped", "hook": null }`. There is no mechanism to evaluate branch-level verdicts, short-circuit on disagreement, or surface a structured failure carrying the offending branch.

**Desired behaviour:** `Aggregator::AnyFail` reads each branch's JSON verdict (locked schema: `{ "pass": bool }`), evaluates results in arrival order, and immediately short-circuits the phase on the first `pass: false` or backend error. Success is only surfaced when *every* target reports `pass: true`. Backend errors are treated as failures, not silently demoted to "missing vote."

**Why now:** This is T-018 on the Phase 3 (aggregator vocabulary) critical path. It blocks T-029 (phase runner), which composes strategy + aggregator + verify hook. Shipping AnyFail now establishes the aggregation error pattern (`StrategyError` carrying shaped `StrategyOutput`) that Concat (CLO-266) and future LLMJudge / Vote aggregators will reuse.

## Existing Code

### `src/strategy/mod.rs`
- `Aggregator` enum stub already contains `AnyFail` (added during CLO-259).
- `StrategyOutput` serialization: when `strategy == StrategyKind::Parallel`, emits `branches`, `aggregator`, `aggregate_output_path`, and `verify`. The shape is correct; only the *values* need updating.
- `StrategyError` variants: `BackendNotFound`, `NoBackends`, `PromptRender`, `Backend`, `Exhausted`, `FloorViolation`. No aggregator-specific variant yet.
- `PhaseError` re-exported from `crate::family`; currently only `FamilyOverlap`.

### `src/strategy/parallel_fanout.rs`
- `ParallelFanOut::execute` uses `FuturesUnordered` to collect per-target `QueryOutput` in arrival order.
- Short-circuits when `successes >= min_responses` (for `Concat` / `Vote` floor semantics).
- Attempts are pushed into a `Vec` in completion order.
- No attempt output is read or parsed — `output_path` is merely a string.

### `src/family.rs`
- `PhaseError` needs a new variant `AggregatorContract` to satisfy the CLO-267 AC: "schema mismatch raises structured PhaseError::AggregatorContract rather than panic."

### `docs/schemas/phase_result_parallel.schema.json`
- Schema accepts `"any_fail"` in the `aggregator` enum. `verify.status` accepts `"pass"`, `"fail"`, `"skipped"`.
- Baseline score: **7 / 10**. The enum stubs, parallel infrastructure, and schema are already in place. What is missing is 100% of the aggregation logic and one error variant.

## Approaches

### Approach A — Inline streaming evaluation (extend ParallelFanOut)

Evaluate each branch's JSON verdict as results arrive in the `FuturesUnordered` loop; short-circuit immediately on first `pass: false` or backend error.

- **Pros:**
  - Minimal code footprint (~80 lines plus tests).
  - Leverages existing completion-order semantics naturally.
  - Short-circuit means fewer wasted backend calls (matches "first failure wins" requirement literally).
  - Fits existing mock-backend test framework without new abstractions.
- **Cons:**
  - Aggregation logic lives inside the strategy, making isolated unit tests slightly harder.
  - Future `LLMJudge` aggregator (needs backend calls during aggregation) will force a refactor; but T-017 is already scheduled after T-015, so this refactor is guaranteed to happen anyway.
- **Effort:** S
- **Risk:** low

### Approach B — Separate `aggregator` module with post-hoc dispatch

Extract aggregation into a new `src/aggregator/mod.rs`. `ParallelFanOut` collects all attempts, then calls `apply_aggregator(&aggregator, &attempts, &outputs)` before returning.

- **Pros:**
  - Clean separation of concerns.
  - Unit-test aggregators without spawning `FuturesUnordered`.
  - Aligns with M3's roadmap of four aggregator variants.
- **Cons:**
  - Loses streaming short-circuit for `AnyFail` (must collect and buffer all results before evaluating).
  - Introduces a new module whose interface may need redesign when LLMJudge needs backend access.
  - Over-engineering for a single enum variant when the refactor is inevitable for T-017.
- **Effort:** M
- **Risk:** medium

### Approach C — Trait-based aggregator with streaming hooks

Define `trait AggregatorLogic { fn on_branch_result(&mut self, ... ) -> AggregatorControl; fn finalize(&self) -> Result<(), AggregatorError>; }`. `ParallelFanOut` holds `Box<dyn AggregatorLogic>`.

- **Pros:**
  - Most extensible; LLMJudge can hold backend references.
  - AnyFail short-circuits via `AggregatorControl::Fail`.
- **Cons:**
  - Maximum boilerplate and speculative API design before the phase runner (T-029) exists.
  - Trait object safety concerns around async / backend references.
  - Over-engineering for the immediate task.
- **Effort:** L
- **Risk:** high

## Decision

**Chosen approach: A — Inline streaming evaluation.**

Rationale: AnyFail's semantics map perfectly to the `FuturesUnordered` arrival-order loop that `ParallelFanOut` already maintains. The implementation is a small, self-contained private helper inside `parallel_fanout.rs` that parses JSON verdict text and returns a new `StrategyError::AnyFail` variant carrying the offender attempt and full `StrategyOutput`. When the LLMJudge trait is designed in T-017, this helper moves cleanly into the aggregator abstraction with no public API breakage — `StrategyError::AnyFail` will simply be emitted by a different caller.
