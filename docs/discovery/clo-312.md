# Discovery Report — CLO-312

## Problem framing

**WHO:** Loker users debugging a workflow run.
**HOW today:** They `cat runs/<run_id>/trace.jsonl` or pipe through `jq` to inspect OTel GenAI spans.
**WHAT we want:** A built-in `loker trace <run_id>` subcommand that renders each span as a single, colorized, human-readable line — no external tools needed.
**WHY now:** T-043 is scheduled for Phase 9 (M8 slice) per the implementation roadmap. The trace writer (CLO-293) is done; the missing piece is consumption.

The trigger is straightforward: every run produces a `trace.jsonl`, but the CLI offers no way to read it back.

## Existing code

### CLI entry point (`src/main.rs`)

- `clap`-derived `Commands` enum with ~20 subcommands (ask, hunt, fix, resume, report, etc.).
- `resolve_run_dir(run_id: &str)` already exists (CLO-310). It resolves bare names to `<project_root>/runs/<run_id>` by walking ancestors for `lok.toml`. Supports absolute and relative paths. This is exactly what `trace` needs.
- `colored` is already a dependency (used for green checkmarks, cyan labels, etc.).

### Trace infrastructure (`src/trace.rs`, `src/trace/writer.rs`, `src/trace/memory.rs`)

- `TraceSink` trait with 6 lifecycle methods.
- `TraceWriter` appends JSONL to `run_dir/trace.jsonl`.
- `InMemorySink` captures spans for tests.
- Schema at `docs/schemas/trace_span.schema.json` defines the full span shape.

### Run directory (`src/run_state/run_dir.rs`)

- `RunDir::trace_path()` returns the canonical `trace.jsonl` path.
- Run directories are already created and validated by `RunDir::create`.

### Test patterns

- `insta` is a dev-dependency; used for snapshot tests across the codebase (`tests/explain_cli.rs`, `src/aggregator/concat.rs`, etc.).
- `tests/trace_jsonl.rs` already tests trace emission; no reader tests exist yet.

### No existing pretty-printer

There is zero code for trace consumption today. We are building from scratch on top of a solid, well-defined format.

## Baseline score

**9/10.** The trace format is stable, schema-validated, and the CLI infrastructure (clap, colored, resolve_run_dir) is already in place. There is no legacy pretty-printer to replace. The only gap is the fixture trace.jsonl for snapshot tests.

## Approaches considered

### Approach A: Inline helper in `main.rs`

Add `Commands::Trace { run_id, json }` to the CLI enum and handle it with an inline `run_trace()` async fn in `main.rs`, similar to how `run_report()` is structured.

- **Pros:**
  - Minimal file creation; fast to implement.
  - Reuses existing `resolve_run_dir()` without needing to expose it from a module.
- **Cons:**
  - Bloats `main.rs` (already ~2500 lines).
  - Snapshot tests must live in `tests/` as integration tests, making iteration slower.
  - Pretty-printing logic is not reusable if we later want a web UI or TUI view.
- **Effort:** S
- **Risk:** low

### Approach B: Dedicated `src/commands/trace.rs` module

Create a new `src/commands/mod.rs` tree (or add to `src/lib.rs` exports) with a `TracePrinter` struct that encapsulates file reading, span parsing, and formatting. Wire a thin CLI handler in `main.rs`.

- **Pros:**
  - Clean separation; `main.rs` stays lean.
  - Unit-testable formatting logic without spawning the binary.
  - Snapshot tests can assert on the rendered string directly in the module.
  - Reusable if we later build a `loker tui` or web dashboard.
- **Cons:**
  - Slightly more boilerplate (new module, exports).
- **Effort:** S
- **Risk:** low

### Approach C: Streaming parser (memory-conscious)

Use a line-by-line `BufReader` + `serde_json` streaming parser instead of loading the whole file.

- **Pros:**
  - Handles arbitrarily large trace files with constant memory.
- **Cons:**
  - Overkill for loker traces (typical runs have 10–100 spans; even 1000 spans is < 1 MB).
  - Makes snapshot testing and multi-pass formatting harder.
- **Effort:** S
- **Risk:** low

## Approach chosen

**Approach B + C hybrid:** A dedicated `src/commands/trace.rs` module with line-by-line streaming (cheap and natural with `BufReader`). The formatter is unit-testable, and `main.rs` only dispatches.

**Reason:** The codebase already separates complex CLI logic into modules (`tasks::hunt`, `tasks::ci`, etc.). A new `commands::trace` module follows the same convention. Streaming is trivial here — `BufReader::lines()` + `serde_json::from_str` per line — so we get the memory safety of C without any real complexity cost.
