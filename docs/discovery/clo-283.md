# Discovery Report — CLO-283: Append-only manifest writer with crash-safe rewrite

## Step 1 — Problem Framing

### Who is affected
Every downstream phase in loker (T-026, T-029, T-031) that needs to load, verify, or resume artefacts produced by earlier phases. Without a canonical manifest, resumability has no trustworthy index of what exists and what is corrupt.

### Current behaviour vs desired behaviour
Today: no manifest module exists in `src/`. Phase artefacts are written ad-hoc by individual strategies; no content-addressed registry ties an artefact to its producer, schema version, or cryptographic hash.
Desired: a `Manifest` struct that mirrors `docs/schemas/manifest.schema.json`, supports `append(entry)` with crash-safe atomic rewrite, sha256 content addressing, and orphan-entry sweep on load per the D3 write protocol.

### Why now
T-002 (D2 schemas) and T-003 (D3 atomic write protocol) are both shipped on `main`. T-024 (this task) is the next sequential dependency on the critical path for M5/M6, blocking T-026, T-029, T-031. The schema, the protocol, and the fixture pipeline are all in place; implementing the writer is the only remaining blocker.

## Step 2 — Existing code

### What exists
- `src/family.rs` — defines `PhaseError` (5 variants). `ArtefactSchemaMismatch` is referenced in `docs/run-state.md` and the PRD but does **not** yet exist as a variant.
- `tests/schema_validation.rs` — T-002 harness. Validates every `*.schema.json` under `docs/schemas/` against positive/negative fixtures under `tests/fixtures/schemas/`. `manifest.schema.json` is already present and has fixtures (`empty.json`, `single_phase.json`, `multi_phase_with_hitl.json`, plus 3 negative fixtures).
- `docs/schemas/manifest.schema.json` — canonical D2 output for the manifest envelope and entry shape.
- `docs/run-state.md` — D3 documentation of the atomic file commit primitive, manifest rewrite semantics, and kill-matrix row 9 (orphan-entry sweep).
- `Cargo.toml` — already includes all needed dependencies: `serde`, `serde_json`, `sha2`, `tempfile` (dev-dep), `uuid`, `chrono`, `thiserror`, `anyhow`.

### What does NOT exist
- Any `src/manifest.rs` or `mod manifest`.
- `ArtefactSchemaMismatch` in `PhaseError`.
- Any code for sha256 helpers, directory digests, or atomic JSON file rewrite.
- Tests under `tests/manifest.rs`.

### Baseline score
**0 / 10.** There is zero existing code for the manifest writer. However, the surrounding infrastructure (schemas, fixtures, validation harness, dependency set, and write protocol spec) is mature. Implementation is a green-field module, not a refactor.

## Step 3 — Approaches

### Approach A — Full-Rewrite Atomic JSON (tmp + rename + fsync)
- **Summary**: Serialize in-memory entries to JSON, write to a `NamedTempFile` in the same directory, fsync file, rename to `manifest.json`, fsync parent dir. On load, parse, run orphan sweep, validate schema versions.
- **Pros**: Matches D3 protocol exactly; simple; `tempfile` crate handles collision-free random suffix; POSIX-atomic rename guarantees readers see old or new, never torn JSON. Low hundreds of entries means full rewrite is cheap.
- **Cons**: O(N) write cost on every append (rewrite entire file). No bounds on file size across a long run. Not suitable for eventual streaming read (but v0 does not need that).
- **Effort**: M (one module + tests + schema fixtures).
- **Risk**: Low.

### Approach B — Append-only lines with index
- **Summary**: Maintain a human-readable `.jsonl` log of entries plus a separate index file. Only append new lines; index updated via rename.
- **Pros**: O(1) append cost. Supports tail-based reading. Can recover from partial line corruption.
- **Cons**: Deviates from D3 spec which chose JSON (not JSONL) for the manifest. Requires custom parsing for both files. Adds complexity for no concrete v0 benefit (low hundreds of entries). Schema validation becomes harder (must validate each line separately then an assembled envelope).
- **Effort**: L.
- **Risk**: Medium (protocol divergence, schema tooling incompatibility).

### Approach C — Memory-only manifest with external store
- **Summary**: Build manifest in memory; persist to an embedded DB (sqlite/sled) rather than raw JSON.
- **Pros**: ACID durability, compact, queryable.
- **Deps**: Extra crate. Not in current Cargo.toml.
- **Cons**: D3 explicitly requires tmp+rename for POSIX atomicity and portability. sqlite WAL mode is not as portable for filesystem-level recovery tools. Overkill for low hundreds of entries.
- **Effort**: L.
- **Risk**: High (dep, protocol divergence, extra runtime state).

## Step 4 — Choice

**Chosen: Approach A — Full-Rewrite Atomic JSON.**

The D3 decision record already evaluated candidates (tmp+rename vs attempt-directory canonical) and picked tmp+rename for the manifest. Approach A is the natural implementation of that decision. The only concession is that each append rewrites the whole file, which is perfectly acceptable at v0 sizes.
