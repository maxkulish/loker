# Discovery: CLO-313 - `loker ls --blocked`

## Problem framing

Developers and operators running Loker workflows with HumanVerifier gates are affected today because a paused run is only visible if they already know where to inspect `runs/<id>/pending/`. The current CLI has `run`, `resume`, `explain`, and `trace`, but no read-only inventory of work waiting on a human decision. We want `loker ls --blocked` to scan the project `runs/` directory and show each unresolved HITL gate with run id, phase, severity, age, and a decision URL/path. This matters now because FR-37/T-044 is the downstream CLI surface for the HumanVerifier pending schema and the CLO-319 per-phase lock work.

## Existing code

- CLI dispatch is centralized in `src/main.rs` using clap `Commands`. `Trace` is a recent adjacent command that resolves a run directory and delegates implementation to `loker::commands::trace`.
- `src/commands/mod.rs` currently only exports `trace`, making a new `src/commands/ls_blocked.rs` module the least disruptive home for scan/format logic that tests can call directly.
- `resolve_run_dir` and `find_project_root` in `src/main.rs` establish the current convention for bare run ids: project root is found by walking for `lok.toml`, with `runs/<id>` under that root. `ls --blocked` should use the same root heuristic for its default `runs/` scan.
- `HumanVerifier` writes pending requests to `runs/<run_id>/pending/<phase>.json`; the schema is `PendingRequest` in `src/strategy/verify/human_verifier.rs` with `run_id`, `phase`, `severity`, `opened_at`, `timeout_at`, `artefact`, `context`, and `decision_options`.
- Human responses use `responses/<phase>.json` and are consumed/renamed to handled files. For this command, a matching live `responses/<phase>.json` means the pending gate is no longer blocked.
- CLO-319 added `PhaseLock` under `runs/<id>/locks/<phase>.lock`; its JSON body is useful future context but the CLO-313 acceptance criteria define blocked state primarily from pending/response files. Lock handling should therefore stay additive/optional rather than required for correctness.
- Existing tests include command-level unit/snapshot tests (`tests/trace_pretty.rs`, `tests/snapshots/...`) and HITL fixtures built with temporary run directories (`tests/phase_runner_human_verifier.rs`).

## Baseline score

**8/10.** The pending/response schemas and CLI/test patterns already exist, so no rewrite is needed. The missing piece is an additive command module plus clap wiring; the only moderate uncertainty is the exact display formatting and whether to include lock metadata now or defer it.

## Approaches

### Approach A: Additive command module scanning pending/response files

One-line summary: Implement `src/commands/ls_blocked.rs` with pure scan/render functions, wire it to `loker ls --blocked` in `src/main.rs`, and snapshot-test fixture output.

Pros:
- Minimal blast radius and mirrors the existing `trace` command pattern.
- Easy to unit/snapshot test without invoking async workflow execution.
- Directly matches acceptance criteria based on `pending/<phase>.json` and `responses/<phase>.json`.

Cons:
- Adds another command module with small filesystem-walk logic.
- Display format must be chosen and then stabilized by snapshots.
- Lock metadata from CLO-319 would be optional rather than central.

Effort: S
Risk: low

### Approach B: Build listing from run-state loader/manifest abstractions

One-line summary: Extend existing run-state loading/manifest code to understand pending and response artefacts, then have the CLI render that richer model.

Pros:
- Could reuse broader run-state semantics later.
- Keeps filesystem interpretation in run-state rather than a command module.
- May support future UI/session listing use cases.

Cons:
- Larger API surface and more coupling for a read-only listing command.
- Risk of changing loader assumptions unrelated to this task.
- More work to satisfy the same FR-37 acceptance criteria.

Effort: M
Risk: medium

### Approach C: Consume only per-phase lock files

One-line summary: Treat `runs/<id>/locks/<phase>.lock` as the source of blocked entries and render lock holders.

Pros:
- Uses the CLO-319 schema intended to be inspectable.
- Can expose active holder/process data.
- Naturally filters released locks via `PhaseLock::inspect`.

Cons:
- Does not satisfy the explicit pending/response acceptance criteria by itself.
- A HITL gate can be pending without a live phase lock after the process exits.
- More dependent on advisory-lock lifecycle details than necessary.

Effort: S/M
Risk: high

## Chosen approach

**Approach A: Additive command module scanning pending/response files.** It directly implements FR-37 and the Linear acceptance criteria with the smallest blast radius. Lock-file inspection can be layered in later only if design/implementation finds stale-lock filtering is necessary for display polish.
