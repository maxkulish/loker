# CLO-295 Discovery Report: Run Resumability via Status Markers

## Problem Framing

Today, `loker run <workflow>` creates a `RunDir`, starts a heartbeat, and executes every workflow step unconditionally. If the process crashes mid-run or is killed by the user, the next invocation starts from scratch — creating a brand-new run directory and re-running all phases. This wastes API tokens and time, and leaves the user with multiple partial run directories to clean up manually.

We want `loker resume <run-dir>` to continue a partially-completed run by reading the status markers and manifest already on disk. Phases with `<phase>.completed` markers (and verified sha256 digests) are skipped entirely. The first phase without a completed marker becomes the resume point, re-run in a fresh attempt directory. A live writer (heartbeat within TTL) causes the resume to abort with `RunInProgress`. A fully-completed run is a no-op. All state lives on disk — no bespoke resume file.

## Existing Code

The codebase already has a solid D3 protocol foundation:

- **`src/run_state/load.rs`** — `RunState::load()` implements the read protocol: loads manifest, scans markers, drops orphan entries, verifies sha256 digests, classifies heartbeat as `Live`/`Stale`. This is ~80% of what a resume planner needs to assess on-disk state.
- **`src/run_state/markers.rs`** — `MarkerWriter` writes `started`/`completed`/`failed` markers atomically. `next_attempt()` derives attempt counters from marker + dir scanning.
- **`src/run_state/heartbeat.rs`** — `HeartbeatWriter` spawns a tokio task ticking every 100s (default 300s TTL). `is_stale()` checks age against TTL.
- **`src/run_state/attempt_dir.rs`** — `AttemptDir` manages `attempts/<phase>/<n>/` directories with atomic promote-to-canonical.
- **`src/run_state/run_dir.rs`** — `RunDir::create()` bootstraps a fresh run directory with initial manifest and `attempts/` subdir.
- **`src/phase_runner.rs`** — `PhaseRunner::run()` coordinates strategy → aggregator → verify → persist. It already writes started markers, records terminal failures, and writes completed markers. The `persist` submodule handles manifest append and attempt archiving.
- **`src/manifest.rs`** — `Manifest::load()`, `append()`, `verify()`, and `dir_digest()` provide the content-addressed artefact registry.
- **`src/main.rs`** — CLI has `Run` and `Workflow` commands but no `resume` subcommand. `run_workflow()` creates a `RunDir`, prints the path, and calls `WorkflowRunner::run()`.
- **`tests/run_state_load.rs`** — Extensive tests for `RunState::load()` covering happy path, schema mismatch, corrupt/missing entries, orphan sweep, heartbeat stale/live, and `ChangesDir` digest verification.

**Baseline score: 7/10.** The atomic write protocol, marker types, heartbeat, manifest, and attempt directories are all well-implemented and tested. What's missing is purely the **resume orchestration layer**: a CLI subcommand, a resume planner that decides skip vs rerun per phase, a run-level executor that wires the planner to `PhaseRunner`, stale-tmp sweep, advisory lock for parallel-writer detection, and the TDD test contract (`tests/resume.rs`). No rewrite of existing code is needed — we compose on top.

## Approaches

### Approach A: Resume-as-WorkflowRunner Extension

Add resume logic directly into `WorkflowRunner`. The runner checks the run_dir before each depth level, skipping steps whose phases are already completed.

- **Pros:** Minimal new modules; reuse existing dependency graph and parallel execution logic.
- **Cons:** WorkflowRunner is already 6.8KB of complex code; adding resume state machine makes it harder to maintain. Steps ≠ phases in current model — mapping is unclear.
- **Effort:** M
- **Risk:** Medium — conflates two concerns, regression risk in core workflow engine.

### Approach B: Resume-as-separate ResumeRunner (chosen)

Create a new `src/resume.rs` module with a `ResumePlanner` that uses `RunState::load()` to decide the resume plan, and a `ResumeRunner` that walks the plan and delegates phase execution to `PhaseRunner`. The CLI `resume` subcommand creates a thin wrapper that calls `ResumeRunner::resume(run_dir, workflow)`.

- **Pros:** Clean separation — resume logic is isolated, testable, and does not touch `WorkflowRunner` internals. Can reuse `PhaseRunner` directly (which already writes markers and manifest entries). Maps cleanly to the TDD test contract.
- **Cons:** Need to wire workflow phase list into resume runner (currently workflows use `Step`, not `PhaseConfig`). Some adapter code needed.
- **Effort:** M
- **Risk:** Low — builds only on existing, well-tested primitives.

### Approach C: Resume-as-PhaseRunner Extension

Push resume logic down into `PhaseRunner` itself, making each phase self-resuming by checking its own marker before doing work.

- **Pros:** Very granular; each phase "just works" on re-invocation.
- **Cons:** PhaseRunner currently does not know about the workflow sequence or upstream artefacts. Adding manifest-based upstream artefact loading would bloat PhaseRunner beyond its scope. Also, idempotency (no-op for fully completed run) cannot live inside a single phase.
- **Effort:** L
- **Risk:** High — violates single-responsibility; would require refactoring PhaseRunner's contract.

## Approach Chosen

**Approach B: Resume-as-separate ResumeRunner.**

Reason: The D3 protocol already separates "read state" (`RunState::load`) from "write state" (markers/manifest/heartbeat). A dedicated `ResumePlanner` + `ResumeRunner` mirrors this separation at the orchestration layer. We can write `tests/resume.rs` that constructs a `RunDir`, writes markers, and asserts the resume plan without spinning up real backends. PhaseRunner already handles all per-phase writes; we only need to decide which phases to invoke.
