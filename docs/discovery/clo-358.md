# Discovery Report: CLO-358 — Phase bridge mislabels artefact kind in manifest

## Problem framing

**WHO:** Users running phase-based workflows (e.g., `loker run task-kickoff`) who inspect `manifest.json` to understand what artefacts a run produced.

**WHAT TODAY:** Every `.md` artefact is labeled `kind: "design.md"` regardless of actual filename. For example, `review.md` and `plan.md` both appear as `"design.md"` in the manifest.

**WHAT WE WANT:** The manifest `kind` field should match the artefact filename stem: `design.md` → `"design.md"`, `review.md` → `"review.md"`, `plan.md` → `"plan.md"`, and arbitrary future markdown outputs should also be representable without a code change.

**WHY NOW:** CLO-327 introduced the phase-based runner and hardcoded the `.md` → `DesignMd` mapping as a temporary simplification. The PRD for CLO-327 explicitly expects `design.md`, `review.md`, and `plan.md` to be distinguishable in the manifest, so this is a known follow-up defect.

This is the root cause: any `.md` output gets `DesignMd`.

## Baseline score: 6/10

The code is well-structured but the `Kind` enum is too rigid for an expanding set of workflow output filenames. The fix is small but touches the type system, serde, schema, and two match sites. A score of 6 reflects that the change is localized but requires care to avoid regressions in manifest loading and HITL verification.

## Approaches identified

### Approach A: String-backed `Kind` (newtype)

Replace the `Kind` enum with `pub struct Kind(pub String)` and a few associated constants (`DESIGN_MD`, `REVIEW_MD`, etc.).

- **Pros:**
  - Zero code changes needed for new workflow output filenames.
  - Mapping in `phase_bridge.rs` becomes trivial: `Kind(phase.output.clone())`.
- **Cons:**
  - Loses exhaustiveness checking at match sites.
  - Requires touching every `match` on `Kind` across the codebase (`run_state/load.rs`, `human_verifier.rs`, `summary/mod.rs`).
  - Schema must be relaxed to `type: string`, which weakens validation.
- **Effort:** M
- **Risk:** medium

### Approach B: Extend enum with `PlanMd` + `OtherMd(String)` catch-all

Keep the `Kind` enum but add:
- `PlanMd` for the immediate missing variant.
- `OtherMd(String)` for any unknown `.md` filename (e.g., `analysis.md`, `fix.md`, `synthesis.md`).

- **Pros:**
  - Fixes the immediate issue (`plan.md`).
  - Future-proof: new filenames serialize correctly without code changes.
  - Well-known kinds (`DesignMd`, `ReviewMd`) keep exhaustiveness safety where they matter.
  - `OtherMd("analysis.md")` serializes as `"analysis.md"`, satisfying the AC.
- **Cons:**
  - Match sites need an `OtherMd(s)` arm (but this is a single additive arm).
  - Schema needs updating to allow arbitrary strings or at least the new known values.
- **Effort:** M
- **Risk:** low

### Approach C: Minimal fix — add only `PlanMd` and smarter stem matching

Add only `PlanMd`. Update `phase_bridge.rs` to match exact filenames: `design.md` → `DesignMd`, `review.md` → `ReviewMd`, `plan.md` → `PlanMd`, everything else `.md` → `DesignMd`.

- **Pros:**
  - Smallest diff.
  - Fastest to implement and review.
- **Cons:**
  - Does not solve the general problem; `analysis.md`, `fix.md`, etc. will still be mislabeled.
  - Every new workflow output filename will require another code change.
- **Effort:** S
- **Risk:** low

## Approach chosen: **B**

**Reason:** Approach B fixes the immediate defect (`plan.md` mislabeled) while also making the system future-proof for the many other markdown output filenames already in use (`analysis.md`, `fix.md`, `synthesis.md`, `judge.md`, `code.md`, `exec.md`, `think.md`). The `OtherMd(String)` catch-all is a small, additive change that does not break existing consumers. It balances type safety for well-known kinds with flexibility for new workflow authors.

The schema will be updated to keep the existing enum as a recommended set but relax to allow any string, ensuring forward compatibility.
