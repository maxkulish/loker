# Discovery Report — CLO-292: PhaseRunner composing Strategy + Aggregator + VerifyHook

## Problem framing

Workflow authors and downstream run/resume orchestration are affected today because Loker has the phase primitives but not the coordinator that turns a phase definition into a durable terminal result. Current behaviour is fragmented: strategies can call backends, aggregators can fold branch output, verify hooks can judge output, and manifest/status modules can persist state, but no `PhaseRunner` composes these in the required order. The desired behaviour is a single phase-level API that dispatches by configured names, executes attempts, verifies output, persists exactly one successful artefact to the manifest, and writes started/completed/failed markers for recovery. This is needed now because T-028 blocks M5 trace/run/resume tasks and the M6 end-to-end reference workflow.

## Existing code

### What exists

- `src/strategy/mod.rs` defines the object-safe `Strategy` trait plus shared `PhaseContext`, `Prompt`, `StrategyOutput`, `StrategyError`, `StrategyKind`, `Attempt`, and verify-outcome types.
- `src/strategy/single_model.rs`, `src/strategy/parallel_fanout.rs`, and `src/strategy/escalating_retry.rs` implement the three strategy families already needed by this task.
- `src/aggregator/mod.rs` exposes concat, vote, LLM judge, and `any_fail_evaluate`; `src/aggregator/concat.rs` has an aggregator enum whose supported runtime dispatch currently covers concat and explicitly rejects unsupported variants.
- `src/strategy/verify/` exposes the `VerifyHook` trait plus `RunCommand`, `LLMVerifier`, and `TestRunner` implementations.
- `src/manifest.rs` provides manifest schema types, producer/kind enums, SHA helpers, atomic append/rewrite, content verification, and marker-based orphan filtering.
- `src/run_state/markers.rs` provides `MarkerWriter` for started/completed/failed marker writes; `src/run_state/load.rs` exists for resume-oriented manifest/marker loading.
- `docs/run-state.md` defines the canonical write protocol: started marker, artefact write, manifest rewrite, completed marker; failure archive under `attempts/<phase>/<n>/` before failed marker.
- `docs/prd/2026-04-25-loker.md` includes the maintainability requirement that `PhaseRunner` be tested as a trait boundary, and `docs/plans/001-implementation-roadmap.md` places T-028 at the M5 integration point.

### Gaps for CLO-292

- No `phase_runner` module or public `PhaseRunner::run(...)` API exists yet.
- No configuration-level dispatcher maps the issue's names (`single`, `parallel`, `escalating_retry`; `first`, `concat`, `vote`, `any_fail`, `all_pass`; `run_command`, `llm_verifier`) to concrete in-tree implementations.
- Aggregator vocabulary is not fully aligned with the issue: `first` and `all_pass` need a thin PhaseRunner-level implementation, while concat/vote/any_fail can reuse existing modules.
- Strategies currently produce `StrategyOutput` metadata; PhaseRunner must decide the canonical artefact payload/path, write it, create the manifest entry with the right producer, and write markers in the protocol order.
- Terminal error mapping needs to wrap strategy/verify/persistence failures into the typed PhaseRunner surface required by the issue.

### Baseline score

**7 / 10.** Most leaf primitives exist and are tested, including strategy implementations, verify hooks, manifest persistence, and status markers. The remaining work is an integration layer with careful type/API design and test doubles rather than a rewrite of the underlying execution primitives.

## Approaches identified

### Approach A — Thin orchestration module over existing primitives

- **Summary**: Add `src/phase_runner.rs` with a small config model, dispatcher helpers, and `PhaseRunner` that composes existing strategies, simple PhaseRunner-level aggregators (`first`, `all_pass`), verify hook execution, manifest append, and marker writes.
- **Pros**
  - Reuses the already-merged M2–M4 primitives with minimal churn.
  - Keeps the integration point explicit and independently testable.
  - Leaves CLI/run-directory wiring to T-030/T-031 as requested.
- **Cons**
  - Requires adapter code because existing strategy outputs are metadata-heavy and not a single canonical artefact abstraction.
  - May need small additions to manifest/marker ergonomics discovered during implementation.
  - Dispatcher config may be superseded by the future workflow TOML parser.
- **Effort**: M
- **Risk**: Medium

### Approach B — Introduce a broader execution-engine abstraction first

- **Summary**: Define a more general engine/config model that normalises phase definitions, strategy config, aggregator config, verify config, artefact IO, and run-state IO before adding `PhaseRunner`.
- **Pros**
  - Could reduce future churn when T-030/T-031 wire run-level orchestration.
  - Provides a single canonical config type earlier.
  - May make trace/cost hooks easier to thread later.
- **Cons**
  - Higher scope than CLO-292 and risks pulling in non-goals.
  - Delays the M5 blocker behind abstractions not required by the TDD contract.
  - More likely to conflict with future workflow parser work.
- **Effort**: L
- **Risk**: High

### Approach C — Extend each strategy to own persistence and verification

- **Summary**: Push verify, aggregation, artefact persistence, and marker writes into each strategy implementation rather than adding a separate runner.
- **Pros**
  - Localises per-strategy retry/attempt behavior.
  - Escalating retry already has verify-aware control flow, so some logic appears close to existing code.
  - Fewer new top-level types.
- **Cons**
  - Duplicates manifest/marker/persistence code across strategies.
  - Violates the desired trait-boundary separation from the PRD.
  - Makes future trace/resume/cost concerns harder to add consistently.
- **Effort**: M-L
- **Risk**: High

## Chosen approach

**Approach A — thin orchestration module over existing primitives.**

This best matches the T-028 scope: PhaseRunner is the integration point, not a new execution engine or a rewrite of strategies. It keeps strategy, aggregator, verify hook, manifest, and marker responsibilities separated while adding only the adapters needed to produce one durable phase outcome.

## Discovery debt

None. The issue is explicitly blocked by CLO-283 and CLO-285 in Linear, but the current branch already contains manifest and load modules to design against; any remaining incompatibility should be handled during design/implementation rather than by opening a separate discovery follow-up.
