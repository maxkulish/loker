# Discovery Report: CLO-270 — Define VerifyHook trait and VerifyResult enum

**Task:** T-020 (Roadmap Phase 4 - Verify hooks)  
**PRD:** FR-18 (VerifyHook trait)  
**Date:** 2026-04-29  

---

## Problem framing

- **WHO:** Every verify-shaped path in the loker codebase currently uses stand-in implementations. `EscalatingRetry` (CLO-258) carries a soft block because it pattern-matches on a plain `String` reason inside `VerifyResult::Fail` rather than a structured `FailureReason`. Downstream verify-related tasks (CLO-271 RunCommand, CLO-272 LLMVerifier, CLO-273 TestRunner, CLO-260 pass_failure_context) all depend on a stable trait + result enum.

- **WHAT today:** `src/strategy/verify.rs` defines `VerifyHook`, `VerifyResult`, and `VerifyError` but the trait signature takes `&QueryOutput` (backend output) rather than a verify-specific context, the `Fail` variant uses `{ reason: String }` instead of a structured `FailureReason`, and the enum lacks `#[non_exhaustive]`. No `VerifyContext` type exists. `EscalatingRetry` calls `self.verify.verify(&query).await` directly with the backend output.

- **WHAT we want:** A single `VerifyHook` trait + `VerifyResult` enum with `#[non_exhaustive]` that all verify hooks implement. `Pass` and `Fail { reason: FailureReason }` are concrete (used in v0); `Repair { suggestion }` and `Score(f32)` are reserved variants that compile but no caller acts on. `FailureReason` carries structured context (verifier stdout/stderr, truncated payload) sufficient for CLO-260's `pass_failure_context`. A new `VerifyContext` struct carries phase artefacts + manifest pointer but not credentials. `VerifyError` distinguishes hook-implementation faults (sandbox crash, backend unreachable) from a clean `Fail` verdict.

- **WHY now:** T-020 gates T-021, T-022, T-023 (all Phase 4 verify hooks) and T-013 retro-fit (`EscalatingRetry` needs to consume `FailureReason`). The roadmap's critical path to Slice A runs through T-020 first. Every day this trait is a stand-in, the retro-fit cost for downstream consumers grows.

## Existing code

### `src/strategy/verify.rs` (current)

The existing module has three core types:

```rust
pub enum VerifyResult {
    Pass { notes: Option<String> },
    Fail { reason: String },
    Repair { suggestion: String },
    Score(f32),
}

pub struct VerifyError {
    pub message: String,
}

#[async_trait]
pub trait VerifyHook: Send + Sync {
    fn name(&self) -> &str;
    async fn verify(&self, output: &QueryOutput) -> Result<VerifyResult, VerifyError>;
}
```

Gaps with the CLO-270 scope:

| Gap | Current | Required |
|-----|---------|----------|
| `#[non_exhaustive]` | Missing | On `VerifyResult` enum |
| `Fail` variant | `{ reason: String }` | `{ reason: FailureReason }` |
| `FailureReason` struct | Does not exist | Structured container for CLO-260 |
| `VerifyContext` | Does not exist | Passed to `verify()` instead of `&QueryOutput` |
| `notes` field on `Pass` | `{ notes: Option<String> }` | `Pass` (no notes — per spec) |
| `VerifyError` | Struct with `message` | Same shape is fine, but must be documented as distinct from `Fail` |
| Test coverage | 0 tests | Unit test on stub returning each concrete variant |

### `src/strategy/escalating_retry.rs` (sole consumer)

`EscalatingRetry` calls the hook as:

```rust
self.verify.verify(&query).await
```

where `query: &QueryOutput`. It pattern-matches on:

```rust
VerifyResult::Fail { reason } => reason.clone(),
```

and uses `result.is_pass()`. These call sites must be updated to use `FailureReason` and `&VerifyContext`.

### `src/strategy/mod.rs`

Re-exports `verify::{VerifyError, VerifyHook, VerifyResult}`. No changes needed beyond the updated types propagating through.

### `src/apply_verify/` (separate concern)

The `apply_verify` module has its own `VerifyResult` (in `verification.rs`) for shell-command verification runs. This is unrelated — it measures `exit_code`, `stdout`, `stderr`, `elapsed_ms`, `timed_out`, `truncated`. The two `VerifyResult` types serve different purposes and should remain distinct.

## Approaches

### Approach A: In-place refactor of `src/strategy/verify.rs`

Refactor the existing `verify.rs` module to add `FailureReason`, `VerifyContext`, `#[non_exhaustive]`, and update the trait signature. Update the single consumer (`EscalatingRetry`) in the same commit.

- **Pros:**
  - Single-file change, minimal diff
  - No new files to maintain
  - Immediate payoff for CLO-258 retro-fit
- **Cons:**
  - Trait signature change (`&QueryOutput` → `&VerifyContext`) is a breaking change for any code outside this repo referencing the trait
  - `EscalatingRetry` needs to build `VerifyContext` from `QueryOutput` at the call site, creating a temporary coupling
- **Risk:** Low — the module is small (50 lines), the consumer is one file
- **Effort:** S (2-3 files changed)

### Approach B: New module `src/verify/` with deprecation path

Create a new top-level `src/verify/` module with the clean API, deprecate the old `src/strategy/verify.rs` types with `#[deprecated]` shims pointing at the new module. Migration happens incrementally.

- **Pros:**
  - Clean slate, no legacy naming
  - Deprecation period gives downstream consumers (CLO-271, CLO-272, CLO-273) time to adapt
  - Can introduce `VerifyContext` without `QueryOutput` coupling
- **Cons:**
  - Two copies of the same types during migration window
  - Adds complexity: re-exports, deprecation attributes, cross-module imports
  - No actual downstream consumers yet (CLO-271, CLO-272, CLO-273 are not implemented)
- **Risk:** Low — but unnecessary complexity for v0 where only one consumer exists
- **Effort:** M (4-6 files)

### Approach C: Enrich in-place + add `VerifyContext` factory

Same as Approach A, but also add a `VerifyContext::from_query_output(query: &QueryOutput)` constructor so `EscalatingRetry` can build the context without exposing `QueryOutput` fields in the trait contract.

- **Pros:**
  - All benefits of Approach A
  - Clean API boundary: hook implementations never see `QueryOutput`
  - Factory method documents which `QueryOutput` fields flow into verify context
  - Easy for future callers (phase runner) to build context from other sources
- **Cons:**
  - Slightly more code than A
- **Risk:** Low
- **Effort:** S (3-4 files)

---

## Approach chosen: **C — Enrich in-place + factory constructor**

**Reason:** Approach C gives the cleanest API boundary (hooks receive `VerifyContext`, not `QueryOutput`) while keeping the change contained. The `from_query_output` factory is a single function that documents exactly which backend signals flow into verify context. Once the phase runner (T-029) replaces `EscalatingRetry` as the direct caller, the factory can be updated without touching hook implementations.
