## Problem Framing

**Who is affected:** Workflow authors and operators running multi-phase AI workflows that need human escalation gates (reviewers, signoff steps, policy checks) before continuing.

**Current behaviour:** `VerifyHook` currently supports `RunCommand`, `LLMVerifier`, and `TestRunner`; verify failures are strictly machine-evaluated and represented through existing backend outputs and backend errors. There is no native pause state that writes a pending marker into run state or waits on a structured human response, so manual intervention must be done outside the runner flow and is not first-class discoverable.

**Desired behaviour:** `HumanVerifier` should emit a formal pending request in the run directory, stop phase progress at verify-time, and unblock when a structured response file is present, preserving existing strategy/artefact contracts. Operators should be able to inspect exactly what phase/artefact is pending and what human decision was recorded.

**Why now:** `CLO-317` starts M10 (HITL), and FR-17 depends on this scaffold before gate server (`T-051`) and advisory locking (`T-050`) are added.

## Existing Code

### Verify orchestration layer
- `src/phase_runner.rs`
  - `VerifyHookName` currently includes only `None`, `RunCommand`, `LlmVerifier`.
  - `PhaseRunner::run` resolves verify hook through `dispatch::resolve_verify_hook`, executes it, and treats `!is_pass()` as terminal verify failure.
- `src/phase_runner/dispatch.rs`
  - Dispatch currently maps `RunCommand` and `LlmVerifier`; no `HumanVerifier` selector.
  - `canonical_bytes()` and `selected_attempt_index()` logic already provides single canonical artefact bytes for verifier consumption.

### Verify hook API and implementations
- `src/strategy/verify/verify.rs`
  - Core trait `VerifyHook` and result type (`Pass`, `Fail`, reserved `Repair`, `Score`) already exists.
  - `VerifyContext` carries stdout/stderr, backend_name, model, structured output, and duration.
- `src/strategy/verify/{run_command.rs,llm_verifier.rs,test_runner.rs}`
  - Concrete hooks are implemented and tested; no human-wait behavior present.

### Run-state model
- `src/run_state/markers.rs`
  - Supports `started`, `completed`, `failed` markers only.
  - HITL marker directories are not yet wired into run execution.
- `src/run_state/mod.rs`, `run_state/run_dir.rs` define stable run directory layout and marker/attempt conventions.

### HITL schema groundwork (ready but unused)
- `docs/schemas/pending.schema.json` and `docs/schemas/response.schema.json` already define pending/request and human-response payload shapes.
- Fixture coverage exists under `tests/fixtures/schemas/pending/*` and `tests/fixtures/schemas/response/*`, and schema validation is exercised in `tests/schema_validation.rs`.

### Baseline score: 8 / 10

The primitive blocks are mostly present (verify abstraction + schema contracts + run layout), so most of the path is integration and lifecycle glue rather than foundational redesign. Most risk is in resume semantics and waiting behavior, but no major architecture rewrite is required.

## Approaches Identified

### Approach A — Direct verifier integration in existing phase runner
Add a new `VerifyHookName::HumanVerifier` in `src/phase_runner.rs` and `dispatch.rs`; implement `HumanVerifier` as a normal hook that writes `pending/<phase>.json`, then returns a synthetic non-pass `VerifyResult` path until `responses/<phase>.json` is present.

- **Pros**
  - Reuses `PhaseRunner::run()` error/marker flow and existing `VerifyContext`.
  - Smallest surface area: localized changes to verify dispatch + one new hook.
  - Fast to implement and test in v0.
- **Cons**
  - Requires explicit conventions for pending state detection to avoid blocking forever on malformed responses.
  - Needs follow-up for lock/queue safety (`T-050`) and severity timeout (`T-049`).
- **Effort:** M
- **Risk:** medium

### Approach B — Phase-level wait primitive in a separate `resume` handler
Introduce a generic `HumanWaiter` component outside `VerifyHook` called by `PhaseRunner` before/after strategy execution. Hooks remain untouched; phase runner controls the pending/response lifecycle.

- **Pros**
  - Keeps verify hooks purely pure/verifier-centric; HITL stays a scheduler concern.
  - Easier to enforce timeout and lock semantics centrally in a later iteration.
- **Cons**
  - Broader changes touching `PhaseRunner` control flow and attempt/state handling.
  - Requires larger regression pass before baseline tasks can proceed.
- **Effort:** L
- **Risk:** medium

### Approach C — Shell out HITL path behind a new verify hook + dedicated state command
Keep hook interface unchanged by adding `run_external` behaviour that executes a command to block/resume based on filesystem state, with a dedicated `HumanVerifier` state machine in that command layer.

- **Pros**
  - Minimal code changes in verify trait internals.
  - Fits existing `TestRunner`-style patterns in terms of filesystem-driven control.
- **Cons**
  - Extra process boundaries + error handling complexity.
  - Non-obvious observability of exact pending/reject/retry state in core state model.
- **Effort:** M
- **Risk:** high

## Approach Chosen

**Approach A — Direct verifier integration in existing phase runner**

### Why
This task is scoped as a v0 scaffold, and the repo already has the verify abstraction, schemas, and run layout needed for a low-risk path. A dedicated `HumanVerifier` hook plus dispatch wiring gives immediate, testable behavior with minimal code churn and preserves existing flow in `PhaseRunner` for non-HITL cases.
