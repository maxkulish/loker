# Discovery Report: CLO-268 — Implement Aggregator::LLMJudge with cross-family enforcement

| Field | Value |
|-------|-------|
| Task | CLO-268 |
| Date | 2026-04-28 |
| Phase | discovery |
| Branch | `feat/clo-268-llm-judge` |

## Problem Framing

**Who is affected:** Workflow authors using `Strategy::ParallelFanOut` who need to aggregate N candidate responses into a single chosen answer with structured rationale. Example: a generation phase that fans out to three different-family models (Claude, GPT, Gemini), then uses a fourth, distinct-family model as a judge to pick the best response and explain why.

**Current behaviour:** `ParallelFanOut` records per-branch `Attempt` records and supports `Aggregator::Concat` and `Aggregator::AnyFail`. The `LLMJudge` enum variant exists in `Aggregator` but has **zero** implementation — it is only a schema label. There is no mechanism to call a separate backend as judge, construct a ballot prompt, enforce family diversity, or parse a structured judge response into a chosen index and rationale.

**Desired behaviour:**
- `Aggregator::LLMJudge` calls a designated `judge_backend` after all candidate branches complete.
- It constructs a ballot prompt from a template, labelling each candidate by source backend and family.
- It enforces cross-family separation via `enforce_cross_family` from CLO-265: if the judge backend's family overlaps with any candidate target, the phase fails unless `require_judge_different_family = false`.
- The judge must return JSON matching `{ chosen_index: usize, reason: string }`; malformed responses raise `PhaseError::AggregatorContract`.
- Judge backend transport errors surface as `PhaseError::JudgeUnavailable`.
- The final `StrategyOutput` points to an aggregated artefact containing the chosen candidate's output plus rationale metadata.

**Why now:** This is T-017 on the Phase 3 critical path. It is the last aggregator variant before T-029 (phase runner) can compose the complete strategy → aggregator → verify pipeline. CLO-265 (family lookup) is already merged to main, so the cross-family check is unblocked.

## Existing Code

### `src/aggregator/mod.rs`
- Already owns `Concat` and `AnyFail` logic.
- Defines `AggregateInput`, `BranchOutcome`, `BranchSuccess`, `BranchFailure`, `AggregatedArtifact`, `AggregatorError`.
- `Aggregator` enum currently only has `Concat`; needs `LLMJudge` variant.
- `concat.rs` has the concat-specific logic. This is a good pattern to follow for `llm_judge.rs`.

### `src/aggregator/concat.rs`
- `Aggregator` enum + `aggregate()` method.
- Config payload: `heading_template: String`.
- Returns `Result<AggregatedArtifact, AggregatorError>`.
- Baseline pattern for adding `LLMJudge` config payload (`judge_backend`, `prompt_template`, `require_judge_different_family`).

### `src/family.rs`
- `family_of(backend_id)` → `Family` lookup table (CLO-265, merged to main).
- `enforce_cross_family(targets)` → `Result<(), PhaseError::FamilyOverlap>`.
- `PhaseError` already has `FamilyOverlap` and `AggregatorContract`.
- **Missing:** `PhaseError::JudgeUnavailable` variant (needed for AC: "judge backend transport error surfaces as `PhaseError::JudgeUnavailable`").

### `src/strategy/parallel_fanout.rs`
- `ParallelFanOut` dispatches to N backends via `FuturesUnordered`.
- Collects all `Attempt` records before aggregation (unlike `AnyFail`, which short-circuits).
- Currently only branches on `is_any_fail`; `Concat` is handled post-loop.
- No hook for secondary backend call during aggregation.

### `src/backend/mod.rs`
- `Backend` trait: `async fn query(&self, prompt, cwd, model) -> Result<QueryOutput, BackendError>`.
- `QueryOutput::from_text(text, backend, duration)` builder.
- `BackendError` has typed variants including `Network`, `Unavailable`, etc.
- Mock backends (`tests/strategy_parallel_fanout.rs`) use a `MockBackend` struct with configurable delay/response.
- No wiremock used yet in this repo for unit tests (wiremock is present in `tests/tensorzero_backend.rs` for HTTP contract tests).

### `src/strategy/mod.rs`
- `Aggregator` enum stub: `Concat`, `AnyFail`, `Vote`, `LLMJudge`.
- `StrategyError` has variants for `BackendNotFound`, `NoBackends`, `PromptRender`, `Backend`, `Exhausted`, `FloorViolation`, `AnyFail`.
- **Missing:** `StrategyError` variant for judge-specific failures (but the issue says judge errors are `PhaseError`, not `StrategyError`).

### `docs/schemas/phase_result_parallel.schema.json`
- Already accepts `"llm_judge"` in the `aggregator` enum.
- `verify` accepts `"pass"`, `"fail"`, `"skipped"`.
- Baseline score: **7 / 10**. Schema stubs, enum labels, family lookup, and parallel infrastructure already exist. What is missing is 100% of the behavioral aggregator logic, the cross-family enforcement hook, the judge prompt builder, the JSON ballot parser, and one `PhaseError` variant.

## Approaches

### Approach A — Inline LLMJudge in `parallel_fanout.rs` (extend existing loop)

After the `FuturesUnordered` loop collects all attempts, call a new `aggregate_llm_judge()` helper inline within `parallel_fanout.rs`. The helper receives the judge backend name, template, attempts, and a slice of all registered backends to resolve the judge backend.

- **Pros:**
  - Minimal indirection; all logic visible in one file.
  - Reuses existing `PhaseContext` and `backends` slice.
  - No new trait or module needed.
- **Cons:**
  - Tightly couples strategy execution with judge aggregation.
  - `parallel_fanout.rs` grows significantly (already 300+ lines).
  - Harder to unit-test judge logic in isolation (need to construct a full `ParallelFanOut` + mock backends).
- **Effort:** M
- **Risk:** medium

### Approach B — Extract `llm_judge.rs` module under `src/aggregator/`

Follow the `concat.rs` pattern: create `src/aggregator/llm_judge.rs` with its own config enum variant, prompt builder, ballot parser, and family-check helper. `ParallelFanOut` calls `aggregator.aggregate(...)` just like `Concat`, but passes an extended `AggregateInput` that includes a reference to the judge backend and the full backend list.

- **Pros:**
  - Clean separation of concerns; judge logic is unit-testable without `FuturesUnordered`.
  - Prompt template tests need no live backend.
  - Snapshot tests for generated ballot text are easy.
  - Mirrors the `concat.rs` pattern already established in M3.
- **Cons:**
  - Requires threading `backends: &[Arc<dyn Backend>]` and `PhaseContext` into `Aggregator::aggregate()`, changing the trait-ish shape that `Concat` currently uses.
  - Need to decide how the judge backend is resolved from name to `Arc<dyn Backend>` in the aggregator module.
- **Effort:** M
- **Risk:** low

### Approach C — Full `Aggregator` trait with async backend access

Define `trait AggregatorLogic { async fn aggregate(&self, input: AggregateInput, backends: &[Arc<dyn Backend>], ctx: &PhaseContext) -> Result<AggregatedArtifact, AggregatorError>; }`. Convert `Concat` and `LLMJudge` into trait impls.

- **Pros:**
  - Future-proof for all four aggregator variants.
  - Clean async boundary for judge backend calls.
- **Cons:**
  - Major refactor touching `Concat` and `AnyFail` (already shipped in CLO-266/267).
  - `async` in trait + object-safety concerns unless using `#[async_trait]` or RPITIT (Rust 1.75+).
  - Over-engineering for a single new variant; T-029 phase runner may redesign this boundary anyway.
- **Effort:** L
- **Risk:** high

## Decision

**Chosen approach: B — Extract `llm_judge.rs` module under `src/aggregator/`.**

Rationale: The `src/aggregator/` module already owns `Concat` behavior in `concat.rs` and `AnyFail` evaluation in `mod.rs`. Adding `llm_judge.rs` is the natural next step and keeps the judge-specific concerns (prompt construction, ballot parsing, family enforcement, backend lookup) isolated from the strategy's `FuturesUnordered` loop. The `Aggregator` enum in `concat.rs` needs to expand to include `LLMJudge { judge_backend, prompt_template, require_judge_different_family }` anyway; placing the behavioral logic in the same module tree is consistent. Unit tests for prompt templates and ballot parsing run without mock HTTP. Wiremock-backed tests for the full judge backend call sit in `tests/` as integration tests. This approach accepts a minor expansion of `AggregateInput` (or a new `LLMJudgeInput` wrapper) to carry judge resolution context, but avoids the large trait refactor of Approach C.
