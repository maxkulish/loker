# Discovery Report: CLO-261 — TensorZero create_backend wiring

## Framing

**WHO** is affected: Workflow authors and loader/runtime paths that declare `backend: tensorzero`. Today `Workflow::validate_with_capabilities` can accept TensorZero because `capabilities_for_name("tensorzero")` exists, but runtime creation via `create_backend("tensorzero", ...)` still falls through to `Unknown backend: tensorzero`.

**WHAT** the current behaviour is vs WHAT we want: Current behaviour is semantic divergence between supported-name validation and dispatcher instantiation. We want the same backend name set to be accepted by both, with `tensorzero` constructing a `TensorZeroBackend` from loader-provided configuration through a narrow adapter into `TensorZeroBackendOpts`.

**WHY now**: CLO-251 intentionally scoped TensorZero to capability declaration only, and Copilot flagged the missing dispatcher arm on PR #11. CLO-250 already introduced the TensorZero config/runtime option types, so this follow-up can close the M1 wiring gap without changing the backend wire protocol.

## Existing code

### Backend dispatcher (`src/backend/mod.rs`)
- `capabilities_for_name` already includes `"tensorzero"` and advertises `file_edit: true` alongside claude/codex/gemini.
- `create_backend(name, config, retry_policy)` handles `codex`, `gemini`, `claude`, `ollama`, and feature-gated `bedrock`, but not `tensorzero`.
- Unknown names currently fail with `anyhow::bail!("Unknown backend: {}", name)`, which is the failure CLO-261 must eliminate for `tensorzero`.
- `RetryExecutor` wrapping happens after backend construction, so a TensorZero arm can reuse existing retry-policy behaviour.
- Unit tests already pin `capabilities_for_name("tensorzero")`, but no test pins parity between capability names and create-dispatcher names.

### Config layer (`src/config.rs`)
- `BackendConfig` is the generic per-backend loader shape passed into `create_backend`; it has `command`, `api_key_env`, `model`, `timeout`, retry knobs, and CLI-specific fields.
- CLO-250 added top-level `TensorZeroConfig` with `endpoint`, `default_model`, `api_key_env`, `timeout_secs`, `retry_policy`, plus `to_backend_opts()`.
- `TensorZeroConfig::to_backend_opts()` resolves `api_key_env` and returns `TensorZeroBackendOpts`.
- The current create dispatcher receives only `&BackendConfig`, not the whole `Config`, so CLO-261 needs a local adapter or a broader dispatcher signature change.

### TensorZero backend (`src/backend/tensorzero.rs`)
- Runtime constructor is `TensorZeroBackend::new(TensorZeroBackendOpts) -> Result<Self, BackendError>`.
- `TensorZeroBackendOpts` contains `endpoint`, `model`, `api_key`, and `timeout`.
- Endpoint normalization (`/openai/v1/`) is intentionally done in the backend helper, so the adapter should pass endpoint through rather than duplicate URL rewriting.
- `is_available()` returns `true` without probing; connection/auth failures are surfaced by `query()` as typed `BackendError`s.
- Existing public tests in `tests/tensorzero_backend.rs` directly instantiate `TensorZeroBackend`, exercising wire behaviour but not the dispatcher path.

### Related docs and decisions
- `specs/2026-04-26-clo-250-add-tensorzero-config-schema.md` explicitly avoided forcing TensorZero into subprocess-shaped `BackendConfig` for the long-term config surface.
- `docs/handoff.md` documents top-level `[tensorzero]` as the operator-facing TOML section.
- CLO-261's issue scope is narrower: add the dispatcher arm and a `BackendConfig -> TensorZeroBackendOpts` bridge for the existing `create_backend` call shape.

## Baseline score: 8/10

Strengths:
1. `TensorZeroBackend` is implemented and covered by wiremock tests.
2. Runtime opts already exist and are re-exported.
3. Config env resolution pattern exists in `TensorZeroConfig::to_backend_opts()`.
4. Retry wrapping is centralized after backend construction.
5. Capability lookup already names `tensorzero`.

Gaps:
1. Dispatcher has no `tensorzero` arm.
2. `create_backend` lacks access to top-level `[tensorzero]`, only `BackendConfig`.
3. No parity test exists between `capabilities_for_name` and dispatcher-supported names.
4. No integration test exercises `create_backend("tensorzero", ...)` on a wiremock endpoint.

No rewrite is needed; the gap is a contained adapter and match-arm addition.

## Approaches identified

### Approach 1: Minimal dispatcher arm + BackendConfig adapter (chosen)
- Add a private adapter in `src/backend/mod.rs` mapping `BackendConfig` fields to `TensorZeroBackendOpts` (`command` as endpoint, `model` as function/model, `api_key_env` via env lookup, `timeout` seconds with sane default).
- Add `"tensorzero" => Arc::new(tensorzero::TensorZeroBackend::new(adapter(config)?)?)` to `create_backend`.
- Unit-test adapter behaviour and add a dispatcher integration test with wiremock.
- Pros:
  - Smallest change; preserves `create_backend` signature and all call sites.
  - Directly satisfies issue wording around `BackendConfig -> TensorZeroBackendOpts`.
  - Keeps endpoint normalization in `TensorZeroBackend`.
- Cons:
  - Uses subprocess-shaped `BackendConfig.command` as HTTP endpoint, which is not the long-term operator-facing `[tensorzero]` shape.
  - Requires clear docs/tests so the mapping is not mistaken for a broader config redesign.
- Effort: S
- Risk: low

### Approach 2: Change create_backend to receive full Config
- Change dispatcher signature to `create_backend(name, &Config, retry_policy)` or add a TensorZero-specific creation path that can read top-level `[tensorzero]`.
- Pros:
  - Aligns better with CLO-250's top-level `[tensorzero]` design.
  - Avoids overloading `BackendConfig.command` as an endpoint.
- Cons:
  - Many call sites in `src/conductor.rs`, `src/workflow.rs`, and tests currently pass `&BackendConfig`.
  - Bigger refactor for a one-arm dispatcher gap.
  - Risks mixing backend selection and global config lookup concerns.
- Effort: M-L
- Risk: medium

### Approach 3: Synthesize `backends.tensorzero` during config load
- During `load_config`, when top-level `[tensorzero]` exists, insert/update `config.backends["tensorzero"]` with a derived `BackendConfig`; leave `create_backend` signature unchanged.
- Pros:
  - Keeps dispatcher simple while preserving the top-level TOML surface.
  - Can make workflow loader work from documented `[tensorzero]` config automatically.
- Cons:
  - Hidden mutation during config load is harder to reason about and test.
  - Still needs a field-mapping convention into `BackendConfig`.
  - Scope extends beyond the dispatcher arm requested by CLO-261.
- Effort: M
- Risk: medium

## Approach chosen: Approach 1

Choose the minimal dispatcher arm plus private adapter. It closes the semantic divergence with the least surface-area change, keeps all existing call sites intact, and provides a clear seam for later config-loader synthesis if the project wants top-level `[tensorzero]` to auto-materialize a backend entry.
