# CLO-291 Discovery Report: M6 End-to-End Integration Test

## Problem Framing

**WHO**: The loker orchestrator project. M6 is the exit gate for Phase 7 and
the final pre-v0 checkpoint — it proves the three primitives (HTTP-gateway
backend, named strategies, verify hooks) compose end-to-end.

**WHAT**: Today individual components are tested in isolation:
- Strategy behaviour (`strategy_*` tests)
- Template substitution (`workflow_template.rs`)
- Workflow grammar parsing (`workflows_design_doc_tdd.rs`)
- Phase runner with injected mocks (`phase_runner_integration.rs`)
- RunDir layout (`run_dir_layout.rs`)
- Manifest operations (`manifest.rs`)
- Trace JSONL writing (`trace_jsonl.rs`)
- Summary aggregation (`summary.rs`)
- TensorZero backend wiremock contracts (`tensorzero_backend.rs`)

No test runs the full four-phase pipeline (design → review → implement →
verify) against a real spec and asserts the combined output: run-dir layout,
manifest with sha256 entries, trace.jsonl with gen_ai spans, per-phase
artefacts, summary.json, and resume idempotency.

**WHY NOW**: All three blockers are resolved:
- CLO-289 (prompt templates) — merged PR #44
- CLO-290 (calculator spec at `examples/specs/calculator.md`) — merged PR #38
- CLO-269 (Vote aggregator) — merged PR #24

The branch `feat/clo-291-e2e` is up to date with `main`.

**Baseline score: 4/10** — good skeleton, no E2E integration test.

## Existing Code

### Key modules the test must interact with

| Module | File | Role |
|--------|------|------|
| Workflow grammar | `src/workflow/grammar.rs` | Parses `.lok/workflows/*.toml` → typed `Workflow` AST with phases |
| Template engine | `src/workflow/template.rs` | Substitutes `{{ spec }}`, `{{ phase.<name>.output }}`, `{{ var.<name> }}` |
| Phase runner | `src/phase_runner.rs` | Executes a single phase with a strategy, backends, verify hook |
| Workflow runner | `src/workflow/mod.rs` (old) | Runs shell-based workflows (step model, not phase model) |
| Workflow conductor | `src/workflows/mod.rs` | Orchestrates phase-based workflows |
| RunDir | `src/run_state/run_dir.rs` | Creates `runs/<workflow>-<ts>-<uuid>/` with manifest |
| Manifest | `src/manifest.rs` | Append-only manifest with sha256 entry tracking |
| Trace writer | `src/trace.rs` + `src/trace/*` | OpenTelemetry GenAI JSONL trace |
| Summary writer | `src/summary/*` | Final `summary.json` with per-backend tokens |
| Markers | `src/run_state/markers.rs` | `*.started.N`, `*.completed`, `*.failed` markers |
| TensorZero backend | `src/backend/tensorzero.rs` | HTTP gateway backend (live mode) |

### Existing test patterns

1. **`tests/integration.rs`** — CLI-level tests: `cargo run --bin loker run <workflow.toml>` 
   with shell-only workflows (no LLM backends needed). Fast, self-contained.

2. **`tests/phase_runner_integration.rs`** — In-memory mock backends implementing the
   `Backend` trait. Tests single phases and verify hooks at the `PhaseRunner` level.
   Uses `MockBackend` / `ErrorBackend` with deterministic text output.

3. **`tests/tensorzero_backend.rs`** — Wiremock contract tests for the TensorZero
   backend HTTP surface. In-process wiremock server returning `ResponseTemplate`.

4. **Test fixtures**: `tests/fixtures/workflows/` (test workflow TOMLs),
   `tests/fixtures/tensorzero/` (HTTP request/response bodies),
   `tests/fixtures/schemas/` (JSON schemas for trace events, spans, verdicts, manifests).

### What's missing

- **No `tests/fixtures/m6/` directory** — no wiremock response bodies per phase
- **No E2E workflow-level mock** — `phase_runner_integration.rs` tests phases in
  isolation, not the full pipeline with template substitution, manifest tracking,
  trace recording, and summary emission
- **No resume idempotency test** — no test asserts that re-running a completed
  workflow with `--rerun=false` makes zero backend calls
- **No E2E trace schema validation** — `schema_validation.rs` tests schemas, but
  no test validates a real trace.jsonl from a full pipeline run

## Approaches

### Approach A: PhaseRunner-level orchestrated mock (recommended)

Use the existing `PhaseRunner` API with mock backends (like `phase_runner_integration.rs`)
but orchestrate all four phases end-to-end through the workflow conductor,
asserting the combined output.

**Pros:**
- Reuses existing `MockBackend` pattern — no HTTP overhead
- Fast: no wiremock server startup, no port binding, no cross-process
- Full assertion coverage: run-dir, manifest sha256s, trace.jsonl spans,
  per-phase artefacts, summary.json, marker files
- Easy to test resume idempotency (re-invoke with same RunDir)

**Cons:**
- Tests at the conductor level, not the CLI `loker run` level
- Requires exposing the workflow conductor API for external callers
- Need to handle template substitution as a manual step before phase execution

**Effort:** M (2-3 days)
**Risk:** Low

### Approach B: Wiremock-stubbed TensorZero gateway

Run an in-process wiremock server that responds to TensorZero HTTP requests
with deterministic fixture bodies. Configure the loker config to point at
the mock server.

**Pros:**
- Tests the actual TensorZero backend code path
- Closer to production: exercises HTTP serialization, retry, auth
- Fixture files (`tests/fixtures/m6/<phase>/<backend>.json`) serve as
  documented response contracts

**Cons:**
- The canonical workflow (`design-doc-tdd.toml`) uses CLI backends
  (`claude/`, `codex/`, `gemini/`, `ollama/`), not TensorZero
- Only exercises the TensorZero path — other backends not tested
- Slower: wiremock server startup per test
- More complex setup: need to configure loker TOML to use TensorZero
  for all backends

**Effort:** M (2-3 days)
**Risk:** Medium — depends on creating a TensorZero-mapped workflow TOML

### Approach C: CLI-level shell-backend workflow

Create a fixture workflow that uses `shell` backends that echo deterministic
JSON/text output. Run via `cargo run --bin loker run <fixture>` like
`tests/integration.rs`.

**Pros:**
- Tests full CLI surface (`loker run`, exit codes, stdout/stderr)
- No mocking infrastructure needed
- Self-contained: no network, no external processes

**Cons:**
- The shell backend is a different code path from the phase/strategy backends
- Cannot test strategy behavior (parallel fan-out, escalating retry)
- Cannot test verify hooks or aggregators
- Doesn't exercise the canonical workflow

**Effort:** S (1 day)
**Risk:** Medium — tests the wrong abstraction level

## Approach Chosen

**Approach A: PhaseRunner-level orchestrated mock.**

Rationale:
1. Reuses the **exact same mock backend pattern** already proven in
   `phase_runner_integration.rs` — no new infrastructure.
2. Exercises the **real four-phase pipeline** through the workflow conductor:
   template substitution, RunDir creation, manifest tracking, trace recording,
   markers, summary emission.
3. **Fast**: deterministic in-memory responses, no HTTP, no CLI subprocesses.
   Budget well under 5s.
4. **Resume idempotency** is trivial: load the same RunDir, assert no new
   manifest entries or marker files.
5. **Trace schema validation** can use the existing fixture schemas.

The trade-off (not testing at the `loker run` CLI level) is acceptable
because:
- CLI-level shell tests (`tests/integration.rs`) already cover the `loker run`
  path with different workflows.
- The critical M6 assertion is that the **four phases compose correctly**
  through the conductor — that's a Rust API test, not a CLI test.
- A follow-up can add a `loker run design-doc-tdd --spec ...` smoke test for
  CLI-level coverage.

## Discovery Debt

None. The approach is well-understood and the implementation is additive
(a single test file + fixture response bodies).
