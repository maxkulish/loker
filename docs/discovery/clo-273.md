# Discovery Report: CLO-273 — Implement TestRunner verify hook parsing cargo + pytest JSON

**Date:** 2026-05-01
**Branch:** `feat/clo-273-test-runner`
**Task type:** development

## Problem framing

Workflow verification currently supports `LLMVerifier` and `RunCommand`, but there is no concrete hook that executes project tests and derives a binary gate signal from structured test results. This blocks the retry strategy from using deterministic compile/test outcomes (first-class test evidence) before escalating or accepting an implementation, and currently leaves the phase runner without a production-ready test-quality gate.

Today, users can only get unstructured pass/fail signals; there is no parser for cargo/pytest machine-readable output or standardized first-failure details in `FailureReason`. This means retry decisions are blind to whether tests truly ran, how many passed/failed, and what failed first.

`CLO-273` is now unblocked by `CLO-270` and `CLO-271`, and FR-16 already defines this capability as required for the retry loop. Implementing this now completes the verify-hook trilogy and unblocks `T-029` phase runner adoption of test-based verification.

## Existing code

- `src/strategy/verify/verify.rs` already defines `VerifyHook`, `VerifyResult`, `FailureReason`, `VerifyContext`, and structured `sandbox_violation` metadata.
- `src/strategy/verify/run_command.rs` already implements a process-based verifier with:
  - env allowlist, timeout + kill-on-timeout process-group cleanup,
  - stdout/stderr caps with truncation,
  - exit/signal mapping into structured failures.
- `src/strategy/verify/mod.rs` exports `LLMVerifier` and `RunCommand`; a `test_runner` module is present and can be added without architectural friction.
- `tests/verify_run_command.rs` establishes behavior for sandboxing/exit-code mapping and provides patterns for hook-level tests.
- `tests/verify_test_runner.rs` (currently in progress) can drive parser behavior from fixed fixtures under `tests/fixtures/test_runner/` and validate full `to_verify_result` mapping.
- Context discovery already recognizes project capabilities (`has_cargo`, `has_pytest`) in `src/context.rs`, so auto-selecting/validating runner mode can be implemented cleanly in later phases.

## Baseline score

**7/10** — The core trait architecture and `RunCommand` execution scaffolding already exist, so the hook can be implemented directly in `verify::test_runner` with low architectural risk. Remaining risk is mainly correctness of parser edge-cases and mapping error/signal states to meaningful `FailureReason` across cargo + pytest variants.

## Approaches identified

### Approach A — New TestRunner hook module with structured output parsers

- **Summary:** Implement `TestRunner` in `src/strategy/verify/test_runner.rs` (or extend current file) to execute either cargo/pytest through `RunCommand`, parse JSON output, and map to `VerifyResult`.
- **Pros:**
  - Aligns with existing verify-hook architecture and avoids legacy module coupling.
  - Reuses proven execution/sandboxing primitives from `RunCommand`.
  - Easy to test with fixture-driven parser unit/integration tests.
- **Cons:**
  - Must support two distinct JSON formats cleanly (`cargo` JSON-lines + pytest summary object).
  - Must explicitly handle malformed/out-of-band output and non-zero exits.
- **Effort:** M
- **Risk:** Medium

### Approach B — Shared parser service + thin hook wrapper

- **Summary:** Create a generic parser service (`parse_test_output`) shared across possible future hooks, and keep `TestRunner::verify` as a thin adapter over `RunCommand`.
- **Pros:**
  - Easier future extension for other test frameworks.
  - Better separation between execution and domain parsing.
- **Cons:**
  - Additional module layering and indirection for this single feature.
  - Delays immediate delivery; extra tests needed for service boundaries.
- **Effort:** M
- **Risk:** Low-Medium

### Approach C — Delegate all parsing to shell glue script

- **Summary:** Keep Rust parsing minimal by invoking a shell/py script that normalizes test output into a fixed JSON schema.
- **Pros:**
  - Reduces Rust parsing complexity in the short term.
  - Can support custom repo-specific reporting formats quickly.
- **Cons:**
  - Re-introduces external dependencies and brittle runtime contract.
  - Harder to secure, test, and reason about in-process timeout/cap/signal semantics.
- **Effort:** M
- **Risk:** High

## Approach chosen

**Chosen: Approach A** — Implement/complete the dedicated `TestRunner` verifier module with `RunCommand` execution and inline structured parsers for cargo and pytest.

**Rationale:** It is the lowest-risk fit with the existing verify-hook architecture, preserves execution guarantees already implemented in `RunCommand`, and supports fixture-driven tests directly in Rust where we already have mature patterns for hook verification.

## Discovery debt

None. The issue provides explicit test contract and acceptance criteria; any parser edge-cases can be handled by fixture-driven tests before promotion.
