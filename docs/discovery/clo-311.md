# Discovery: CLO-311 `loker explain <workflow>`

## Problem framing

Workflow authors and maintainers are affected: before running a workflow they need to understand the phase DAG, strategy selection, backend fan-out/escalation, verify hooks, and declared artefacts. Today the canonical `design-doc-tdd` workflow is encoded in TOML and validated by lower-level parser/runtime pieces, but there is no CLI command that renders the structure as a readable static summary. The desired behavior is `loker explain <workflow>` producing a stable text report without backend calls or run-history lookup. This is needed now because Phase 9 is completing the CLI surface after `loker run`, and FR-34/T-042 explicitly calls for a snapshot-tested explain command.

## Existing code

- `src/main.rs` already has a top-level `Commands::Explain { dir, backend, focus }` for codebase explanation. This creates a CLI naming conflict with the requested `loker explain <workflow>` surface; the least disruptive path is to evolve this command into a unified explain command that detects workflow names/paths first and falls back to existing codebase explanation behavior.
- `src/main.rs::run_workflow()` already uses `workflow::find_workflow(name)` and `workflow::load_workflow_from_source(source)` for the step-based runner. That lookup behavior should be reused so `design-doc-tdd`, project-local `.lok/workflows/*.toml`, paths, and embedded workflows are found consistently.
- `src/workflow/mod.rs::WorkflowSource` carries either a file path or embedded TOML content. It exposes `display_name()`, and `find_workflow()` searches direct paths, `.lok/workflows`, global config, and embedded workflows.
- `src/workflow/grammar.rs` contains the phase-based TOML AST: `Workflow`, `Phase`, `Strategy`, backend resolver, input resolver, validation, and linting. It already detects missing phase references, duplicate phase names, malformed backend refs, forward references, and strategy constraints. Since phase dependencies only allow references to earlier phases, cycles are effectively surfaced as forward-reference/invalid-reference errors when a cycle is encoded.
- The canonical phase workflow exists at `.lok/workflows/design-doc-tdd.toml` and `tests/fixtures/workflows/design-doc-tdd.toml`. It declares `design`, `review`, `implement`, and `verify` with strategies, backends, `inputs`, prompt templates, and outputs.
- Verify hooks are not first-class fields in `workflow::grammar::Phase` today; examples keep hooks as comments or reserved `[phases.contract]` data. `src/phase_runner.rs::PhaseConfig` has `verify: VerifyHookName`, so the explain output can render `verify: none` for current grammar and optionally surface reserved contract keys/comments only when they become parsed data later.
- `Cargo.toml` already includes `insta`, and tests already use inline snapshots (`tests/aggregator_llm_judge.rs`). CLI integration tests run commands via `cargo run --quiet --bin loker -- ...` in `tests/run_cli.rs`, which is a suitable pattern for snapshoting `loker explain` output.

## Baseline score

7/10. The parser, lookup, validators, example workflow, and snapshot tooling are already present, so no rewrite is needed. The main gap is CLI integration and a small formatter/analysis layer; the only design wrinkle is preserving the existing codebase `loker explain` behavior while adding workflow explain semantics.

## Approaches

### Approach A: Unified top-level `loker explain` workflow-first detection

One-line summary: Keep the existing top-level command, accept a target argument, render workflow summaries when the target resolves to a workflow, and otherwise fall back to codebase explanation.

Pros:
- Matches the requested `loker explain <workflow>` command exactly.
- Preserves existing codebase explanation for directories and existing flags.
- Reuses current workflow lookup and phase grammar validation.

Cons:
- Requires careful argument/help text so users understand dual behavior.
- Ambiguous names may need deterministic precedence.
- Slightly touches existing codebase explain CLI surface.

Effort: M
Risk: medium

### Approach B: Add `loker workflow explain <workflow>` only

One-line summary: Add an explain subcommand under the existing `workflow` namespace and leave top-level `loker explain` untouched.

Pros:
- Avoids the existing codebase explain conflict.
- Smallest CLI parsing change.
- Easy to scope to workflow-only behavior.

Cons:
- Does not satisfy the literal acceptance criteria.
- Adds a second explain surface that may confuse users.
- Would likely require a follow-up to add the top-level alias anyway.

Effort: S
Risk: low implementation risk, high product mismatch risk

### Approach C: Build a separate phase-graph analyzer API first

One-line summary: Create a reusable analyzer that returns typed nodes/edges/errors, then have CLI formatting consume it.

Pros:
- Best long-term foundation for future diagram exports.
- Clean separation between analysis and rendering.
- Easier unit testing of graph behavior.

Cons:
- More structure than v0 requires.
- Diagram export is a non-goal for this task.
- Slower path to the snapshot-tested CLI.

Effort: L
Risk: medium

## Chosen approach

Approach A: Unified top-level `loker explain` workflow-first detection.

This satisfies the exact FR-34 surface while minimizing new architecture. The implementation can reuse `find_workflow`, `WorkflowSource`, and `workflow::grammar::Workflow` validation, add a stable text formatter, and keep the existing codebase explainer as the fallback path.
