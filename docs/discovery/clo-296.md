# Discovery Report — CLO-296: Implement summary.json with per-backend tokens + cost_budget_usd warning

## Problem framing

Loker's run executor currently emits per-phase artefacts, a manifest, trace.jsonl, and status markers — but no aggregate run summary. Operators, CI pipelines, and downstream tooling have no single file to read for total cost, token usage per backend, phase outcomes, or budget compliance. Every stakeholder who wants to answer "how much did this run cost?" or "did it exceed the budget?" must cobble the answer together from multiple files. The desired behaviour is a single `runs/<id>/summary.json` emitted at run end (success OR terminal failure) that aggregates per-phase outcomes, per-backend token rollups, total cost in USD, wall-clock duration, and a `cost_budget_warning: bool` when a configured `cost_budget_usd` is exceeded. This is needed now because it is a roadmap requirement (T-032), PRD FR-23/FR-23a, and a dependency for the end-to-end reference workflow (M6) where cost feedback is expected.

## Existing code

### What exists

- **`docs/schemas/summary.schema.json`** — Already complete schema with required fields (`loker.run_id`, `schema_version`, `started_at`, `finished_at`, `duration_ms`, `status`, `totals`, `backends`, `phases`), optional cost fields, `cost_budget_usd` / `budget_warning`, and `$defs` for `usage`, `backend_usage`, `phase_summary`. The schema has `additionalProperties: false` throughout.
- **`tests/fixtures/schemas/summary/positive/minimal.json`** and **`with_failures.json`** — Positive fixtures exist for schema validation tests.
- **`tests/fixtures/schemas/summary/negative/negative_duration.json`** and **`unknown_status.json`** — Negative fixtures exist.
- **`src/manifest.rs`** — `Kind::SummaryJson` is already registered in the manifest enum (serde-renamed to `"summary.json"`). `ManifestEntry::from_payload` and `Manifest::append` are ready for summary registration.
- **`src/run_state/run_dir.rs`** — `RunDir` provides `path()`, `manifest_path()`, `trace_path()`, `run_id()`. Summary would be written at `run_dir.path().join("summary.json")`.
- **`src/trace.rs` / `src/trace/writer.rs`** — Trace.jsonl lines contain `gen_ai.system` (backend name), `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `loker.run_id`, `loker.phase`, `loker.outcome`. The trace file is append-only via `TraceWriter`.
- **`src/phase_runner.rs`** — `PhaseRunner::run()` orchestrates strategy execution, aggregator, verify, manifest append, and marker writes. Each `PhaseOutcome` carries `strategy_output` (with `attempts: Vec<Attempt>`, each having `usage: TokenUsageReport`, `backend`, `model`, `duration`) and `strategy_kind`.
- **`src/strategy/mod.rs`** — `TokenUsageReport` with `input_tokens` / `output_tokens`. `Attempt` has `backend`, `model`, `usage`, `duration`, `finish_reasons`. `StrategyOutput` has `attempts`, `strategy` (StrategyKind), `final_status`.
- **`src/backend/mod.rs`** — `TokenUsage` with `prompt_tokens` / `completion_tokens`. `QueryOutput` carries `usage: Option<TokenUsage>`, `model`, `backend`.
- **`src/phase_runner/persist.rs`** — `commit_success` writes artefact and manifest entry. `record_terminal_failure` writes failure markers. These are the patterns a SummaryWriter would follow.
- **`tests/schema_validation.rs`** — Automatically validates all `docs/schemas/*.schema.json` fixtures against positive/negative test cases. A summary fixture already exists and will be checked by this harness once the summary writer exists.
- **`docs/run-state.md`** — Defines the atomic write protocol (write-tmp, fsync, rename) used by all file writes.

### Gaps for CLO-296

- **No `SummaryWriter` or `SummarySink` exists.** No code path collects per-phase outcomes at run end.
- **No pricing infrastructure exists.** `prices.toml` is referenced in the issue as a static price table keyed by `<backend>:<model>`, but no such file or lookup function exists. This must be created.
- **No run-level executor to call finalize.** `PhaseRunner::run()` handles single phases. The run-level executor that calls `SummaryWriter::finalize` after all phases complete doesn't exist yet (it's the run coordinator/WorkflowRunner, which is a separate task). The issue says finalize is invoked by the run-level executor; for testing, we can mock the caller.
- **`cost_budget_usd` source.** The `Workflow` struct in `src/workflow/mod.rs` doesn't have a `cost_budget_usd` field. The Config (`src/config.rs` / `lok.toml`) doesn't have one either. The source of this value needs to be plumbed — likely as a parameter to `SummaryWriter::finalize`.
- **No trace-file reader.** The summary must read `trace.jsonl` to aggregate token usage by backend+model. The trace file is append-only JSONL; a reader/parser module is needed.
- **No per-phase outcome tracker.** PhaseRunner emits per-phase outcomes but there's no accumulator that collects them across the run. The summary needs to know each phase's outcome (`completed`/`failed`/`skipped`), attempts count, wall-clock ms, and strategy.
- **Test fixtures / test contract.** The issue specifies `tests/summary.rs` with 5 test cases. No such file exists yet.

### Baseline score

**8 / 10.** The schema, manifest kind, run-dir accessors, and trace format are all pre-existing and well-defined. The trace writer pattern (`TraceSink` trait, file-backed writer, in-memory test sink) provides a strong template. The remaining work is additive: a new module (`summary.rs`), `prices.toml`, a trace reader, and wiring. No existing primitives need restructuring.

## Approaches identified

### Approach A — Dedicated `SummaryWriter` module with `SummarySink` trait (trace-like pattern)

- **Summary**: Create `src/summary.rs` with a `SummaryWriter::finalize(&RunDir, &TraceFile, &Manifest, &Workflow) -> Result<()>` function. Define `SummarySink` trait for test capture (like `TraceSink` / `InMemorySink`). Reads `trace.jsonl` to aggregate tokens per backend/model, computes cost via a static `prices.toml`, collects per-phase outcomes from the manifest and markers, writes `summary.json` via atomic write, and registers the artefact in the manifest.
- **Pros**
  - Follows the established `TraceSink` / `TraceWriter` / `InMemorySink` pattern that tests already use.
  - `SummarySink` trait enables in-memory test capture (TDD contract requires this).
  - Single-writer finalize means no concurrent-write complexity.
  - Idempotent (overwrites on resume) as specified in AC.
- **Cons**
  - Requires a trace-file parser that reads all lines and aggregates — this is the largest new code block.
  - Pricing table `prices.toml` is a new file format and lookup surface.
  - `cost_budget_usd` sourcing needs to be resolved (workflow config vs. parameter).
- **Effort**: M
- **Risk**: Low

### Approach B — Hook-based: emit summary incrementally during phase run

- **Summary**: Add a summary hook to `PhaseRunner::run()` that accumulates token usage and phase outcomes incrementally, then writes summary.json at the run-level finalize call. Avoids reading trace.jsonl by tracking state in memory.
- **Pros**
  - No trace-file parsing needed.
  - State is always up-to-date in memory.
  - Simpler aggregation logic.
- **Cons**
  - Requires threading summary state through PhaseRunner or a side-channel accumulator.
  - Adds complexity to the PhaseRunner hot path.
  - On resume, the in-memory state must be rebuilt from trace anyway — so the trace reader problem is only deferred, not eliminated.
  - Doesn't match the issue spec ("Reads trace.jsonl to aggregate").
- **Effort**: M
- **Risk**: Medium

### Approach C — Inline finalization in the run-level executor

- **Summary**: Instead of a separate `SummaryWriter::finalize`, emit summary.json as a final phase in the run coordinator. Create a synthetic `SummaryPhase` that runs after all real phases.
- **Pros**
  - Reuses the existing phase runner infrastructure (markers, manifest append, artefacts).
  - Summary is automatically idempotent (phase.completed marker prevents double-write).
- **Cons**
  - Abuses the phase runner for a non-LLM operation.
  - The run-level executor doesn't exist yet, so this adds coupling before the abstraction exists.
  - More complex to test in isolation.
  - Phase outcomes would need special handling (not a real phase result).
- **Effort**: L
- **Risk**: High

## Chosen approach

**Approach A — Dedicated `SummaryWriter` module with trace-based aggregation.**

This matches the issue spec exactly ("Reads `trace.jsonl` to aggregate"), follows the established `TraceSink` pattern, keeps the PhaseRunner clean, and produces the simplest isolated test surface. The trace reader needed for Approach A is a one-time parse cost that any approach using trace data must pay anyway. Pricing table lookup via `prices.toml` is isolated in its own helper and can be replaced with a live query (FR-23's open question) without changing the summary writer.

## Discovery debt

None. The schema is already settled, fixtures exist, the manifest kind is registered, and the trace format is fixed. Two minor open questions (pricing table location and cost_budget_usd plumbing) are implementation details — not unknowns that block implementation.
