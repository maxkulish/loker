## Problem framing

The loker phase runner (not yet built) and the resume path (T-031) need crash-safe
per-phase status markers to know which phases have started, completed, or failed.
Today, the manifest writer (`src/manifest.rs`, CLO-283) has an atomic write
primitive and an orphan-entry sweep, but there is no marker system that records
per-phase lifecycle events atomically. Without markers, the resume path cannot
distinguish "phase is in progress" from "phase is done" without guessing —
which violates the crash-injection contract (FR-23c).

**WHO**: The phase runner (T-028) and the resume walker (T-031) are the consumers.
**WHAT today**: `src/manifest.rs` provides `atomic_write` and the `Manifest` struct,
but there are no marker files in `runs/<id>/markers/`.
**WHAT we want**: A `MarkerWriter` API (`write_started`, `write_completed`,
`write_failed`) backed by the D3 atomic tmp+rename protocol, a `HeartbeatWriter`
Tokio task on a configurable cadence, and an `attempt_counter` helper.
**WHY now**: T-025 is the critical dependency for T-031 (resumability) and T-027
(attempt directories). The D3 protocol and atomic write primitive are already
decided and implemented in the manifest module.

## Existing code

- **`src/manifest.rs`**: Contains `atomic_write()` (tmp → fsync → rename → parent-fsync),
  `Manifest`, `ManifestEntry`, orphan sweep. Private helper — the markers module
  will need to either share it (extract into a helpers module) or replicate it.
- **`docs/run-state.md`**: Full D3 protocol spec including marker JSON schemas,
  the per-phase commit order (started → artefact → manifest → completed), and
  the kill matrix (14 crash-injection test rows). Marker body shapes are already
  specified here.
- **`src/family.rs`**: `PhaseError` enum with `#[non_exhaustive]` — new variants
  can be added without breaking downstream.
- **`Cargo.toml` deps**: `tempfile = "3"` (atomic tmp), `serde + serde_json = "1"`
  (marker JSON), `chrono = "0.4"` (timestamps), `sha2 = "0.10"` (manifest entry hash),
  `tokio = "1"` (heartbeat task), `rand = "0.9"` (tmp suffix). All needed deps
  are already present.
- **Test patterns**: Unit tests in `tests/manifest.rs` use `tempfile::TempDir`,
  `fs::read_dir`, `serde_json::json!` macros. Integration tests live in `tests/`.
- **`src/lib.rs`**: Public modules are re-exported here. New module needs
  `pub mod run_state;` (if any types are needed by integration tests).

### Baseline score: **6/10**

The `atomic_write` primitive exists but is private to `manifest.rs`. The marker
module needs new code from scratch (module, types, tests). No rewrite is needed
of existing code, but the marker code must be carefully aligned with the D3
protocol spec and the kill-matrix test coverage is significant. Score: 6
("some reuse, but substantial new code and test surface").

## Approaches identified

### Approach A: Standalone `run_state` module (recommended)

Create `src/run_state/markers.rs` with `MarkerWriter`, `HeartbeatWriter`,
`attempt_counter` as a new module. Extract `atomic_write` into a shared
`src/run_state/atomic.rs` helper (or reuse via `pub(crate)`) so both the
manifest module and markers module can use it.

**Pros:**
- Clean separation: markers are a distinct concern from the manifest
- Shared `atomic_write` prevents protocol divergence between manifest and markers
- Tests are isolated to a single module (`tests/run_state_markers.rs`)

**Cons:**
- Requires extracting `atomic_write` from `manifest.rs` (minor refactor)
- Two extra files in the module tree (`atomic.rs`, `markers.rs` + `mod.rs`)

**Effort:** M (2-3 days including test contract)
**Risk:** Low — protocol is fully specified in `docs/run-state.md`

### Approach B: Inline markers into `manifest.rs`

Add marker types and the heartbeat task directly into the existing `src/manifest.rs`
file, using the private `atomic_write` already there.

**Pros:**
- Zero refactoring to share `atomic_write`
- Fewer files

**Cons:**
- `manifest.rs` becomes a grab-bag of run-state concerns (manifest, markers, heartbeat)
- Violates single-responsibility — the file already has ~400 lines
- Harder to test independently

**Effort:** S (1-2 days)
**Risk:** Medium — tightly couples two distinct concepts; future T-031 resume
walk code would also need to go here or import from here, making the dependency
graph messy.

## Chosen approach: **Approach A — Standalone `run_state` module**

**Reason**: The D3 protocol explicitly separates markers from the manifest
(two different sub-directories in `runs/<id>/`, two different JSON schemas,
two different lifecycle roles). Merging them into one module would create
a maintenance liability as T-031 and T-027 add more run-state code. The
one-time cost of extracting `atomic_write` into a shared helper is negligible.

## Discovery debt

None — all unknowns from this discovery are resolved in the D3 protocol
spec (`docs/run-state.md`) and the existing test infrastructure.
