# Discovery Report — CLO-314

## Problem framing

**WHO:** Anyone landing on the loker GitHub repository — potential contributors, users evaluating the project, or existing lok users checking out the fork.
**HOW today:** The README is a comprehensive but dense document that mixes thesis, architecture, deployment, roadmap, lineage, and license into a single wall of text. A newcomer cannot get "what does this do and how do I start" in under one screen.
**WHAT we want:** A README that surfaces the thesis in one paragraph, explains the three primitives (Strategy, Aggregator, VerifyHook) in digestible form, shows install via `cargo install loker` and `make release`, and demonstrates a single end-to-end example the reader can copy-paste and run — all within one page for the install + run section.
**WHY now:** Phase 9 (M8, CLI surface) is complete — `loker run`, `loker resume`, `loker explain`, and `loker trace` all shipped. The CLI surface is stable enough that the example in the README will work. Phase 10 (M9, Documentation) is the next milestone. The existing README inherited from lok and accumulated milestones as they shipped; it needs a focused rewrite to serve as the project's front door.

## Existing code

### Current README.md

- ~220 lines of Markdown covering thesis, three primitives, architecture diagram (ASCII), deployment instructions, "what works today" command list, full roadmap table, design document links, and lineage.
- The primitives section is aspirational (Strategy/Aggregator/VerifyHook are documented as enums but M2-M4 shipped months ago — the code is ahead of the docs).
- No end-to-end example with actual `loker run ...` command + expected output.
- Install section only shows `cargo install --path .` (source build from the repo root), not `cargo install loker` from crates.io.
- The roadmap table duplicates what `docs/plans/001-implementation-roadmap.md` tracks more carefully.
- Lineage/license section is important but takes up space at the bottom.

## Baseline score

**3/10.** The README is the project's front door, and it fails at being one:
- No quick-start experience — the reader must scroll past architecture, roadmap, and lineage before seeing a single command.
- Code is ahead of docs — the primitives shipped months ago but the README still says "None ship yet (M2-M4)".
- No end-to-end runnable example.
- The install section is buried and incomplete.
- Old README content (lok-era history, full roadmap table) should be moved to `docs/` to reduce noise.

This is not a rewrite of working code — it is a rewrite of *communication*. The codebase is healthy; the README is the bottleneck.

## Approaches considered

### Approach A: Incremental edits to the existing README

Keep the current structure (thesis → primitives → architecture → deployment → commands → roadmap → lineage → license) and update individual sections: bump M2-M4 from "not shipped" to "shipped", add a commands section, swap the install snippet, add a short example at the bottom.

- **Pros:**
  - Minimal diff; easy to review.
  - Preserves existing hyperlinks and anchor targets others may reference.
- **Cons:**
  - The fundamental flow is backwards — roadmap and lineage come before the reader knows what the project does.
  - "Under one screen for install + run" is impossible with the current structure.
  - Accumulated cruft (old roadmap table, lok-era notes) remains unless explicitly excised.
- **Effort:** S
- **Risk:** low

### Approach B: Full rewrite from scratch

Replace README.md entirely with a new document structured as: one-paragraph thesis → three primitives → install → one-page example → roadmap → reference pointers. Archive the old README content under `docs/old-readme.md`.

- **Pros:**
  - Can hit the "under one screen for install + run" acceptance criterion.
  - Clean break from the inherited lok tone — the README speaks in loker's own voice.
  - Follows the issue's scope precisely.
- **Cons:**
  - Larger diff; more review surface.
  - Risk of losing useful content if the archive step is skipped.
- **Effort:** M
- **Risk:** low

### Approach C: Modular README with sub-sections

Keep README.md as a thin index that links to `docs/overview.md`, `docs/quickstart.md`, `docs/primitives.md`, etc. The README itself is just thesis + install + links.

- **Pros:**
  - Very short README; each topic lives in a focused document.
  - Discoverable via `docs/` directory.
- **Cons:**
  - GitHub README is the zero-click entry point; requiring link-following reduces first-impression retention.
  - Risk of docs rot in the sub-files if they aren't surfaced by the CLI or CI.
  - Over-engineered for a project that already has `docs/` organized by topic.
- **Effort:** M
- **Risk:** medium — sub-files may fall out of sync

## Approach chosen

**Approach B — Full rewrite from scratch.**

**Reason:** The acceptance criteria require the install + run section to fit under one screen, which is structurally impossible with the current README. A clean break allows us to write in loker's own voice (not inherited from lok), prioritize the newcomer experience, and archive the old content cleanly. The risk is low because the old content is preserved at `docs/old-readme.md` and the codebase is already well-documented elsewhere.
