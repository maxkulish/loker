# Discovery Report: CLO-319 — First-write-wins per-phase advisory lock

| Field | Value |
|-------|-------|
| Task | CLO-319 |
| Date | 2026-05-06 |
| Phase | discovery |
| Branch | `feat/clo-319-advisory` |

## Problem Framing

**Who is affected:** Operators running `loker resume` on workflows with HITL-blocked phases (via `HumanVerifier`) or any resumable phase where a previous run crashed mid-execution and left a stale `started` marker.

**Current behaviour:** `RunLock::acquire` (in `src/resume/lock.rs`) takes an OS-level exclusive advisory lock on `run_dir/.lock`. This protects the *entire run directory* from concurrent resume processes, but it is too coarse: it prevents two operators from concurrently resuming *different* phases of the same run. More importantly, once the run-level lock is released, nothing prevents two resumed processes from racing into the *same* paused phase (e.g. a HITL gate where two operators independently run `loker resume <id>`). The phase runner has no awareness of in-flight per-phase work, so both writers may simultaneously create attempt directories, overwrite markers, and corrupt the run state.

**Desired behaviour:** A filesystem-based advisory lock keyed by `(run_id, phase_name)` with first-write-wins semantics. The first process to acquire the lock proceeds; the second sees a clear, actionable error without spawning backend work. If the original process crashes, the lock must become reclaimable after a staleness timeout (PID + timestamp inspection, matching the heartbeat protocol already in `src/run_state/heartbeat.rs`). The lock state must be readable on disk so that `loker ls --blocked` (T-044 / CLO-313) can enumerate which phases are currently locked and by whom.

**Why now:** T-048 (`HumanVerifier` scaffold) is in progress. Once a phase can pause for human review via `pending/<phase>.json`, concurrent resume attempts on the same blocked phase are a real risk. T-050 is the prerequisite lock layer before T-051 (per-gate fallback server) and T-053 (UI sessions list) can safely execute.

## Existing Code

### Run-level advisory locking
- `src/resume/lock.rs`
  - `RunLock` uses `fs2::FileExt::try_lock_exclusive()` on `run_dir/.lock`.
  - Acquire is non-blocking; returns `ResumeError::LockInUse` when held.
  - Lock is released on `Drop` (fd close). No content is written to the file.
  - Two unit tests cover acquire/release and contention.

### Run directory & marker layout
- `src/run_state/run_dir.rs`
  - `RunDir::create` sets up `runs/<slug>-<ts>-<uuid>/` with `manifest.json`, `attempts/`, `trace.jsonl`.
  - `AttemptDir` gives scoped handles for `attempts/<phase>/<n>/`.
- `src/run_state/markers.rs`
  - `MarkerWriter` writes `started`, `completed`, `failed` markers atomically via `atomic_write`.
  - `StartedMarker` already carries `writer_pid`, `writer_host`, `started_at`, and `heartbeat_ttl_seconds`.
- `src/run_state/heartbeat.rs`
  - `HeartbeatWriter` spawns a Tokio task that ticks `heartbeat.json` every `interval_seconds`.
  - `is_stale` compares `tick_at` against `now - ttl_seconds`.
  - Proven pattern: PID + timestamp + host in a JSON file for crash detection.

### Resume orchestration
- `src/resume.rs`
  - `ResumePlanner` inspects phase markers and decides `Skip`, `Resume { next_attempt }`, or `RunFresh`.
  - `ResumeRunner::execute` archives the current attempt and calls `PhaseRunner::run`.
  - `archive_current_attempt` renames `run_dir/<phase>/` → `attempts/<phase>/<n>/`.
- `src/main.rs` (resume handler)
  - Acquires `RunLock`, sweeps stale tmp, loads `RunState`, checks heartbeat, then plans and executes.
  - No per-phase lock is consulted today.

### HITL scaffold (dependency)
- `src/strategy/verify/human_verifier.rs`
  - Writes `pending/<phase>.json` and waits on `responses/<phase>.json`.
  - The pending/response paths are scoped to the run directory.
  - When a phase is paused for human review, the next `loker resume` will re-enter `PhaseRunner::run` for that phase — exactly when the race occurs.

### Baseline score: 7 / 10

The codebase already has all the building blocks: advisory locking via `fs2`, atomic writes via `atomic_write`, PID/timestamp-based stale detection via heartbeat, and phase-scoped attempt directories. The gap is specifically a *per-phase* lock primitive that composes these pieces. No rewrite of run-state layout or marker schema is needed.

## Approaches Identified

### Approach A — Per-phase lock file with OS advisory locking
Create a new `PhaseLock` struct in `src/run_state/phase_lock.rs` (or extend `src/resume/lock.rs`). Each phase gets its own lock file at `run_dir/locks/<phase>.lock`. The lock file contains a JSON payload with `writer_pid`, `writer_host`, `acquired_at`, and `ttl_seconds`. Acquire uses `try_lock_exclusive` on the file; on contention, the loser reads the payload to report who holds it. A stale check inspects PID liveness + timestamp before attempting reacquisition.

- **Pros**
  - True first-write-wins via `flock` / `LockFileEx` — kernel-enforced against all OS processes.
  - Lock state is readable JSON for `loker ls --blocked` without additional APIs.
  - Reuses existing `fs2` dependency and `atomic_write` protocol from D3.
- **Cons**
  - Requires a new `locks/` subdirectory in the run directory layout.
  - Windows path may need slightly different PID-liveness check (no `libc::kill(0)`; use `OpenProcess` or skip PID check on non-Unix).
- **Effort:** M
- **Risk:** low

### Approach B — Marker-based locking (no OS advisory lock)
Write a `<phase>.locked` marker under `run_dir/markers/` containing PID + timestamp. Acquire reads the marker; if absent, writes atomically and succeeds. If present but PID+timestamp is stale, overwrites and succeeds. If present and live, returns contention error.

- **Pros**
  - No new directory; stays within existing `markers/` conventions.
  - Simpler to implement; no `fs2` locking calls.
- **Cons**
  - Read-check-write is racy under true concurrency (two processes can simultaneously read "no lock" and both write).
  - Not advisory: other tools (e.g. a Rust script using `fs2`) can ignore the marker.
  - Harder to guarantee first-write-wins without additional atomic primitives.
- **Effort:** M
- **Risk:** medium

### Approach C — Extend `RunLock` with phase name in lockfile content
Keep the single `run_dir/.lock` but write `{ "phase": "design", "pid": 1234, ... }` into it. The run-level lock serializes *all* phase access within the run. A second resume on any phase blocks until the first run finishes entirely.

- **Pros**
  - Minimal code change: reuse `RunLock`, just add JSON content.
  - No new directory or lock file schema.
- **Cons**
  - Far too coarse: resuming phase A cannot proceed while phase B is in progress in the same run.
  - Breaks parallel phase execution if the runner ever supports it.
  - Does not satisfy the requirement that two simultaneous resume attempts on the *same* phase are blocked while *different* phases should be allowed.
- **Effort:** S
- **Risk:** medium

## Approach Chosen

**Approach A** (per-phase lock file with OS advisory locking).

Reason: It is the only approach that provides true first-write-wins semantics against all OS processes, readable lock state for the upcoming `loker ls --blocked` command, and proven stale-lock recovery using the same PID+timestamp pattern already established by `HeartbeatWriter`. The new `locks/` directory is a small, additive extension to the run layout.

## Discovery Debt

- [ ] Exact lock TTL default: the issue mentions "60s heartbeat auto-release" in the roadmap table, but the acceptance criteria says "stale locks (process gone) are reclaimable on next attempt." We will use 60s as the default TTL (matching the roadmap and being shorter than the 300s run heartbeat) and make it overridable.
- [ ] Windows PID-liveness check: Unix can use `libc::kill(pid, 0)`. Windows may need `windows-sys` or we can fall back to "if timestamp > TTL, treat as stale" without PID check. This is acceptable for v0 because the issue explicitly scopes to a single machine (non-goals: distributed locking).
