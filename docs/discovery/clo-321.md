# Discovery Report: CLO-321 — Daemon mode `loker ui --serve`

| Field | Value |
|-------|-------|
| Task | CLO-321 |
| Date | 2026-05-07 |
| Phase | discovery |
| Branch | `feat/clo-321-ui` |

## Problem Framing

**Who is affected:** Operators using loker who need visibility into all runs on a host. Today, each run is an isolated directory under `runs/` with no unified web surface to inspect active, blocked, or completed runs.

**Current behaviour:** The per-gate fallback server (T-051 / CLO-320) provides a one-shot axum server that serves exactly one HITL gate and exits after a decision. There is no mechanism to browse all runs, list blocked gates, or view run state without filesystem navigation.

**Desired behaviour:** A long-running `loker ui --serve` daemon that binds to a localhost port, discovers all run directories under the configured runs root, and serves a web surface listing all known runs. The daemon reuses route handlers from T-051 and adds new endpoints for run discovery. Graceful shutdown (SIGINT/SIGTERM) with structured logging. Daemon survives individual run failures — a corrupt run directory does not crash the server.

**Why now:** T-051 (per-gate axum server) is complete, providing the route handler module and axum dependency. The roadmap Phase 12 (M11) starts here. T-052 is the foundation for sessions list (T-053), SSE tail-f (T-054), and threat-model tests (T-055). Without it, there is no daemon to extend.

## Existing Code

### T-051 per-gate axum server (`src/hitl_server/`)
- `src/hitl_server/mod.rs` — `GateConfig`, `ServerOutcome`, `ServerError` types. Module declarations.
- `src/hitl_server/routes.rs` — Shared axum route handlers: `GET /`, `POST /approve`, `POST /reject`. `AppState` struct with gate config and decision signalling. `router(state)` builds the `Router`. HTML rendering with `render_html` / `render_html_fallback`. Form handling with `DecisionForm`.
- `src/hitl_server/one_shot.rs` — `start(config)` binds to `127.0.0.1:0`, spawns the axum server on a background task, returns `ServerHandle` with addr + decision receiver + shutdown channel. Server exits on decision or `cancel()`.

### CLI structure (`src/main.rs`)
- `Commands` enum with `#[command(subcommand)]` for all commands.
- `find_project_root()` walks ancestors looking for `lok.toml`.
- `resolve_run_dir()` resolves bare run_id names to absolute paths under `runs/`.
- No `ui` or `serve` subcommand exists yet — must be added.

### Run directory discovery pattern
- `src/commands/ls_blocked.rs` — `scan_blocked_runs()` reads `<project_root>/runs/`, iterates each subdirectory looking for pending HITL gates. This is the closest existing pattern for run discovery and can be factored into a shared helper.
- Run directories are created as `runs/<slug>-<YYYYMMDD>-<HHMMSS>-<short_uuid>/` via `RunDir::create`.

### Run state loading (`src/run_state/`)
- `load.rs` — `RunState::load` reads `manifest.json`, scans markers, verifies artefact integrity. Returns `RunState` with `entries`, `phase_status`, `heartbeat`.
- `markers.rs` — phase status marker file conventions (`.started`, `.completed`, `.failed`).
- `run_dir.rs` — `RunDir::create` and path layout.

### Dependencies
- `Cargo.toml` already has: `axum = "0.7"`, `tokio = { features = ["full"] }`, `serde`, `serde_json`, `chrono`, `tower = "0.5"`.
- `tower` is already a dependency but `tower-http` (for CORS, etc.) is not needed — v0 is localhost-only with no auth.
- No new dependencies required for T-052. (T-054 SSE will need `notify` — deferred.)

### Baseline score: 8 / 10

The codebase has excellent primitives: the route handler module is explicitly designed for daemon reuse, axum is already in the dependency tree, run discovery via filesystem iteration works, and graceful shutdown patterns exist in the one-shot server. The score is 8 (not 10) because:
- The router in `routes.rs` is built for a single-gate `GateConfig` state. The daemon needs a different `AppState` that holds a runs index, not a single gate's config.
- Route handlers from T-051 will be extended, not directly composed — the daemon adds new routes (`GET /`, `GET /runs/:id`, etc.) at a different router root.
- No structured logging framework is wired in for long-lived daemon output.

## Approaches Identified

### Approach A — New `Ui` command with daemon module in-tree
Add a `Commands::Ui { serve: bool, bind: Option<String> }` variant to the CLI enum in `main.rs`. Create a new `src/ui/` module containing:
- `serve.rs` — daemon bootstrap: `bind` to `127.0.0.1:<port>`, run runs-discovery loop, spawn axum app, graceful shutdown on SIGINT/SIGTERM.
- `routes.rs` — daemon-specific routes: `GET /` (runs list), `GET /runs/:id` (per-run overview). Reuses `hitl_server::routes::router` for per-gate gate views at a nested path.
- `discovery.rs` — run directory scanner: list `runs/` dirs, load `manifest.json`, return structured summary.

The existing `hitl_server::routes::router` is composed at a sub-path (e.g., `GET /gates/:phase`), reusing 100% of its logic. No change to the one-shot server.

- **Pros**
  - Clean separation: `src/ui/` is independent from `src/hitl_server/`.
  - Reuses all T-051 route handlers via composition at a sub-path.
  - No new binary entry points or build complexity.
  - Runs discovery mirrors the established `ls_blocked` pattern.
  - Graceful shutdown via `axum::serve` with `with_graceful_shutdown`.
- **Cons**
  - Adds a new top-level module and command variant — minor maintenance surface.
  - Runs directory scanner must handle IO errors gracefully without crashing the server.
- **Effort:** M
- **Risk:** low

### Approach B — Extend hitl_server into a daemon module
Rename or extend `src/hitl_server/` to become a general UI server. Add daemon mode fields to `GateConfig` and conditional branching in the server bootstrap.

- **Pros**
  - Fewer modules; all UI code lives in one place.
  - Direct reuse of `GateConfig`, `AppState`, and `router`.
- **Cons**
  - `hitl_server` semantics are "one-shot per-gate fallback." Adding daemon concerns to the same module creates an awkward split of concerns.
  - The daemon's `AppState` (runs index) is fundamentally different from the one-shot's `AppState` (single gate config).
  - Conditional branching in shared types increases maintenance risk.
  - Naming becomes confusing: `hitl_server::daemon::start` vs `hitl_server::one_shot::start`.
- **Effort:** S
- **Risk:** medium (architectural debt)

## Approach Chosen

**Approach A** (New `Ui` command with daemon module in-tree).

Reason: Clean separation of concerns. The `hitl_server` module is purpose-built for one-shot per-gate fallback. Adding daemon concerns to it would violate the single-responsibility principle and create confusing semantics. A dedicated `src/ui/` module with `serve.rs`, `routes.rs`, and `discovery.rs` mirrors the project's existing module conventions (one module per concern, tested independently). The T-051 route handlers are reused via composition at a sub-path, satisfying the "share 100% of route handlers" requirement from FR-27.

## Discovery Debt

- [ ] The run discovery scanner must handle edge cases: empty `runs/` directory, non-directory entries, corrupt manifest.json, partially-written run directories, permission errors. Each should be logged and skipped rather than crashing the daemon.
- [ ] The runs list endpoint needs a sensible serialisation format for `GET /` (JSON + HTML). Start with JSON; the HTML template is deferred to T-053 (sessions list).
- [ ] Port allocation: default to a well-known port (e.g., 127.0.0.1:8080) or use `:0` and print? The AC says "localhost URL listing all known runs" — a predictable port is more usable for operators. Default to `127.0.0.1:8080`.
