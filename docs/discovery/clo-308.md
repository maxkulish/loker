# Discovery Report: CLO-308 — Extend `loker doctor` with TensorZero reachability check

## Problem framing

**WHO** is affected: Loker operators who configure `[tensorzero]` in `lok.toml` and want to verify their backend without launching a full orchestration run. Today `loker doctor` only checks for local LLM CLI binaries (codex, npx, claude) and API key env vars — it has no awareness of the TensorZero HTTP gateway that M1 tasks wired into the backend layer.

**WHAT** the current behaviour is vs WHAT we want: Current behaviour: `loker doctor` prints a binary-check table and API-key checklist. If TensorZero is the configured backend, the operator must run a full `loker ask` or manually `curl` the gateway to learn whether it is reachable. Desired behaviour: `loker doctor` prints an additional `tensorzero` row showing `HEALTHY` (green) or `UNREACHABLE` (red) with the underlying error class (DNS, connection refused, timeout, auth failure, or 5xx). This should honour `lok.toml` `[tensorzero]` config and env-overrides.

**WHY now**: This is roadmap task T-039 (Phase 8), PRD FR-35. The TensorZero config schema (CLO-250) and backend wiring (CLO-261) are both complete, so the `loker doctor` subcommand — which previously had no TensorZero config to read — now has a clear `endpoint` and `api_key_env` to probe. Adding reachability here completes the operator-facing diagnostic surface before M1 closes.

## Existing code

### `src/main.rs` — CLI entry & Doctor command
- The `Commands::Doctor` arm (≈60 lines) is entirely inline in `main.rs` starting at line 779.
- It checks three binaries via `which::which`, counts `available`, then prints API-key presence for `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, and `AWS_PROFILE`.
- The `config` variable (loaded at line 496 via `config::load_config`) is **not used** by the Doctor arm today.
- No tests cover the Doctor command output or exit-code logic.

### `src/config.rs` — TensorZero configuration
- `TensorZeroConfig` struct exists with `endpoint`, `default_model`, `api_key_env`, `timeout_secs`, and `retry_policy`.
- `TensorZeroConfig::to_backend_opts()` resolves `api_key_env` to an actual token from the environment.
- `Config.tensorzero: Option<TensorZeroConfig>` is populated from `lok.toml` layered loading.

### `src/backend/tensorzero.rs` — Backend HTTP client
- Uses `genai` crate with a custom `ServiceTargetResolver` for OpenAI-compatible surface.
- `TensorZeroBackendOpts` carries `endpoint`, `model`, `api_key`, `timeout`.
- Endpoint normalisation appends `/openai/v1/` to the configured URL.
- Extensive wiremock tests already exist in `tests/tensorzero_backend.rs`.

### TensorZero gateway `/health` endpoint
- Per TensorZero docs, `GET /health` checks gateway health + dependency health (Postgres/ClickHouse when enabled).
- Returns JSON `{ "gateway": "ok", "postgres": "ok" }` on success.
- For reachability validation, any 2xx response indicates the gateway is reachable and accepting HTTP.

### Test infrastructure
- `wiremock = "0.6"` in `[dev-dependencies]`.
- `tokio::test` + `MockServer` pattern already established in `src/backend/tensorzero.rs` inline tests and `tests/tensorzero_backend.rs`.
- `reqwest` is a direct dependency (used by `genai` and available for standalone calls).

## Baseline score: 9/10

Strengths:
1. Config layer (`TensorZeroConfig`) already reads `endpoint` and resolves `api_key_env`.
2. `reqwest` is available for making a direct HTTP probe.
3. `/health` endpoint contract is documented and stable.
4. Wiremock test framework is already integrated.
5. The `config` variable is already loaded at CLI startup and available in the `Doctor` arm.

Gaps:
1. Doctor logic is inline in `main.rs` and therefore awkward to unit-test.
2. No existing test coverage for `Doctor` command output.
3. The probe must not trigger the full `genai` client (lightweight `reqwest::get` is sufficient for a health endpoint).

No rewrite is needed; the work is additive and a minor refactor for testability.

## Approaches identified

### Approach A: Inline expansion in `main.rs`
- Add a `config.tensorzero.map(...)` block after existing checks that sends a `reqwest::get` to `{endpoint}/health` with the resolved `api_key` as `Authorization: Bearer <token>`.
- Classify the response/error into `HEALTHY`/`UNREACHABLE` with the error class printed inline.
- Integration-test the whole CLI via a subprocess or use `tests/doctor.rs` with main binary.
- Pros: smallest line-count change; no new module.
- Cons: `main.rs` Doctor arm grows larger; unit-testing requires either heavy integration-test harness or untested inline code.
- Effort: S
- Risk: low

### Approach B: Extract `src/doctor.rs` module (chosen)
- Move the existing Doctor logic and the new TensorZero probe into a `pub async fn run_doctor(config: &Config) -> (String, bool)` in a new `src/doctor.rs` module.
- `main.rs` calls `run_doctor(&config).await` and prints the returned pretty table.
- The function produces a `CheckResult` enum (`Healthy`, `Unreachable(DoctorErrorClass)`) that is trivially unit-tested with wiremock.
- Pros: testable with wiremock (no subprocess); clean separation of CLI plumbing from business logic; preserves existing output format and exit-code contract.
- Cons: requires moving ≈60 lines from `main.rs` into a new file.
- Effort: S
- Risk: low

### Approach C: Reuse `TensorZeroBackend` for the probe
- Construct a `TensorZeroBackend` via its existing `new()` path and call a hypothetical `health()` method on `Backend` trait.
- Pros: DRY — leverages existing client construction and auth resolution.
- Cons: `genai` client is overkill for a simple `GET /health`; would require adding a new `Backend::health()` trait method touching all backend implementations.
- Effort: M
- Risk: medium (trait churn, unnecessary abstraction)

## Approach chosen: Approach B

Extracting `src/doctor.rs` gives us immediate testability while keeping the change small. The existing Doctor inline code is already a self-contained concern (binary checks → API key checks → TensorZero probe → summary line). A module boundary simply makes it testable with the wiremock harness the project already uses. This also future-proofs `loker doctor` for additional checks (e.g. Docker daemon, orchestrator version) without further bloating `main.rs`.
