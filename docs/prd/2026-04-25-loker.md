## 1. Overview

loker is a Rust orchestration engine that runs multi-phase LLM workflows where each phase deliberately picks its model(s), provider(s), and aggregation strategy. It is a hard fork of `lok` that adds three primitives no production Rust or Go crate currently packages: an HTTP-gateway backend (TensorZero), explicit named strategies (`single`, `parallel`, `escalating_retry`), and first-class verify hooks (shell command, LLM judge, test runner, human reviewer). The reference workflow is `design-doc-tdd`: a four-phase pipeline that produces a design doc, fans out cross-family review, escalates implementation cheap-to-strong with test-driven verify, and runs a parallel verification check. loker stays agnostic about which provider answers any given call - that choice lives behind TensorZero or behind existing CLI subprocess backends inherited from lok.

**Scope expansion note (2026-04-25)**: An earlier note in `workflow-design.md` framed loker's predecessor as "not a workflow engine for human-in-the-loop product development." This PRD deliberately reverses that for v0 by including M10 (`HumanVerifier`) and M11 (`loker ui`). Rationale: HITL is a `VerifyHook` implementor that adds no new trait family, and a localhost-only browser UI fills a gap no other Rust tool covers cleanly. Documented here so reviewers do not mistake this for inherited scope.

## 2. Problem & Objectives

### Problem Statement

Engineers running AI-driven development today face three concrete gaps:

1. **No cross-family aggregation primitive.** Calling Anthropic, OpenAI, Google, and a local Ollama model in parallel and merging via a different-family judge requires hand-rolled code in every project. Empirical results (EdgeJury, arXiv:2601.00850) show same-family aggregation produces correlated failure modes, yet no Rust or Go library enforces cross-family diversity as a default.
2. **No named escalating-retry primitive.** Cascading from a cheap model to a strong one based on a verify gate is a known cost-saving pattern (FrugalGPT, cascadeflow), but every Rust agent framework either retries within one model or has no retry at all.
3. **No production-ready human-in-the-loop checkpoint.** Existing tools either require a SaaS backend, a heavy SPA, or shell out to ad-hoc scripts. Engineers want a localhost-only browser UI that gates a workflow phase on a human approve/reject with inline comments that flow into the next phase's prompt.

The cost of leaving these gaps unfilled is concrete: each project rebuilds the same hand-coded retry loop, cross-family review stays a research artefact rather than a default, and HITL is either skipped or implemented as Slack hacks.

### Objectives

- **O1**: Ship a Rust binary `loker` that runs the `design-doc-tdd` reference workflow end-to-end against real providers within a project-configured cost budget. The budget is set in `lok.toml` (or per-workflow); loker reports actuals via `summary.json` and warns on overshoot. v0 does not enforce a hard cap (post-v0 work).
- **O2**: Expose `Strategy::EscalatingRetry`, `Aggregator::LLMJudge` (cross-family enforced by default), and `VerifyHook::HumanVerifier` as documented public APIs that third parties can wire into their own workflows.
- **O3**: Achieve a pre-merge gate (`make check` = fmt + clippy + test) that runs in under 60 seconds with no live network dependency, so contributors can iterate locally.
- **O4**: Provide an opt-in `LOKER_TZ_INTEGRATION=1` integration suite that boots TensorZero via Docker Compose and validates a real round-trip in CI.

## 3. Users & Use Cases

### Personas

| Persona | Role | Need | Pain Point |
|---------|------|------|------------|
| Solo Rust engineer running AI workflows on their own box | maintainer-as-user | Reliable design-review-implement-verify loop without writing per-project orchestration | Hand-coded retry and review logic in every repo; no cross-family default |
| Small team adopting AI-assisted development | downstream user | Drop-in workflow runner triggered from CI, git hooks, or interactive agents | LangGraph/LangChain too heavy; bespoke shell scripts brittle |
| Researcher exploring cross-family aggregation | technical reader | A reproducible Rust implementation of EdgeJury / ORCH patterns | Papers describe the protocol; no production code packages it |

### Key Use Cases

**UC-1: Run `design-doc-tdd` from a terminal**
- Trigger: User runs `loker run design-doc-tdd --spec specs/feature-x.md`.
- Steps:
  1. loker reads `lok.toml` (or workflow file), resolves backend names, validates cross-family constraint.
  2. Phase `design` calls a single strong reasoner via TensorZero.
  3. Phase `review` fans out to three different families in parallel; an `LLMJudge` from a fourth family merges.
  4. Phase `implement` cascades cheap -> medium -> strong with `cargo test --quiet` as the verify gate.
  5. Phase `verify-tests` runs two parallel checks; `AnyFail` aggregator surfaces any rejection.
  6. Run directory `runs/<id>/` contains every artefact, plus `trace.jsonl` in OpenTelemetry GenAI conventions.
- Outcome: Reproducible run record, cost <= ~$1.50, downstream phases consume upstream artefacts via filesystem.

**UC-2: HITL gate on a high-severity phase**
- Trigger: Workflow author declares `verify_hook = { type = "human", severity = "high" }` on a phase.
- Steps:
  1. Engine writes `runs/<id>/pending/<phase>.json` and either notifies the running daemon or spawns a one-shot axum server.
  2. Reviewer opens browser, sees pending panel, leaves global + inline comments, clicks Approve or Reject.
  3. UI writes `runs/<id>/responses/<phase>.json` (first-write-wins).
  4. Engine picks up the response, maps to `VerifyResult::Pass { notes }` or `Fail { reason }`, threads comments into next phase's prompt context.
- Outcome: A human pivot decision is captured, durable, and replayable from filesystem only - no daemon required for the gate to terminate.

**UC-3: Resume a partially complete run**
- Trigger: User runs `loker resume <run_id>`.
- Steps:
  1. loker walks `runs/<id>/`, identifies which phase artefacts already exist.
  2. Skips completed phases; restarts from the first incomplete phase.
  3. For `parallel` strategy with one failed reviewer, only the failed reviewer reruns (step-level granularity for that strategy).
- Outcome: No wasted recomputation; the user can iterate quickly when one external API stalls.

**UC-4: Trigger from an agent CLI or git hook**
- Trigger: Claude Code / Codex / OpenCode / `pre-push` hook calls `loker run pre-pr-validation`.
- Steps: identical to UC-1 but the invoker is a script or another agent.
- Outcome: loker behaves identically regardless of trigger - one binary, many drivers.

## 6. Scope & Phasing

### Recommended Phasing Slices

The eleven milestones split cleanly into three slices that can be reviewed and released independently. This grouping is the recommended sequencing for review and shipping; the per-milestone scope below is unchanged.

| Slice | Milestones | Goal | Exit Criteria |
|-------|------------|------|---------------|
| Slice A - Vertical core | M1 - M6 | A working `design-doc-tdd` reference workflow with HTTP-gateway backend, all primitives, and resumable runs | M6 integration test green on `examples/specs/calculator.md`; pre-merge gate <= 60s |
| Slice B - Polish & docs | M7 - M9 | TensorZero deployment recipe, CLI ergonomics, migration documentation | M9 doc accepted; `cargo doc` covers every public trait + named primitive |
| Slice C - HITL & UI | M10 - M11 | `HumanVerifier` + per-gate fallback + daemon UI | M11 UI passes threat-model test suite and per-gate fallback works without daemon |

Slice A is the loker thesis. If A ships green and the project must stop, B and C can be deferred without compromising the cross-family + escalating-retry + verify-hook story.

### In Scope (v0 - Milestones M0 through M11)

- M0 Fork preparation (done): clone, rename, all inherited tests green.
- M1 TensorZero backend via `genai` resolver, mocked + opt-in real-gateway tests.
- M2 Strategy primitives: `SingleModel`, `ParallelFanOut`, `EscalatingRetry`.
- M3 Aggregator vocabulary: `Concat`, `LLMJudge`, `AnyFail`, `Vote` plus cross-family enforcement.
- M4 Verify hooks: `RunCommand`, `LLMVerifier`, `TestRunner`.
- M5 Phase runner + `trace.jsonl` + skip-on-exists resumability.
- M6 `design-doc-tdd` reference workflow + prompt templates + tiny example spec.
- M7 TensorZero deployment recipe (Tier 2: gateway + ClickHouse + UI via docker-compose).
- M8 CLI polish: `explain`, `resume`, `doctor`, `trace` pretty-printer.
- M9 Documentation: README, one-page tutorial, lok-to-loker migration note.
- M10 `HumanVerifier` + per-gate fallback axum server.
- M11 `loker ui` daemon + sessions list + detail view.

### Out of Scope (v0)

- **GUI / TUI for non-HITL workflows.** lok ecosystem already has agtx and ralph-tui. Reason: scope discipline; HITL UI is the only graphical surface v0 ships.
- **Persistent state inside loker itself.** Filesystem is the source of truth. Reason: replayability and zero-daemon HITL termination depend on it.
- **Distributed execution across machines.** Reason: one-binary-on-one-box is the v0 use case; distribution is a different design problem.
- **Learned coordinator / routing.** Reason: the whole point of the fork is hand-encoded routing; learned routing belongs in a future `Strategy::Learned`.
- **Observability dashboard.** TensorZero UI supplies it. Reason: avoid duplicating the transport layer's tooling.
- **Agent-style multi-turn tool-use through the HTTP backend.** Use subprocess backends for that. Reason: the HTTP path is for stateless calls; tool-use loops belong in a follow-up.
- **Logprobs / semantic similarity verification.** `Score(f32)` API shape reserved, no implementation in v0. Reason: adds embedding dependency and calibration burden without proven demand.
- **Multi-tenant SaaS deployment of the UI.** Localhost only. Reason: the user's workflow is solo or small-team review, not 1000-user.
- **In-browser artefact editing or chat-style threading.** Comments only. Reason: each gate is one decision; threading is a different product.
- **Workflow registry / sharing as crates.** Reason: workflows live in user's repo for v0; registry is post-v0.

## 9. Rollout & Measurement

### Release Plan

- **Versioning**: `make release` auto-versions `YYYYMMDD.0.X`, tags, builds, installs to `/usr/local/bin/loker`, pushes. Confirm with the user before invocation.
- **Distribution**: GitHub release with binary tarballs for macOS (arm64) and Linux (x86_64). Cargo install from source for everything else.
- **Migration from `lok`**: M9 doc maps every existing lok knob to its loker equivalent. `lok.toml` and `.lok/workflows/` keep their names through v0 with a deprecation window planned post-v0.
- **Rollback**: previous binary versions stay in the GitHub releases page; users reinstall the prior tag.
- **Feature flag strategy**: not used. v0 ships milestones in order; each milestone is independently releasable.

### Measurement Plan

- **Per-run cost** tracked in `runs/<id>/summary.json` (M5+) and compared against the project's configured `cost_budget_usd` (FR-23a); aggregated manually until post-v0 dashboard exists. No fixed threshold lives in loker itself.
- **Pre-merge gate wall time** tracked by reading CI logs; M9 doc captures the M3-reference-machine baseline.
- **Test count** tracked via `cargo test -q` output in each commit message for milestone-closing commits.
- **Cross-family default coverage** asserted by M3 unit tests; regression caught at pre-merge gate.
- **First measurement**: at M6 close (first end-to-end reference workflow run with cost numbers).
- **Decision criteria**:
  - If mean cost on the reference workflow trends above the project's configured budget across 10 measured runs, revisit `EscalatingRetry` prompt-context-propagation default and the reference workflow's model lineup.
  - If pre-merge gate exceeds 90 s, split slow tests behind an opt-in flag.
  - If cross-family default refusal rate is < 95 % on user-authored workflows, the lookup table needs more coverage before post-v0.

## 11. Pre-implementation Discovery

Review pass 1 surfaced four blind spots that should be closed by spike or written artefact before implementation hardens further. Treat this section as a checklist that gates Slice A (M1 - M6) feature work.

### D1 - TensorZero round-trip spike (blocks M1 close)

**Question**: Does `genai::ServiceTargetResolver` cleanly route to a TensorZero gateway with the auth, model-name mapping, and observability fields loker expects? What does the gateway return for token counts, family identity, and error shapes?

**Method**: stand up a local TensorZero (Tier 2 docker-compose), wire one `tensorzero/<id>` mapping, run a single `single_model` strategy end-to-end. Capture: request headers actually sent, response JSON shape, `BackendCapabilities` derivable fields, observability records as ClickHouse queries.

**Output**: `docs/spikes/2026-04-25-tensorzero-roundtrip.md` with raw request / response pairs and a verdict on whether the in-flight `src/backend/tensorzero.rs` scaffolding matches reality.

### D2 - JSON schemas for run artefacts (blocks M5 close)

**Question**: What are the canonical schemas for `trace.jsonl`, `manifest.json`, per-phase result files (`design.md` is markdown but `verify.json` is structured), HITL `pending/<phase>.json` and `responses/<phase>.json`, and `summary.json`?

**Method**: write JSON Schema (draft 2020-12) for each file. Reuse OpenTelemetry GenAI semantic conventions for `trace.jsonl` records; document loker custom fields under `loker.*` prefix.

**Output**: `docs/schemas/` directory with one `.schema.json` per artefact; CI step that validates fixtures against the schemas.

### D3 - Atomic run-state rules (blocks FR-21, FR-23b - FR-23e)

**Question**: What is the exact write protocol for phase artefacts, manifest entries, and status markers such that any crash leaves the run resumable without manual cleanup?

**Method**: write down the rules. Two candidates: (a) write artefact to `<name>.tmp`, fsync, rename to `<name>`; write manifest entry to `manifest.json.tmp`, fsync, rename; write `phase.completed` last. (b) attempt directories: each retry writes under `attempts/<phase>/<n>/`, the canonical artefact is a symlink (or content-addressed pointer) to the latest successful attempt. Pick one, document the failure modes the other handles less well.

**Output**: Section in `docs/handoff.md` (or new `docs/run-state.md`) with the write protocol, a fault-injection test plan, and the chosen scheme for FR-23e attempt directories.

### D4 - Threat model for `loker ui` (blocks M11)

**Question**: What is the realistic attacker model for a localhost-bound axum server reading filesystem artefacts? Specifically: malicious browser tab making cross-origin POSTs, malicious browser extension reading the page, symlink in a run directory pointing outside the run root, path traversal in URL parameters, stale lock takeover.

**Method**: write the model. Map each Security NFR row to a concrete test fixture. Decide whether v0 needs a per-session token in the URL or whether origin checks plus localhost bind are sufficient.

**Output**: `docs/security/2026-04-25-ui-threat-model.md` with the model, mitigations, and the test list M11 must satisfy.

These four artefacts are the entry tickets to their respective milestones, not retrospective documentation. M1 stays "in flight" until D1 lands; FR-23b - FR-23e do not get implementation work until D3 lands.
